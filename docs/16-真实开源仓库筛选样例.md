# 真实开源仓库筛选样例：三个 PPT 项目

核验日期：2026-09-03。这里不评“哪个项目最好”，而是评它们对 WPS 插件的具体用途：学习设计、复制局部模式，还是直接引入依赖。

## 比较结论

| 项目 | 最值得借鉴 | 主要不匹配 | 建议 |
|---|---|---|---|
| [PPTAgent](https://github.com/icip-cas/PPTAgent) | 模板诱导、布局选择、编辑式生成、生成后评估 | Python、模型、浏览器、容器与 MCP 依赖面大；未验证 WPS | 学 Agent 架构，不直接依赖 |
| [PptxGenJS](https://github.com/gitbrent/PptxGenJS) | JS/浏览器生成 OOXML，shape/chart/table API 清晰 | 跨 Office/Keynote/WPS 兼容仍有 Issue；测试偏手工；当前依赖告警 | 做隔离 spike，验收后再决定 |
| [Marp CLI](https://github.com/marp-team/marp-cli) | Markdown→HTML/CSS→渲染→导出的转换链 | 默认 PPTX 是整页位图；editable 路径依赖 LibreOffice 且有可复现性警告 | 借鉴管线，不嵌入 WPS 插件 |

三者均为公开、未归档、MIT 仓库，但这只解决许可证入口，不证明架构匹配或供应链安全。

## 最适合演示：Marp CLI

这个例子能清楚说明“功能名称相同，工程语义可能不同”：

1. 搜索“PPTX export”，README 看起来完全匹配。
2. 进入 [`converter.ts`](https://github.com/marp-team/marp-cli/blob/main/src/converter.ts)，普通路径实际上先把页面渲染成 PNG，再由 PptxGenJS 写入 PPTX。
3. 因此得到的是可播放的幻灯片，不等于 WPS 中可编辑的文本、形状和图表对象。
4. experimental editable 路径依赖 LibreOffice 的 PDF→PPTX，源码明确警告可复现性不能保证。
5. 依赖审计还显示 Puppeteer、解析器等更宽的运行和供应链表面。

结论不是“Marp 不好”，而是：它非常适合静态渲染与导出的目标，却不符合 WPS 案例的原生可编辑目标。可借鉴转换管线和预览/导出分离，不能直接把整个工具塞进插件。

## PptxGenJS：最接近代码复用的候选

[`pptxgen.ts`](https://github.com/gitbrent/PptxGenJS/blob/master/src/pptxgen.ts) 与 [`slide.ts`](https://github.com/gitbrent/PptxGenJS/blob/master/src/slide.ts)提供浏览器/Node 侧 OOXML 和 `addChart`、`addShape`、`addText` 等抽象，与插件语言更接近。

但采用前仍有三个否决风险：

- 项目测试说明主要依赖跨浏览器、Node、Office/M365 的手工检查，不能假设 WPS 兼容。
- Issue #1531/#1532 暴露跨渲染器图表丢失和 shape ID 冲突风险。
- 临时 `npm audit --omit=dev` 在核验日发现 `image-size` 的 high 风险信号且当时无直接修复；这是精确 lockfile 的调查入口，不等于宣称整个库不安全。

合理下一步是隔离 spike：用目标版本生成包含文本、图表、表格和图片的 PPTX，在 WPS 与 PowerPoint 分别打开、编辑、保存、重开，再决定是否采用。

## PPTAgent：学习高级设计，不复制整个系统

PPTAgent 当前源码中的 `generate_slide`、`_select_layout` 和 `ppteval` 展示了布局候选、内容生成、编辑命令与生成后评价的组合。它适合回答“AI 幻灯片系统如何分层”，但完整依赖包含模型、检索、Playwright、Docker、MCP 和 Web 服务，远超 WPS 插件需要。

这里最值得复制的是接口思想和评价维度，而不是运行栈。Issue #253 和 #240 也表明 MCP 内容块、macOS Docker/WebUI 等环境组合仍会产生故障。

## 评分时必须注明的限制

- Stars、commit、release 和漏洞数都是时点数据，演示前重查。
- `npm audit` 只覆盖当前解析到的 npm 依赖及 registry advisory；查不到不等于安全。
- 本轮没有在 WPS 中执行三个项目，因此“兼容/不兼容”只能由后续 spike 裁决。
- 项目目的不同，不能把“对 WPS 不合适”写成“项目质量差”。

## 演示脚本

```text
仓库声称支持 PPTX
→ 搜索转换 symbol
→ 发现逐页 PNG 实现
→ 检查 editable 分支的官方警告
→ 对照 WPS 的“对象可编辑”成功标准
→ 决定只借鉴管线，不引入整套依赖
```

这段比展示 stars 排名更能体现 AI 调研的价值：AI 帮忙快速读穿多个实现，而人的成功标准决定什么才算可用。
