# T01：Tabloom 信息缺口与来源路由

## 要支持的主张

AI 技术调研不应从宽泛主题搜索开始，而应先把当前决策拆成信息缺口，再为不同问题选择匹配的证据来源。

## 原始链

| 节点 | 内容 |
|---|---|
| 决策问题 | Chrome 原生组、侧边栏、空组、Service Worker、模型分组和发布分别有哪些未知 |
| 信息缺口 | 平台能力、产品价值、代码数据流、真实模型返回、版本/发布一致性 |
| 来源选择 | 官方文档、用户原型反馈、源码/测试、固定假数据 live harness、Git/远端 |
| 转换规则 | 先判断问题属于哪一层，再使用能直接观测该层的来源 |
| 行动 | 选择 Side Panel、建立草稿层、修复导入与空组、保留解析器、增加发布审计 |
| 固化 | 设计、实施计划、回归测试、开发复盘与研究轨迹 |

## 四个例子

1. “侧边栏能否实现”由 Chrome 官方文档回答；“侧边栏里哪些控件有价值”由真实尺寸原型和用户反馈回答。
2. 动态导入错误由错误文本缩小范围，再由 Service Worker 官方文档确认运行边界。
3. 空组是否存在同时需要平台实体事实与用户产品语义，最终通过草稿/原生两层模型兼容。
4. 非 Thinking 不分组不能由 mock 裁决，转向真实 API 原始输出后才确认该次空分组来自模型答案。

## 裁决

- “该项目实际使用了多类信息源支持不同决策”：**FULL**，有同时期产物、测试和 Git 时间线。
- “这套来源路由普遍提高效率”：**NONE**，没有对照组或时间测量。
- “完整保存了当时全部搜索过程”：**NONE**，历史查询和工具日志不完整。

2026-09-07 新鲜验证：在 Node 24.19.0 下 37 项测试通过，扩展结构验证通过。默认 Node 14.17.6 无法启动 `node:test`，这同时验证了“运行结果必须绑定环境”的边界。记录见 [`source-and-runtime-report.json`](runtime/tabloom/source-and-runtime-report.json)。

## 演示用法

最小画面是一张路由表：

```text
平台事实 → 官方文档
产品事实 → 原型与用户
代码事实 → 源码与测试
运行事实 → 最小真实实验
历史事实 → Git 与发布端
过程纪律 → Skill 与门禁
```

推荐度：S。具体 Chrome API、九色枚举和提交哈希留在完整案例或附录。

2026-09-08 复核 Chrome 官方 Side Panel、tabGroups 与 extension service worker 文档：三条平台入口仍可用，动态 `import()` 的限制仍有官方说明。它们只支持平台边界，不替代产品价值与真实模型行为证据。详见[易变事实复核](../sources/volatile-fact-check-2026-09-08.md)。
