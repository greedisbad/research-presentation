# T02：Tabloom 真实边界与业务有效性

## 要支持的主张

自动测试、mock 和结构校验通过后，AI 结果仍可能在真实边界上无用；需要用安全固定输入观察原始响应，并把“可解析、结构合法、业务有效、用户有用”分开验收。

## 现场问题

关闭 Thinking 后，标签有时全部留在未分组。候选原因至少包括：

- 请求参数没有正确关闭 Thinking；
- SSE 正文或 reasoning 分片解析错误；
- JSON 提取或 schema 校验丢失 groups；
- UI 没有应用已解析草稿；
- 模型原始答案就是空 groups。

## 证据升级

| 层 | 动作 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| 单元测试 | 构造 SSE、JSON 和各种 ID/颜色输入 | 客户端对已知输入的请求、解析与校验行为 | 真实供应商会返回什么 |
| 开发者输出 | 展示真实最终 content/reasoning | 传输到扩展边界的数据 | 模型长期稳定性 |
| live harness | 9 个固定假标签、三种模式、Thinking 对照 | 当次真实 API 的原始业务结果 | 真实用户标签与所有未来版本 |
| 用户草稿 | AI 结果先进入可编辑草稿 | 人可检查、修正、重置后再保存 | 自动分组质量已达到生产标准 |

该次用户提供的最终 JSON 中 `groups` 为空，全部真实 tab ID 在 `ungroupedTabIds`。结合边界输出，项目没有把它改写成解析 bug，而是把结论限制为：该次模型返回了结构合法但业务无用的方案。

## 四层门禁

1. **传输完整性**：响应是否到达、流是否结束、content/reasoning 是否分开。
2. **结构有效性**：JSON、类型、颜色、所有 ID 恰好出现一次。
3. **业务有效性**：是否真的改变分组，是否满足用户选择的策略。
4. **人工价值**：组名和归属是否合理；保存前用户是否接受。

## 安全与复现边界

- live harness 使用固定假标签，不读取真实标签内容。
- Key 位于 Git 忽略的 `.env.local`，不打印、不提交。
- 日志只输出耗时、推理字符数、组摘要与未分组数量。
- 真实模型结果会随版本、负载和随机性波动，只能绑定当次运行。

## 裁决

- “mock 通过不能证明真实模型业务结果有用”：**FULL（在本案例）**。
- “该次空分组来自模型原始回答而非解析丢失”：**FULL（绑定当次用户提供输出与边界观测）**。
- “非 Thinking 一定不分组”：**NONE**，不得外推。
- “默认 low Thinking 是所有场景最佳配置”：**NONE**，只是本项目当时产品取舍。

## 演示用法

推荐度：A。正文只展示：

```text
mock 全绿 + schema 合法
            ≠
        业务结果有用
```

完整请求字段、模型名和参数放附录，并在演示冻结前重新核验。
