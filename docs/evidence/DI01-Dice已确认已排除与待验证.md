# DI01：Dice 已确认、已排除与待验证

## 要支持的演讲主张

AI 调研不应在会话结束时重置。把结论分成“已确认、已排除、待验证”，并为下一个任务附上边界与验收条件，才能让调研结果跨会话累积，避免后续 Agent 重新搜索、重新争论或重踩已知失败路线。

## 案例位置

Dice 的游戏业务不是本切片的讲解对象。有用的是三份连续复盘共同保存了：

```text
当前已经做到什么
→ 哪些决定可以直接消费
→ 哪些路线不要重复调研
→ 仍有哪些风险必须通过新证据裁决
→ 下一个纵向切片是什么
```

这是“一次调研的输出如何成为下一次 Agent 的输入”的本地案例。

## 三栏状态不是三种摘要

### 1. 已确认：后续任务可以当作当前基线

合格的已确认项不只是“我们选了 X”，还要包括证据和作用范围。例如：

- 第一阶段明确当前只是程序化角色切片，真实 GLB 管线仍是待验证项；
- 第二阶段用一个 Knight 完成静态托管、GLTF 加载、骨架克隆、动画、阴影、fallback 和构建的纵向试点，通过后才扩展到四个角色；
- 第三阶段明确状态机、私有输入和公开投影的边界，并记录测试、类型检查、构建与浏览器证据。

已确认项的作用是缩小下一个 Agent 的自由度：默认沿用，除非它能提供触发重开的新证据。

### 2. 已排除：带条件的负知识

复盘明确列出了不要重复的工作，例如：

- 已经选定资产基础并实装后，不再重新广泛比较 KayKit、Quaternius 或 AI 3D 生成；
- 不再讨论用物理引擎决定骰子结果，继续由 engine 决定结果、Three.js 负责确定性演出；
- 不用放大筛盅规避几何问题，因为安全阵列方案已建立；
- 首版不再评估远程 TTS，已选择浏览器 SpeechSynthesis；
- 已有特定 host 测试覆盖后，不因后续评审漏读文件而重复添加同类测试。

但“不要重复”不等于永久禁止。负知识应当绑定：当时环境、被观察的问题、已选方案、不选原因以及什么变化会使它重新成为开放问题。

### 3. 待验证：下一轮调研的查询队列

“待验证”不是普通 TODO，而是一组已指向证据的未知项：

| 未知 | 需要的证据 | 触发时机 |
|---|---|---|
| 真实 GLB 的坐标、骨架、动画和加载链是否可用 | 先导入一个角色的纵向切片 | 批量导入前 |
| 四个 GLB 并发加载对移动端的影响 | 目标移动设备的内存与首屏观测 | 上线或扩大角色集前 |
| feature branch 合并后是否冲突 | 在目标基线实际合并并重跑门禁 | 决定合并时 |
| 最终局是否总是先执行惩罚再显示获胜界面 | 真实浏览器终局路径 | 发布前 |
| 刷新时 active session 是否恢复且不重复计数 | 恢复 E2E 与计数断言 | 启用持久化后 |
| Safari、移动端或无 voice 环境下的语音反馈 | 目标环境能力测试与可见降级 | 扩大平台前 |

待验证列表的作用是让下一轮调研从高价值未知开始，而非再从项目名称开始搜索。

## 一个信息如何在三栏之间移动

KayKit 管线在两天间展示了状态转换：

```text
08-31：真实 GLB 管线是最高风险、待验证
→ 09-01：单个 Knight 纵向切片验证整条管线
→ 09-01：KayKit 成为已确认基线，“重新比较资产库”进入已排除
→ 新待验证项转为移动端并发加载、动画混合和部署体验
```

这比一张静态“Lessons Learned”清单更重要：调研状态会被新证据推进，而不是写完后永久不变。

## AI 评审也要进入三栏裁决

09-02 复盘记录了一个非常适合演讲的小例子：

- 第一轮评审指出缺少 host 调度覆盖和旧 timer 所有权清理，有证据，接受并修复；
- 后续两次评审仍称测试缺失，但只查看了 `store.test.ts`，漏读新增的 `host.test.ts`；
- 主线根据具体文件、diff 和测试输出拒绝误报，但同时没有拒绝同轮中有证据的 timer 问题。

因此：

```text
Review finding
→ 定位它声称涉及的文件或行为
→ 查 diff / 测试 / 运行证据
→ Accept / Reject / Defer
→ 将真正问题和已排除误报分别记录
```

AI 评审结论是候选信息，不是高于源码和运行证据的特权结论。

## 任务 brief：把调研状态变成可执行输入

三栏状态用于管理知识；任务 brief 用于让下一个 Agent 行动。最小交接应包含：

```yaml
goal: 本轮要消除的一个高价值未知
non_goals: 不在本轮重新打开的问题
confirmed: 可作为基线的事实和决定
rejected: 已排除路线及其环境和原因
unknowns: 本轮需要新证据的问题
must_read: 必须查看的文件和原始证据
ownership: 可修改的模块与不可触碰的边界
acceptance: 可重跑命令或可观察结果
handoff: 完成时必须报告的决定、失败和剩余风险
```

它不应是整段聊天记录的复制，而是当前有效状态的索引。

## 候选视觉素材

1. **三栏看板**：Confirmed / Rejected / Unverified，每栏放一条 Dice 例子。
2. **状态转换时间线**：“GLB 待验证 → Knight 试点 → KayKit 已确认 → 移动端加载成为新未知”。
3. **一条负知识卡**：不只写“不用物理引擎”，而是展示环境、目标、决定与重开条件。
4. **Review 裁决分叉**：同一份评审中，有证据的 timer 问题进入 Accept，漏读文件的“缺测试”进入 Reject。
5. **Task brief 界面**：左边是巨大聊天记录，右边是一页目标/边界/证据/验收。

## 候选讲述顺序

1. 一个 Agent 结束工作后，下一个 Agent 看到的通常只是代码和一大段聊天。
2. 展示三栏看板，说明三栏分别控制默认沿用、禁止无证据重开和下一轮检索。
3. 用 KayKit 的两天状态转换证明三栏不是死档案。
4. 用 AI 评审误报说明新结论仍要通过证据裁决。
5. 以任务 brief 收束：调研资产要能被下一个 Agent 直接消费。

## 一句可迁移结论

> 不要只对 AI 说“接着做”；先告诉它什么已经确认、什么不应重走、什么必须用新证据回答。

## 证据边界

- 三份文档都是工程复盘，包含事后组织与实践者判断，不是全量实时 telemetry。
- 本切片核验了原始复盘的当前文本和哈希，未重跑 Dice 游戏测试、构建或浏览器验收。
- 复盘中的测试数量、提交和运行结果是历史记录，本切片不将它们写成本轮新鲜验证。
- “减少重复搜索”在本项目中没有时间或 token 对照，只能作为可检查的流程意图，不能宣称已证明效率改善。
- 复盘中的具体游戏选择只是展示记录结构的载体，不进入演讲主体。
