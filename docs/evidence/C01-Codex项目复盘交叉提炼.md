## 第五幕可以归纳的 Codex 优势

### 1. 项目定向，而非只对话定向

Codex 能读取项目规则、目录、源码、依赖、测试、Git 和既有研究。它工作的对象不是一段孤立提问，而是一个带历史和工具的工作区。这使“当前安装版本”“已有失败路线”“哪个包不能动”等信息可以持续参与判断。

### 2. 把生成接到现实反馈上

代码生成后继续接收编译、类型、lint、测试、浏览器控制台、实例状态、截图与真实用户观察。它们分别过滤不同错误；成本高，但比让模型在文本里继续自信地猜更有价值。

### 3. 让错误改变问题表示

失败不只触发“再改一版”，而是把宽泛症状重写成带发生层、版本和预期不变量的问题，再转向更合适的文档、源码、Issue、提交或实验。

### 4. 把一次工作变成项目资产

结论被写成测试、脚本、schema、来源卡、提交、复盘和下一步，而不是只留在会话里。后续 Agent 能读取已确认、已排除和待验证内容，减少重新发散。

### 5. 在高风险处保持人类裁决

用户提供业务现场和视觉判断；主线程处理跨模块设计、审查争议和最终验收；小模型或子任务承担边界明确的实现与核对。这里的价值不是“人退出”，而是人只保留无法安全外包的判断。

## 如何迁移给公司内的小模型或 CLI Agent

| Codex 中观察到的条件 | 可迁移做法 | 小模型需要的额外脚手架 |
|---|---|---|
| 能读取整个工作区 | 将源码、依赖定义、项目文档和内部规范放入统一可检索目录 | 预先生成文件地图和允许读取的路径清单 |
| 能在多种来源间路由 | 为平台、代码、版本、运行、历史问题规定首选来源 | 固定来源顺序、资料卡字段和“找不到时”的降级路线 |
| 能运行项目工具 | 暴露编译、lint、测试、启动服务、浏览器和截图命令 | 用脚本包装命令，输出结构化通过/失败及日志位置 |
| 能根据失败继续调查 | 保存原始错误、发生层、版本、预期不变量 | 提供“错误 → 查询卡”模板，禁止无证据连续改写 |
| 能管理实验分支 | 使用小提交、分支和 worktree | 固定创建、验证、回退和合并流程；不让 Agent 自行做破坏性 Git 操作 |
| 能跨会话恢复 | 将结论写回 Markdown、测试和项目规则 | 强制任务结束生成 Confirmed / Rejected / Unverified 与下一步 brief |
| 能审查 Skill | 让更强模型定期检查流程是否过时、冲突或束缚探索 | 小模型继续执行明确清单；Skill 变更需人或强模型审核 |

适合演讲的简短表达：

> 真正值得学习的不是 Codex 的品牌，而是它把“项目上下文、工具、现实反馈、隔离实验和长期记忆”连成了一个环境。小模型不够聪明，就把这个环境做得更明确。

## 演说边界

- 上述材料只能支持“这些项目中观察到了这些行为”，不能支持对所有项目、模型或团队效率的普遍结论。
- 无法从项目记录推出 Codex、Claude 或其他模型内部究竟如何搜索和推理。
- Commit Message、复盘和 Git 时间线都是外部轨迹，不是完整的隐藏思维记录。
- 编译、测试和截图是证据来源，不是永远正确的裁判；测试目标、截图范围和审查工具本身也需要检查。
- worktree 提供隔离，不替代设计、测试、代码审查或合并冲突处理。
- 公司内资料、真实业务数据和 Key 仍需遵守权限、脱敏、日志与发布规则。
