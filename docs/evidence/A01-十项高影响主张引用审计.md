# A01：十项高影响主张引用审计

审计日期：2026-09-05。

本文件用 [证据综合与引用审计](../22-证据综合与引用审计.md) 的四档协议，抽查 `docs/sources/claim-ledger.md` 中十条会影响演讲主线或听众行动的主张。

## 审计摘要

| 结果 | 数量 | 含义 |
|---|---:|---|
| FULL | 7 | 来源支持主张，且边界在账本中可见 |
| PARTIAL | 3 | 一部分是本项目的方法推断或表述超过来源，需要修订/降级 |
| CONFLICT | 0 | 本轮未发现直接相反的一手来源 |
| NONE | 0 | 未发现完全无支持的抽查主张 |

这不是“仓库引用准确率为 70%”：样本是人为挑选的高影响主张，不是随机样本；FULL 也不代表来源本身无偏或结论已经工程验证。

## 逐项审计

### C01：Deep Research 的流程

- 原主张：深度研究先明确目标和来源，再规划、多步搜索、综合并检查引用。
- 来源：OpenAI Help Center《Deep research in ChatGPT》。
- 判定：`PARTIAL`。
- 支持部分：用户描述目标、选择来源、查看并修改计划、跟踪过程，最后获得带引用/来源链接的结构化报告。
- 不支持部分：文档说明引用供用户验证，没有说系统自身完成了引用正确性检查。
- 修订：将“并检查引用”改为“并提供引用供用户检查”。

### C02：多 Agent 研究的适用场景与代价

- 来源：Anthropic《How we built our multi-agent research system》。
- 判定：`FULL`。
- 依据：文章直接描述 lead agent 规划、subagent 搜索、CitationAgent 定位引用、广度优先任务更适合、多 Agent token 消耗高，以及共享上下文/依赖多的任务不适合。
- 边界：账本已经标为厂商内部复盘，不迁移内部性能数字。

### C13：WPS 加载项技术模型

- 来源：WPS 开放平台《加载项概述》。
- 判定：`FULL`。
- 依据：官方页面明确称加载项基于 Web 技术，每个加载项对应网页，并通过网页中的 JavaScript 与 WPS 应用交互。
- 边界：页面是整体架构说明，不能支持某个具体 Word/PPT API 在目标版本可用。

### C15：公开仓库与许可证

- 来源：GitHub Docs《Licensing a repository》。
- 判定：`FULL`，但必须保留平台例外。
- 依据：GitHub 文档称无许可证时默认版权法适用，作者保留源码权利；同时 Terms of Service 允许 GitHub 用户查看和 fork 公开仓库。
- 推荐表述：公开可见与可 fork 不等于获得复制、分发和制作衍生作品的一般许可。
- 边界：不是具体项目法律意见。

### C28：Deck.gl 失败驱动证据链

- 来源：Deck.gl 本地复盘、四个实验、结构测试，以及 [D01](D01-Deckgl失败现象与问题重写.md)、[D02](D02-Deckgl从文档到源码与实验.md)、[D03](D03-Deckgl候选路线与决策比较.md)。
- 判定：`PARTIAL`。
- 支持部分：确实存在模型假设、官方文档、目标版本源码、同仓库范式和运行实验的记录；本轮结构测试 9/9 通过。
- 未充分支持：无法由一个案例证明该顺序普遍导致 Agent 收敛，也无法独立重建初版失败的全部历史。
- 处理：保留“在本案例中帮助问题收敛”的个案表述，禁止写成普遍提效规律。

### C29：负知识和任务 brief 作为调研记忆

- 来源：Dice 本地复盘与 OpenAI Harness Engineering。
- 判定：`PARTIAL`。
- 支持部分：本地文档确实显式保存已确认、已排除和待验证事项；OpenAI 复盘支持把仓库内知识作为 Agent 可读系统记录。
- 未充分支持：没有有/无 LEARNINGS 的对照，不能证明减少多少重复搜索、时间或 token。
- 处理：把“减少重复劳动”写为预期作用，把“比完整聊天更明确”限定为结构可检查性判断。

### C34：三遍阅读与分层成本

- 来源：S. Keshav《How to Read a Paper》。
- 判定：`FULL（方法来源）`。
- 依据：原文提出逐遍增加阅读深度，并允许在每遍后决定是否停止。
- 边界：将论文三遍法迁移到网页、源码、视频和 AI token 分配，是本项目的类比，不是 Keshav 原文验证。

### C39：Information Foraging 与 Sensemaking 双循环

- 来源：Pirolli & Card 2005。
- 判定：`FULL（理论结构）`。
- 依据：论文直接描述围绕信息寻找与围绕意义建构的两组活动以及大量交互，并给出从外部数据到 evidence file、schema、hypothesis 和 presentation 的转换。
- 边界：原研究面向情报分析；用于 AI 技术调研是方法迁移。

### C40：源码理解的问题层级与多证据组合

- 来源：Ko、Sillito、LaToza、Wyrich 的程序理解研究。
- 判定：`FULL（人类程序理解）`。
- 依据：Sillito 的四类问题支持从焦点到跨子图的层级；Ko 和 LaToza 支持源码、debugger、历史、运行和同事知识共同参与回答行为与设计问题。
- 边界：这些研究不证明 AI 已经具有人类式理解；将问题树用于 Agent 是工程设计。

### C41：引用存在、支持和覆盖是不同维度

- 来源：ALCE、AIS 与后续 Deep Research 审计研究。
- 判定：`FULL`。
- 依据：ALCE 明确把 citation precision/recall 与流畅度、答案正确性分开；AIS 独立定义内容对已识别来源的可归因性。
- 边界：Deep Research 新研究中的产品分数不进入本主张。

## 本轮实际修订

### 1. 修订 C01

```diff
- 规划、多步搜索、综合并检查引用
+ 规划、多步搜索、综合，并提供引用供用户检查
```

这是一个典型 `PARTIAL`：来源确实谈到了引用，但原句把“用户可以验证”升级成了“系统完成检查”。

### 2. 降低 D01 的因果语气

演讲统一使用：

> 在 Deck.gl 这个案例中，证据升级让问题从反复生成转为可验证的工程子问题。

不使用：

> 这套流程已经证明可以普遍提升所有 Agent 的问题解决效率。

### 3. 明确视频切片不可纳入“完整证据链”统计

V01 保留为流程结构案例，但原始音频/逐字转写缺失，涉及数量、费用、准确率与引语时必须标为本地记录或回到作者文章。

## 对演讲最有价值的现场例子

用 C01 做 60 秒审计演示：

1. 展示一条听起来合理的主张；
2. 打开官方来源中“report with citations so you can verify”的位置；
3. 指出“供用户验证”不等于“系统已验证”；
4. 当场把一句话降低到证据真正支持的强度。

这比只提醒“AI 会幻觉”更可操作：听众能看到如何修，而不是只获得恐惧。
