# 《用 AI 完成技术参考搜索、筛选与结构化整理》逐页演讲稿

> 副标题：把“找巨人肩膀”这件事自动化
>
> 课程介绍：用 AI 自动分析源码、提取视频干货，输出结构化技术文档
>
> 能力淬炼：提升技术信息筛选、梳理、转化为可用开发资源的实操能力

## 使用说明

这是根据讲者逐页试讲录音重写的全量母稿，共 31 页。页数来自内容，不是目标。它还不是最终 45 分钟删减版，也不是 HTML 视觉稿。

标记说明：

- **页面任务**：这一页如果删除，会损失什么。
- **画面建议**：后续制作 HTML 时应寻找或制作的视觉材料。
- **页面文字**：真正显示在屏幕上的少量文字。
- **口播**：讲者可以直接说，也可以继续改成自己的语气。
- **证据边界**：提醒哪些话不能讲过头，不一定显示在屏幕上。

## 第一幕：先承认一件事——AI 也没有那么省心

### 01｜AI 过上了打工人梦想中的生活

**页面任务**

用原文笑话开场，让全场迅速建立共同经验，不先讲术语。

**画面建议**

一张社交媒体帖子样式卡片。保留原文，配简单纯色头像和点赞、评论图标，不加解释性小字。

**页面文字**

> ai 过过上了打工人梦想的生活，上级必须指令明确，工作出错了领导全权负责，钱到位再上班，少一分晚一秒都罢工。
>
> 并且还会摸鱼偷懒，而且你骂他也得花钱

**口播**

这其实是我对打工人的一种美好祝愿：希望有一天，我们也能像 AI 一样，指令不明确就先问清楚，资源不到位就不背锅。

但这个笑话也说中了我做这些项目时最深的感受。我们常说“让 AI 帮我查一下”，好像把一句话扔进去，答案就会自己长出来。真正做项目时不是这样。AI 当然知道很多公共知识，可是它不知道我们公司以前踩过什么坑，不知道这个需求为什么和网上的普通案例不一样，也不知道半年后还要接什么功能。

所以我今天不准备讲一个万能 Prompt。我想直接从几个真实项目开始：我做了什么，AI 在哪里帮到了我，它具体去了哪里找，哪里又必须由人来判断。

### 02｜我说的“调研”，不是搜出十个链接

**页面任务**

给整场演讲一个朴素定义，并自然过渡到 WPS。

**画面建议**

中间是一条短链：`遇到问题 → 找候选 → 看原始证据 → 做小实验 → 留在项目里`。背景用后续几个项目的淡化缩略图，而不是工具 Logo 墙。

**页面文字**

```text
找得到 ≠ 找得对 ≠ 能用 ≠ 下次还能复用
```

**口播**

我这里讲的技术调研，不是搜索引擎返回十个链接，也不是 AI 帮我写一篇看起来很完整的综述。

对我来说，调研至少要走到五步：先把问题说清楚；再扩大候选；进入文档、源码、Issue 或真实页面拿证据；做一个足以淘汰错误方案的小实验；最后把结论、失败和边界留在项目里。

这套事情并不只属于程序员。产品经理给出的业务条件，会直接决定我们搜什么、筛掉什么；设计和实际用户看到的现象，也可能推翻代码层面看起来很合理的判断。

我先从一个最贴近“不要重复造轮子”的项目讲起：一个 WPS AI 插件。

## 第二幕：WPS——找巨人的肩膀，不等于找到一个巨人

### 03｜我想做一个 WPS AI 插件，但没有现成答案

**页面任务**

交代项目目标、时代背景和真实困难。

**画面建议**

展示 WPS 插件最终界面截图；旁边只放三个目标词：Word、Excel、PPT。可再放一张项目早期截图，体现这是较早的实践。

**页面文字**

- 在 WPS 的 Word、Excel、PPT 中提供 AI Agent
- AI 不只回答问题，还要实际操作文档对象
- 资料分散，目标环境行为并不完全等同于 Microsoft Office

**口播**

这个项目是我几个月前做的。当时我还没有使用现在这套 Codex 工作方式，模型能力、搜索能力和整个流程都没有今天成熟，所以最后的视觉和工程过程不一定是最好的。

目标听起来很自然：在 WPS 的 Word、Excel、PPT 里做一个 AI Agent，让它不仅能聊天，还能改文字、表格和幻灯片。

问题是，网上当然有 Office 插件，有文档生成库，也有各种 AI Agent 项目，但没有哪个项目可以直接搬过来变成我的答案。WPS 的资料没有我希望的那么完整；Microsoft Word 的资料更全，可它们的对象和方法虽然看起来相似，实际行为又不总是一致。

这时“不要重复造轮子”不能理解成“找到一个仓库，复制下来”。

### 04｜候选池不是 AI 凭空生成的

**页面任务**

说明人和 AI 如何共同扩大搜索空间。

**画面建议**

左侧“我提供的线索”，包括 PageAgent；右侧“AI 继续发现的项目”；中间汇总成候选池。不要把所有仓库 Logo 平铺成清单。

**页面文字**

```text
人的先验线索 + AI 的扩展检索 = 候选池
```

**口播**

候选并不是 AI 凭空搜出来的。我先把自己知道的线索告诉它。比如阿里开源的 PageAgent，我之前听说过，觉得其中某些 Agent 状态组织方式可能有用。AI 再围绕这些线索继续找 PPTAgent、PptxGenJS、Slidev、Marp、python-pptx，以及其他文档和设计相关项目。

项目最后研究了 11 个候选。这里有一个很重要的点：我们不是让 AI 替人忘掉已有经验，而是把人的起点交给它，让它沿这个起点扩展到我们没有时间逐个看的范围。

反过来也一样。公司内部以前做过什么、哪个依赖踩过坑、什么方案因为合规不能用，这些 AI 在互联网上查不到。你不告诉它，它就会把已经走过的弯路再走一遍。

### 05｜没有一个库是答案，但每个库都可能贡献一部分

**页面任务**

展示 WPS 案例最核心的选择方式：从仓库提取可借资产，而不是评“最好项目”。

**画面建议**

画一张“这里借一点，那里借一点”的拼装图。四个来源块分别流向内容结构、设计令牌、布局/QA、状态组织，最终汇入 WPS 插件。

**页面文字**

| 来源 | 真正借走的东西 |
|---|---|
| PPTAgent | 内容 Schema、多步工作流 |
| HTML/PPT 项目 | Design Tokens |
| Mck 类项目 | 布局坐标、字符预算、QA |
| PageAgent | 状态组织思路 |

**口播**

调研到最后，11 个项目里没有一个能直接回答“WPS 插件该怎么写”。但这并不等于这次搜索失败了。

PPTAgent 贡献的是内容 Schema 和多步工作流；一些 HTML PPT 项目贡献的是 Design Tokens；另一些项目贡献布局坐标、字符预算和质量检查；PageAgent 给了状态重组方面的启发。openpyxl、XlsxWriter、python-docx 也不是 WPS 的运行时代码，但它们的对象模型和工具语义可以帮助我们思考 Agent 应该暴露什么能力。

所以我后来更喜欢这样理解“站在巨人的肩膀上”：不是先找到一个巨人，而是先把问题拆开，再从很多成熟项目里分别借走已经验证过的认知。

### 06｜相邻生态是线索，不是事实

**页面任务**

用一次真实失败说明文档、相似 API 与实际运行的证据等级不同。

**画面建议**

左侧 Word/WPS 相似对象图，右侧失败与修正：`InsertAfter('\r' + text)` → `InsertParagraphAfter()`。代码只显示必要两行。

**页面文字**

```text
相似名称 → 生成假设
目标环境运行 → 决定事实
```

**口播**

WPS 这一段最容易犯的错误，是把 Microsoft Office 的完整文档直接当成 WPS 的事实。

例如插入 Word 段落。按照相邻生态的经验，给 Range 追加一个回车和文本，看起来应该会产生新段落。代码也没有显得特别离谱。但是在目标环境里，新内容没有成为段落集合能识别的新段落，Agent 于是反复调用，越改越乱。最后实际可行的方式，是明确插入新段落，再设置文本。

这件事不说明相邻文档没用。恰恰相反，它很适合快速生成候选方案；只是它不能越级成为目标环境已经验证的事实。

### 07｜WPS 留下的不是“AI 写了个插件”

**页面任务**

收束第一个案例，并引出结构化归档。

**画面建议**

三层漏斗：11 个候选 → 3 类可行路线 → 项目自己的实现与学习文档。右下角放最终插件截图。

**页面文字**

1. 候选项目池
2. 可借资产与排除理由
3. 失败实验与目标环境结论

**口播**

如果只看最终代码，这个案例很容易被说成“AI 帮我写了一个插件”。但真正值钱的是中间留下的结构：11 个候选为什么被比较；哪些项目只借思路，哪些方案因运行环境或可编辑性被排除；哪个看似合理的 Office 经验在 WPS 中失败。

这些内容以后不一定都要塞进一个 Prompt。可以放在项目说明、学习文档或专属 Skill 里，让下一次进入项目的 Agent 少走一遍弯路。

这也回答了一个常见问题：AI 调研的产物不应该只是一篇总结。它可以是候选矩阵、失败记录、接口设计，甚至直接进入代码和测试。

接下来我讲一个更像传统“搜索资料”的案例，而且对象大家应该很熟悉：B747。

## 第三幕：B747——从一张低清图追到可用的专业资料

### 08｜真正的起点，是一份我带不回家的 Excel

**页面任务**

让非技术听众理解为什么公开资料检索是实际业务问题，而不是搜索技巧表演。

**画面建议**

左边是模糊化的手机/Excel 示意，右边是顺丰公开 B747 舱位图。中间写“信息很多，但无法直接统计”。

**页面文字**

- 内部 Excel 不能上传外网
- 字段杂、部分信息藏在低清图片里
- 回家后只能通过手机零散查看

**口播**

这个需求是做一个 3D 配载相关页面。产品给过一份 Excel，但一方面它不能传到外网，我回家之后拿不到；另一方面，里面的信息很杂，有些列直接塞图片，图片分辨率也不高。

我在公司试过让可用的小模型识图，效果并不稳定。回家以后只剩手机上的零散信息，要靠人手把每个舱位的名字、位置、大小和形状统计出来，非常痛苦。

所以我换了一个问题：这些资料有没有公开版本？我把公开页面和那张舱位分布图交给 AI，让它不要猜模型，而是沿着图上的文字去找。

### 09｜AI 不是一次搜到答案，而是逐轮学会行业语言

**页面任务**

展示可复刻的 B747 检索链，但不展开全部航空细节。

**画面建议**

一条四步时间线，每一步配真实页面局部截图：顺丰舱位图 → 位置代码 → contour code → 公开设备说明。

**页面文字**

```text
顺丰舱位图
→ "B747-400F" "LR" "LL" "PL"
→ PA1 / PMD / H4M / HPL / PEB
→ Position → Contour → Geometry
```

**口播**

第一步，AI 找到顺丰官网公开的 B747 舱位图。那张图本身没有给出所有几何尺寸，但有 A1、A2、LR、LL、PL、11P 这类陌生代码。

第二步，它没有继续只搜“747 货舱尺寸”，而是把机型和几个低频代码放在一起。普通关键词会带来新闻、模型玩具和整机参数；低频词共现会把搜索空间压到货舱 position 和装载 configuration。

第三步，新资料又暴露出 PA1、PMD、H4M、HPL、PEB 这些 contour code。它们成为下一轮搜索词，最后定位到其他航空公司的公开设备说明和装载资料。

这条链最值得学的不是某个 Google 操作符，而是：不要一开始就期待自己知道正确问题。先从可信材料里抄出行业语言，再让每一轮结果生成下一轮查询。

### 10｜找到资料还不够，要把它变成产品能用的结构

**页面任务**

展示搜索结果如何进入配置和 3D 页面，同时明确业务边界。

**画面建议**

左侧公开货舱轮廓/尺寸页面，中央是一小段结构化配置，右侧是项目页面与点击进入 3D 仓位的截图。

**页面文字**

```text
舱位 → 轮廓类型 → 尺寸/形状 → 置信度 → 待确认项
```

**口播**

最后找到的资料不再只是“747 的货舱有多大”，而是某个位置对应什么轮廓类型、轮廓大致是什么形状、有哪些公开尺寸。

AI 把这些资料整理成配置，页面就能显示飞机内部的多个舱位。不同舱位不是同一个方盒子：有的接近矩形，有的像屋顶一样收口，有的在主货舱，有的在下货舱。点击二维位置，还可以进入 3D 视图查看对应的模型。

但这里一定要讲边界。顺丰图确认的是顺丰公开的舱位布局；其他航空公司的资料帮助我们理解 contour 和尺寸体系。这个组合足够支持原型、建模和预判，不等于取得了顺丰正式承运批准。最终业务仍要服从内部 W&B 或 Cargo Loading Manual。

没有 AI，我也可以沿这条链搜索，只是很难在有限时间里想到这些陌生术语，并把不同来源整理成能进入页面的配置。AI 真正放大的，是探索和整理的宽度。

## 第四幕：三个独立故事——筛选、纠错与验证

### 11｜“我要一个像 Excel 的表格”并不是一个完整需求

**页面任务**

进入 Web Excel 案例，强调产品与技术共同提供筛选标准。

**画面建议**

一个模糊气泡“像 Excel”，展开成六个条件卡片。

**页面文字**

- Vue 3 能集成
- 核心功能不依赖付费版
- 排序、筛选、列设置、行列移动
- 合并与取消合并
- 大数据与虚拟滚动单列评估
- 简单 HTML + 国内可访问 CDN

**口播**

另一个项目需要在网页里做非常复杂的 Excel 类交互：排序、筛选、调整列顺序、移动行、合并单元格、突出显示。普通表格组件很容易在某个环节卡住。

如果只问 AI“推荐一个像 Excel 的库”，它一定能给出一个排行榜，但那个排行榜对项目没有意义。是偏业务记录表格，还是偏真正的电子表格？核心功能能不能免费用？我们项目是 Vue 3，不要给我一套 React 才方便集成的答案。演示还希望不经过 npm 构建，直接打开 HTML。

这些不是 AI 应该替我决定的价值判断。产品目标、技术栈和商业边界必须先由人提供。AI 可以帮助把模糊描述展开成可筛选的字段。

### 12｜人不必逐个研究 14 个库，但必须定义淘汰条件

**页面任务**

展示 AI 如何扩大候选，人如何控制判断口径。

**画面建议**

14 个候选经过三道筛网，落到六个实验；只显示类别或少数代表名，不铺满 Logo。

**页面文字**

| 先问什么 | 去哪里确认 |
|---|---|
| 还维护吗 | GitHub 仓库与版本记录 |
| 免费边界 | 许可证与官方功能对照 |
| 合并到底是哪种合并 | 对应版本 API 与真实状态 |
| Vue 3/CDN 能否工作 | 固定版本产物与浏览器 |

**口播**

AI 最终调查了 14 个方案。人不必一页页看完所有文档，但必须规定什么叫“留下”。

比如“支持合并”这四个字就很危险。它可能指固定区域合并，可能指纵向 row span，也可能真的是用户框选任意单元格后合并。如果产品要的是第三种，前两种不能因为宣传页写了 merge 就算通过。

同样，一个 GitHub 仓库还在更新，不代表免费版包含我们要的能力；一个库能嵌入 Vue 页面，也不等于它是原生 Vue 组件。

AI 帮我读得更多，但筛选条件仍来自我们的实际任务。

### 13｜六个同题 HTML，比六篇产品介绍更有用

**页面任务**

展示结构化比较如何变成可操作实验。

**画面建议**

展示 Web Excel 索引页大图和六个 Demo 缩略图；旁边放同一批数据、同一组操作的图标。

**页面文字**

```text
同一批数据 + 同一组任务 + 六个独立 HTML
```

**口播**

调研没有停在一个大表格里。AI 为六个候选分别生成了独立 HTML，用同一批订单数据和近似的顶部操作去比较排序、筛选、移动、合并和宽表表现。

这种方式对我很有用。很多依赖看文档时差不多，真正打开以后，交互模型完全不同。有些适合业务记录表，有些更像电子表格；有些自由合并很自然，有些合并只是固定区域能力。

最终结论不是“第一名是谁”，而是一个很直观的场景表：如果是业务记录表，优先看哪类；如果目标变成完整 Excel 工作区，应该把哪类方案单独立项。产品经理不必理解所有 API，也可以通过页面判断哪种交互更接近业务。

### 14｜CDN 返回 200，也可能拿错了东西

**页面任务**

保留用户关于公司网络、错误 CDN 路径和小模型常见遗漏的实践细节。

**画面建议**

三级门禁：`curl/HTTP`、`文件格式`、`真实浏览器`。配一个 200 但错误产物的红色案例卡。

**页面文字**

```text
地址存在 → 产物适合浏览器 → 公司网络可达 → 页面真的运行
```

**口播**

简单 HTML 加 CDN 很适合快速比较，但我也被它坑过很多次。AI 写完一个地址，页面没效果；再让它改，它可能继续猜另一个地址。

后来我会明确要求它先用 curl 或 HTTP 请求确认文件到底在不在。可这还不够：这个项目里有一个文件返回 200，名字也像 min.js，但内容只是一个 CommonJS 函数，不是浏览器可直接用的完整包。

而且公司的网络环境有额外一层。有些路径在公网存在，公司访问不了；另一些是路径本来就写错了。最后要走过“地址存在、产物格式正确、公司网络可达、浏览器实际加载”几道门。

这类检查不高深，却很适合交给 Agent 自动做。模型越小、任务越长，越不能假设它会主动补上这一步。

### 15｜ECharts 连改五六版，页面就是不变

**页面任务**

用公司口述案例说明生成代码与查证当前版本不是一回事。

**画面建议**

脱敏示意图：折线图两端标签缺失，旁边连续五个“应该可以”的配置气泡全部打叉。明确标注“示意，非公司截图”。

**页面文字**

> 需求：X 轴左右两端必须显示数据端点的标签

**口播**

这是一个公司项目，没有公开截图。产品要求一张折线图的 X 轴左右两端必须显示端点标签。项目不是 TypeScript，写错配置字段也不会有编译错误。

当时用的模型连续改了五六版，每次都说这次应该有效，页面却没有变化。我甚至让它用相同 ECharts 版本单独写一个 CDN HTML，还是没有真正解决。

更尴尬的是，另一个旧项目里相似效果明明能工作，但它使用的是 ECharts 4.9.0；当前项目是 6.0.0。AI 一直在网上示例、旧项目和自己的记忆之间来回猜，我也不知道应该用什么关键词搜索这个非常具体的显示要求。

### 16｜不要继续问“ECharts 一般怎么写”，去问当前项目

**页面任务**

给出 ECharts 故事的真实转折，同时纠正版本字段叙述。

**画面建议**

从“模型记忆/网上示例”箭头切换到本地 `node_modules` 类型定义；显示 `axisLabel.showMinLabel` 与 `showMaxLabel` 两行。

**页面文字**

```js
axisLabel: {
  showMinLabel: true,
  showMaxLabel: true
}
```

**口播**

最后不是 AI 突然灵感爆发，而是我让它停止猜，直接去看当前项目 `node_modules` 里安装版本的类型和定义。

它很快定位到 `axisLabel.showMinLabel` 和 `showMaxLabel` 这组与两端标签有关的配置，再回到真实页面验证，问题才结束。

这里我也需要纠正自己最初的记忆：Apache ECharts 官方 FAQ 说明，这两个字段从 3.5.2 就已经支持，所以不能简单讲成“4.9 没有、6.0 才有”。真正的教训不是背字段，而是当页面反复否定方案时，检索对象应该从“网上一般怎么写”切换为“当前项目安装的这个版本、这个轴类型和这组配置到底如何工作”。

本地源码、类型定义和运行中的页面，本身也是技术资料，而且往往比模型记忆更接近你正在解决的问题。

**证据边界**

官方依据：[Apache ECharts FAQ](https://echarts.apache.org/en/faq.html)。公司项目经过为讲者口述，页面视觉只能制作脱敏示意，不能伪造公司代码截图。

### 17｜Deck.gl：页面能打开，不代表目标行为发生了

**页面任务**

进入后置的技术深案例，先讲失败现象而不是 API。

**画面建议**

展示早期 HTML 与目标效果的并排图，中央写“能打开 / 没报错 / 仍然不对”。

**页面文字**

- 图标要持续旋转
- 仍然可以 picking
- 不要每帧重建无关图层
- CPU 开销可控

**口播**

Deck.gl 这个需求表面上更小：让地图上的台风图标持续旋转。

我早期用 Claude 连接 DeepSeek 试着生成过多个 HTML。页面可以打开，代码也像那么回事，但就是达不到我想要的效果。后来换到 Codex 中较强的模型，它没有只给一个答案，而是做了四条独立路线，并且把性能、picking 和不重建其他图层都列进验收条件。

这不是一个严谨的模型横向评测。工具、网络、上下文和我给出的要求都不同。但它很适合展示一件事：更强的 Agent 不只是多写代码，它会主动把“能打开”改写成一组可以被验证的目标。

### 18｜当文档还不够，继续看目标版本的源码

**页面任务**

展示 Deck.gl 从官方文档到同版本源码的证据阶梯。

**画面建议**

四层阶梯：需求 → 官方 API → 9.1.12 源码 → 真实浏览器。右侧展示官方 `getAngle` 文档和 shader 中度转弧度的一小段源码。

**页面文字**

```text
IconLayer: getAngle
单位：degrees
源码内部：angle * PI / 180
```

**口播**

这个案例最漂亮的地方，是它能展示 AI 到底怎么查。

第一轮先从代码提出两个竞争假设：独立 `IconLayer` 应该使用 `getAngle`，而不是上层 `GeoJsonLayer` 的 `getIconAngle`；角度单位应该传 degree，而不是调用端先转成 radian。

接着去官方 IconLayer 文档确认属性和单位，再去 9.1.12 对应源码看着色器。源码明确在 GPU 内部执行 `angle * PI / 180`，所以调用端再转一次，视觉上就只转了很小的角度。

另一条 GPU 路线第一次还遇到 shader linking error。AI 又继续读相同版本 extension 的源码，找到 9.x 的 shader module 写法，再回到页面复验。

文档回答公开契约，源码回答这个版本到底做了什么，运行错误则告诉我们下一轮该查得更具体。

### 19｜四个方案里，最好看的不一定最适合项目

**页面任务**

讲清为什么需要多路线实验，以及人类观察如何改变选择。

**画面建议**

四张 HTML 缩略图，但只高亮路线 01。旁边放一条人工观察便签：“切回页面后快速补转”。

**页面文字**

| 路线 | 主要取舍 |
|---|---|
| CompositeLayer 内部更新 | 与现有架构贴合，改动小 |
| 低频目标值 + transition | 提交少，暂停/补间要谨慎 |
| GPU uniform | 扩展性强，版本耦合更深 |
| 度/弧度对照 | 用来证明根因，不是生产方案 |

**口播**

我很喜欢先生成几个小 HTML，再让人实际试。四条路线不是为了炫技，而是把不同代价做成可以观察的东西。

其中有一条看起来转得很好，但当浏览器标签或屏幕一段时间不活跃，再切回来时，图标会很快地转一阵，像是在补回错过的旋转。这个现象是我作为使用者观察到的。代码可能认为时间是连续的，但产品体验并不接受这种“追赶”。

最终更适合当前项目的是 CompositeLayer 内部更新路线：不是因为它在所有指标上第一，而是现有 TyphoonLayer 本来就是 CompositeLayer，改动面最小。只有实例规模上升到另一数量级，GPU 路线的复杂度才更可能值得。

AI 能扩大选择、整理取舍；哪一种体验算正确，仍然需要人给答案。

### 20｜单张截图不能证明“它在旋转”

**页面任务**

用 Deck.gl 集中讲一次多通道验证闭环，避免后文重复。

**画面建议**

一个环形闭环：结构测试 → 浏览器运行 → 像素变化 → picking → 静态层计数 → 人工暂停/单步。中心写“同一主张，多种证据”。

**页面文字**

```text
编译 / lint / 测试 / Console / 状态断言 / 截图
各自只能证明一部分
```

**口播**

图标旋转有个很直观的问题：一张截图只能证明页面某一刻长什么样，不能证明它持续在转。

所以这次实验组合了几种信号：结构测试确认关键配置存在；浏览器运行捕获 shader 错误；连续像素签名证明目标区域发生变化；自动 picking 证明那里确实是可拾取的 Deck.gl 对象；静态图层初始化计数证明动画没有反复初始化无关图层；页面还提供暂停和单步，让人可以直接比较前后朝向。

即使这样，人也不能完全退出。有些视觉能力较弱的模型，明明页面没有转，也可能看着两张图说“已经转了”。截图很有用，但证据必须与主张匹配。

这套闭环会花 token，也会花时间。不过编译错误、运行时 Console、测试断言和视觉问题发现的是不同错误。大的变更之后，让 Agent 自己跑一遍，比等人用鼠标把所有路径重新点一遍更稳定。

## 第五幕：Codex 为什么看起来突然变强了

### 21｜同一个大话骰，能玩和好看是两回事

**页面任务**

用所有人都能看懂的前后对比展示视觉反馈价值。

**画面建议**

大话骰早期与当前版本大幅并排。若早期截图不存在，另用历史 commit 创建临时 worktree 后截图，不改主分支。

**页面文字**

```text
能运行 → 看见问题 → 引入资产 → 动画与布局回归
```

**口播**

这个大话骰项目的早期版本是用另一套 CLI Agent 做的。游戏能玩，但画面很暗，人物接近占位几何，界面更像调试面板。如果 Agent 看不到最终画面，它很难知道自己做得难看。

### 22｜AI 甚至能从公开资料走到 Blender 工程

**页面任务**

展示调研可以直接转化为可编辑资产，而不只是 HTML 和文字。

**画面建议**

顺丰/波音公开资料 → 参数化 Blender 脚本 → 747 `.blend`/GLB → 浏览器页面；配一张 747 Blender 渲染和一张货运场景图。

**页面文字**

```text
公开资料 → 参数 → 脚本 → GLB / .blend → 浏览器验证
```

**口播**

另一个项目更夸张一些：我希望做顺丰航空货机和货运动画。Codex 去顺丰官网核对实际机型、运力和品牌素材，去波音资料核对尺寸；再调用本机 Blender 的 Python 接口，参数化生成四款飞机，导出 GLB，同时保留可编辑的 `.blend` 工程。

### 23｜完全陌生的平台，也可以先让 AI 找到入口

**页面任务**

用 Tabloom 简短展示官方文档、原型和插件实现的连接，不展开 Chrome API 清单。

**画面建议**

Tabloom 扩展截图；旁边是 Chrome 官方文档、原型 HTML、真实扩展三张小卡。

**页面文字**

```text
先做可讨论的原型，再进入平台约束
```

**口播**

Tabloom 是一个 Chrome 标签分组侧边栏扩展。开始时我并不知道浏览器插件具体怎么写，AI 可以先把产品交互做成容易讨论的页面，再去查 Chrome 官方文档，把确认过的交互放进真实扩展。

这个项目留下了从可行性、原型、设计、实现、错误、真实模型实验到发布审计的一串文档。它提醒我：调研不是开发前的一次阶段，反馈会不断产生新的信息缺口。遇到 Service Worker、空分组或真实模型输出的问题，搜索对象也会跟着改变。

网页原型不能证明插件 API 已经可用，官方文档也不能证明这个产品设计对用户有价值。不同资料分别回答不同问题。

### 24｜“不要教 GPT-6 做事”可以当段子，不能当工作计划

**页面任务**

先承认强模型正在减少流程教学，再转入公司现实和能力迁移。

**画面建议**

一句大字：“你学得越慢，越可能不用学。”下方翻转出：“但今天的需求还得做。”

**页面文字**

```text
你学得越慢，越可能不用学。
但今天的需求还得做。
```

**口播**

现在网上甚至有一种说法：不要再教 GPT-6 怎么做事了，反过来让它审查你写的所有 Skill。这个说法可以当段子，因为模型确实越来越强，几个月以后，我们很可能直接获得今天还要自己搭出来的能力。

所以学得慢也不用太焦虑——也许你还没学会，这个技巧就过时了。

但我们今天还有需求要做。公司里不一定能使用同样的模型、网络和工具，也不可能把技术债放一年，等未来模型上线再处理。

我还尝试过把 B 站视频从搜索、下载、转写再总结，用它发现主流观点和新的关键词。这个入口有用，但视频更适合扩展候选，不适合自动升级成关键技术事实。真正值得迁移的，不是某个按钮或 Skill，而是 Codex 工作时表现出来的行动方式。

### 25｜第一件可迁移的东西：不要把项目记忆押在聊天记录里

**页面任务**

解释上下文窗口的实际用法和局限，引出长期文档。

**画面建议**

左边是会压缩、遗忘的聊天气泡；右边是项目内稳定文件：README、决策记录、失败日志、测试。

**页面文字**

```text
短任务：新上下文
长任务：上下文 + 本地长期记忆
```

**口播**

很多人把 Agent 的能力理解成“它记得前面说过的话”。我的实际用法没有那么浪漫。

小需求我常常直接开新上下文，不依赖历史。大项目可以接着上一次聊，但上下文终究有限，超过以后会被压缩。压缩保留了什么、遗漏了什么，不完全可控。你在三小时前随口说过的关键限制，可能已经不在它能可靠使用的范围里。

所以重要信息要落到本地：当前需求、架构边界、做过的选择、失败过的方案、验证命令和剩余风险。聊天记录帮助当前回合，项目文件服务下一次进入项目的 Agent。

### 26｜第二件可迁移的东西：给小模型一套能行动的工具

**页面任务**

把 Codex 的“强”拆成工具条件，而不是神秘模型能力。

**画面建议**

五个工具块围绕 Agent：文件/源码、终端、浏览器、网络资料、Git。每个块只给一个例子。

**页面文字**

- 读源码与依赖定义
- 运行构建、测试和 curl
- 操作浏览器、看 Console、截图
- 搜官方文档、Issue 和目标版本源码
- 查看 Git 历史与 diff

**口播**

Codex 看起来很强，一部分原因是它不只会聊天。它能读整个项目，运行命令，访问网页，控制浏览器，看 Console 和截图，还能查看 Git 历史。

在公司如果只能用小模型，也可以尽量把这些能力拆给它。没有内置浏览器，可以用 Playwright；没有漂亮的联网搜索，可以让它先用 curl、官方文档镜像、GitHub 源码或本地依赖。网络不通时，本地 `node_modules`、锁文件、类型定义和项目内文档仍然是一套资料库。

我还遇到过自己不知道如何用英文描述的问题。AI 可以把中文现象改写成库名、版本、错误层和关键不变量，再去 GitHub Issue 搜。别人已经遇到同样问题时，Issue 里的版本范围、绕过方案和维护者回复往往比普通博客更接近答案。

### 27｜第三件可迁移的东西：隔离实验，让现实来裁决

**页面任务**

集中解释 HTML、worktree、浏览器和多反馈通道在 Agent 工作方式中的角色。

**画面建议**

从主项目分出两个安全实验舱：独立 HTML 与 Git worktree；实验结果通过测试和截图回流。

**页面文字**

```text
最小 HTML：隔离依赖与 API 假设
worktree：隔离高风险改动
真实浏览器：隔离“代码看起来对”的错觉
```

**口播**

我在这些项目里反复看到三个很实用的动作。

第一，遇到库选型或 API 不确定性，先做独立 HTML。它能把框架、业务代码和缓存影响拿掉，让多个候选做同一道题。

第二，高风险改动放到 Git worktree。它给 Agent 一个独立目录和分支，主项目可以继续保持可用；方案失败时也不用在一堆混合修改里手工回滚。

第三，让现实反馈裁决。先跑编译、lint 和测试，再进浏览器看运行时错误和真实状态，最后看截图或实际操作。不是每次改一个像素都要跑全套，但大的变更应该走完整闭环。

这些动作没有 AI 也成立。有 AI 时，它们只是把反馈速度放大了。

## 第六幕：人真正需要提供的，是 AI 不知道的现场

### 28｜把过去、现在和未来一起告诉 AI

**页面任务**

明确人类不可外包的上下文，并覆盖产品经理与开发者。

**画面建议**

三栏时间轴：过去/现在/未来。每栏一个真实例子。

**页面文字**

| 过去 | 现在 | 未来 |
|---|---|---|
| 旧 Bug、兼容性、失败方案 | 完整需求、技术栈、不能做什么 | 下一机型、下一功能、扩展边界 |

**口播**

人和 AI 的分工，我最后把它归成过去、现在和未来。

过去，是这个项目发生过什么。某个浏览器、手机、操作系统或依赖组合以前出过什么问题；哪条路表面可行但已经失败。这些可能只存在于人的记忆、代码注释或一次提交里，公网模型不可能自动知道。

现在，是完整需求和现实边界。不要只说“做个表格”，要说 Vue 3、免费范围、公司网络、真实用户怎样操作。也可以把自己准备怎么实现告诉 AI，但要求它反过来审查：这个办法有什么盲点，有没有更符合当前库最佳实践的做法。

未来，是这个功能接下来会长成什么。比如今天只做 747，但以后还会接其他机型，就应该尽量把机型参数集中配置，把几何和业务规则拆开，避免把 747 常量散落在每个组件里。重点不是强行使用某种面向对象形式，而是给变化留下清晰边界。

这三类信息，是我们真正比通用模型多知道的东西。

### 29｜让项目本身成为下一位 Agent 的老师

**页面任务**

将长期文档、Skill、架构和 Commit Message 收束为一个项目维护观点。

**画面建议**

一个项目文件树，突出 `AGENTS.md/CLAUDE.md`、`docs/decisions`、`skills/`、测试、Git log；箭头指向下一次 Agent 会话。

**页面文字**

- 项目入口：做什么、怎么验证、哪些不能动
- 决策与失败：为什么这样选、什么已经试过
- 专属 Skill：重复发生且步骤稳定的工作
- Commit：定位变化，再打开 diff、Issue 与测试

**口播**

AI 时代写代码更快，项目维护反而更重要。

一个功能两三千行塞在同一个文件里，人很难读，AI 也很难只改正确的边界。比起迷信某一种架构，更实际的原则是：文件职责清楚、接口稳定、依赖方向能解释、验证入口容易找到。公司如果有自己的特殊组件写法，也要在项目里告诉 Agent 怎么用、哪些地方容易出错。

失败经历也应该留下。曾经出现过的 Bug、不能升级的原因、动这个模块会影响什么，可以进入项目文档或专属 Skill。

Commit Message 同样有用。当一个地方突然出问题，AI 可以通过 Git 找到它什么时候改过、当时为什么改，再打开 diff、相关测试和 Issue。提交说明是索引，不是事实终点；但索引写得好，半年后的排查会快很多。

真正的长期记忆，不是让模型永远记得，而是让项目保存足够好的线索。

### 30｜自己的脑子不烧 token，但判断仍然很贵

**页面任务**

用第二个原文段子唤回注意力，并给出人的最终责任。

**画面建议**

第二张社交媒体帖子样式卡片，原文不改。下方只放三个小词：业务风险、事实边界、最终验收。

**页面文字**

> 卧槽，惊奇发现，用自己的脑子写代码不烧 token ，是免费的！

**口播**

这句话我也不展开解释。

AI 可以替我们搜索更多候选、读更多源码、生成更多实验、跑更多检查。但什么资料可以进入公司，什么风险不能接受，哪个体验才算正确，最终仍然需要人负责。

有时手工点一下页面确实比让 Agent 写一整套自动化更快；有时一条测试能避免以后每个人重复手测。我们要判断的是哪种反馈值得沉淀，而不是把所有事情都自动化。

即使没有 AI，今天这些方法也成立：把问题拆清楚，优先找原始资料，用多个来源互相约束，做最小实验，把失败和决策写下来。AI 只是让这些动作可以在更大范围、更高频率发生。

### 31｜调研的终点，是下一次不用从零开始

**页面任务**

回收主题，以第三个原文段子结尾，并给听众一个可执行的最小闭环。

**画面建议**

先展示五步最小闭环，最后切换为第三张社交媒体帖子样式卡片。背景淡化 WPS、B747、Web Excel、Deck.gl 和项目文档画面。

**页面文字**

```text
定义问题
→ 扩大候选
→ 回到原始证据
→ 用现实反馈验证
→ 把结论留在项目里
```

随后显示原文：

> 今天学到一句翻译：
>
> 爱让记忆变得更加珍贵（ai让存储更贵）
>
> Al has made memory more expensive

**口播**

今天这些项目技术栈完全不同：WPS 插件、B747 货舱、复杂表格、ECharts、Deck.gl、浏览器插件、游戏和 Blender。

它们真正共用的是同一条链：人先提供项目现场和判断标准；AI 扩大搜索与实验空间；文档、源码、Issue、运行结果和截图分别承担不同证据；最后把有用结论变成配置、代码、测试、资产或项目记忆。

所以“让 AI 替我调研”不是把判断权交出去，而是把机械搜索、候选扩展、初步整理和重复验证交给它，让人把精力放在 AI 不知道的现场，以及资料最终能不能进入真实业务。

如果大家回去只做一件事，我建议不要先收集一百个 Prompt。挑一个今天正在做的需求，把“为什么这样做、查过哪里、什么失败过、怎样证明成功”留在项目里。下一次不管来的是同事、自己，还是另一个 Agent，都不用重新从零开始。

最后用这句话结束。
