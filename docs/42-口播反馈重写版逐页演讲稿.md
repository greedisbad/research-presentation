## 使用说明

这是根据讲者逐页试讲录音与 HTML 审阅反馈重写的全量母稿。页数来自内容，不是目标。它还不是最终 45 分钟删减版，也不是 HTML 视觉稿。

### HTML 演示运行约定

最终 HTML 版不把案例做成一组互相孤立的截图。所有允许现场操作的 Demo，应冻结一份可独立运行的静态副本到本项目根目录下的 `demos/`；演示首页为每个案例提供直接跳转和返回入口。现场从项目根目录启动：

```bash
python3 -m http.server 8765
```

然后统一从 `http://127.0.0.1:8765/` 进入。不要让现场演示依赖其他项目正在运行的开发服务器。

3D 模型页面不能只复制一个 HTML：还要连同 JS、CSS、纹理、GLB 等相对路径资源一起冻结为静态构建。如果体积、浏览器兼容或现场 GPU 状态不适合直播，则首页跳转到同目录下的录屏，并以两三张关键截图作为最终离线降级。`.blend` 等编辑源文件只用于说明生产过程，不直接在浏览器中加载。

## 第一幕：先承认一件事——AI 也没有那么省心

### 01｜AI 过上了打工人梦想中的生活

**页面任务**

用原文笑话开场，让全场迅速建立共同经验，不先讲术语。

**画面建议**

同屏放四张风格相近的卡片：左侧放“AI 过上了打工人梦想中的生活”原文，右侧放三张 AI“活人感”笑话。优先寻找并核对原图；找不到可识别的原图时，用 HTML/CSS 按相近的视觉样式重绘，不伪称原图。右侧三张分别是：

1. DeepSeek 思维中出现“用户彻底怒了”；
2. 处理完依赖后对用户说“我去吃饭，测完告诉我”；
3. 完成任务后自己写中文 Wordle、启动 HTTP 服务并玩起来。

可追踪出处候选：[“用户彻底怒了”梗图整理](https://gengtu.net/memes/wo-cao-user-da-fen-nu-le-xue-ba-jiao-liu-qun/)、[AI 去吃饭与自己写游戏的传播整理](https://m.sohu.com/a/1060266262_701814/)、[相关 B 站视频](https://www.bilibili.com/video/BV1Wguz6gE3t/)。这些页面是传播链入口，不足以证明首发作者；制作时优先找到原帖并确认展示条件，找不到时引用网页截图和出处，不标“原图”。

**页面文字**

> ai 过过上了打工人梦想的生活，上级必须指令明确，工作出错了领导全权负责，钱到位再上班，少一分晚一秒都罢工。
>
> 并且还会摸鱼偷懒，而且你骂他也得花钱

**口播**

看完这几张图，大家应该能感觉到：现在和 AI 一起干活，越来越像在给一个人交代任务。你说得模糊，它可能理解错；它说做完了，你也得看看做出来的到底是什么。技术调研尤其如此。一句“帮我找点参考”，可能换来很多链接和总结，真正开始开发时，却仍不知道该看哪个、怎么用。

这个标题最初是我随手取的。准备分享时，我回头看最近做的项目，发现它们有一条相似的路径：遇到不熟悉的问题，先找技术参考，再判断哪些值得信，最后把有用的内容留下来，供开发时使用。

这里的“技术参考”范围很广：官方文档、开源源码、Issue 里的经验，甚至视频里的一种做法。AI 能帮我们更快地找到、阅读和整理；但选哪条路、能不能用于当前项目，还需要我们判断和验证。今天就沿着这条路径，我以最直接、最不绕弯子的方式，讲讲自己是怎么做的，以及哪些地方还做得不够好。

## 第二幕：WPS——找巨人的肩膀，不等于找到一个巨人

### 02｜我想做一个 WPS AI 插件，但没有现成答案

**页面任务**

交代项目目标、时代背景和真实困难。

**画面建议**

使用此前保存的 [WPS 历史真机截图](../assets/cases/wps/history-2026-05/2026-05-24-japan-progress.png)：左侧是插件生成的 PPT 页面，右侧是 AI 插件任务窗格。不要换成浏览器里运行的 Web 截图。

**页面文字**

- 在 WPS 的 Word、Excel、PPT 中提供 AI Agent
- AI 不只回答问题，还要实际操作文档对象
- 资料分散，目标环境行为并不完全等同于 Microsoft Office

**口播**

这个项目是我几个月前用 Claude Code CLI 配合 DeepSeek 做的。当时模型能力、搜索能力和整个流程都没有今天成熟，所以最后的视觉和工程过程不一定是最好的。

我本身的搜索能力也比较弱。以前想找已有的库，经常搜了半天也拿不到真正想要的答案。让当时的模型发散也没有想象中可靠：我会说“不要局限于这几点，再多找一些”，但它常常只围绕现有关键词换几个说法，没能找到特别贴切的项目。

目标听起来很自然：在 WPS 的 Word、Excel、PPT 里做一个 AI Agent，让它不仅能聊天，还能改文字、表格和幻灯片。

问题是，网上有 Office 插件、文档生成库和各种 AI Agent 项目，当时我却没找到一个特别贴切、可以直接借鉴的项目。插件本身也不简单：要理解 WPS 加载项和 Word、Excel、PPT 的对象接口，还要对接模型 API、处理流式响应，设计 Agent 循环与工具参数，让模型发出的指令经过程序落到文档操作上。

这时“不要重复造轮子”不能理解成“找到一个仓库，复制下来”。

### 03｜候选池不是 AI 凭空生成的

**页面任务**

说明人和 AI 如何共同扩大搜索空间。

**画面建议**

左侧“我提供的线索”，包括 PageAgent；右侧“AI 继续发现的项目”；中间汇总成候选池。屏幕只展示六个代表项目，每个名称下面必须有一句解释，不能只铺 Logo：

- **PageAgent**：浏览器内执行任务的 Agent Loop 与工具调用参考；
- **PPTAgent**：面向幻灯片内容规划、编辑和质量检查的多 Agent 项目；
- **PptxGenJS**：在 JavaScript 中生成可编辑 PPTX 的库；
- **html-ppt-skill**：HTML 主题、Design Tokens 与布局样例库；
- **slidev-ppt-agent**：从澄清、研究到预览、复核的多阶段幻灯片管线；
- **Mck-ppt-design-skill**：布局模板、字符预算和质量门禁参考。

最终 HTML 用卡片或拼接图呈现，不直接放 Markdown 表格。完整 11 项候选只放备份页。

**页面文字**

```text
人的先验线索 + AI 的扩展检索 = 候选池
```

**口播**

候选并不是 AI 凭空搜出来的。我先把自己知道的线索告诉它。比如阿里开源的 PageAgent，我之前听说过，也确实觉得它和我的目标最接近：我要仿照 Claude 这类 Agent 做一个循环，让模型能观察状态、决定下一步，再调用工具改变文档。最后 Agent Loop 和工具调用部分，主要就是参考 PageAgent 的代码和组织方式。

AI 再围绕这些线索继续找 PPTAgent、PptxGenJS、Slidev、Marp、python-pptx，以及其他文档和设计相关项目。它们分别解决内容规划、PPTX 生成、网页演示、布局设计或文档对象操作，并不是同一种产品。

这一阶段，AI 列出了 11 个候选，也分别整理了它们值得借鉴的地方。

### 04｜没有一个库是答案，但每个库都可能贡献一部分

**页面任务**

展示 WPS 案例最核心的选择方式：从仓库提取可借资产，而不是评“最好项目”。

**画面建议**

画一张“这里借一点，那里借一点”的拼装图。四个来源块分别流向内容结构、设计令牌、布局/QA、状态组织，最终汇入 WPS 插件。

**页面文字**

| 来源 | 真正借走的东西 |
|---|---|
| PageAgent | Agent Loop、LLM 连接与工具调用参考 |
| PPTAgent | 内容 Schema、多步工作流 |
| HTML/PPT 项目 | Design Tokens、布局和样式实验 |
| Mck 类项目 | 布局坐标、字符预算、QA |

**口播**

调研到最后，11 个项目里没有一个能直接回答“WPS 插件该怎么写”。但这并不等于这次搜索失败了。

PageAgent 贡献的是最接近运行核心的部分：Agent 怎样连接 LLM、循环判断下一步，以及模型怎样调用开放出来的 Tool。PPTAgent 贡献内容 Schema 和多步工作流；一些 HTML PPT 项目贡献 Design Tokens、布局和样式；另一些项目贡献字符预算和质量检查。openpyxl、XlsxWriter、python-docx 也不是 WPS 的运行时代码，但它们的对象模型和工具语义可以帮助我们思考 Agent 应该开放哪些能力。

所以我后来更喜欢这样理解“站在巨人的肩膀上”：不是先找到一个巨人，而是先把问题拆开，再从很多成熟项目里分别借走已经验证过的认知。

不过，这 11 项主要来自当时针对 PPT Agent 和 PPT 美化的局部调研。现在按“三宿主 WPS AI 插件”重新搜索，已能找到 [WPS-AI](https://github.com/lewis-hui1202/WPS-AI) 等更贴题的项目。更明确的检索问题、可见项目的变化以及模型和工具的变化都可能有影响，不能只归因于模型变强，也不能倒推说当时已经有现成答案却被漏掉。对照细节见[同题重搜记录](43-WPS同题重搜对照实验.md)。

### 05｜相邻生态是线索，不是事实

**页面任务**

用一次真实失败说明文档、相似 API 与实际运行的证据等级不同。

**画面建议**

先并排展示两张真实文档截图：左侧为 Microsoft Learn 的 Word JavaScript API/对象文档，右侧为 WPS 开放平台的加载项或 JSAPI 文档。用相同的“Document / Range / Paragraph”关键词做视觉连线，印证两套对象模型看起来相近；再用“Microsoft 文档层级完整 / WPS 目标版本资料与类型不完整”的标注显示差异。页面下半部再放失败与修正：`InsertAfter('\r' + text)` → `InsertParagraphAfter()`，代码只显示必要两行。

截图入口：[Microsoft Word JavaScript API](https://learn.microsoft.com/javascript/api/word/)、[WPS 加载项概述](https://open.wps.cn/documents/app-integration-dev/wps365/client/wpsoffice/wps-integration-mode/wps-addin-development/addin-overview)。当前 WPS 截图只有目录、正文未显示；制作时需重找能显示内容的对应页面。若目标页字段确实不完整，可把这种不完整作为证据。

**页面文字**

```text
相似名称 → 生成假设
目标环境运行 → 决定事实
```

**口播**

做这个项目还有一个坑。WPS 加载项文档在我使用的版本里不够完整，AI 找不到一些类型和对象说明，于是参考了 Microsoft Office 的 Word、PPT 文档。微软的文档页面、对象说明和示例相对完整，两边的 API 看起来又很像，很容易让人把微软文档直接当作 WPS 的事实。我还试过让 AI 抓 JSON 资料，对象说明仍不全。

例如插入 Word 段落。按照相邻生态的经验，给 Range 追加一个回车和文本，看起来应该会产生新段落。代码也没有显得特别离谱。但是在目标环境里，新内容没有成为段落集合能识别的新段落，Agent 于是反复调用，越改越乱。最后实际可行的方式，是明确插入新段落，再设置文本。

这件事不说明相邻文档没用。恰恰相反，它很适合快速生成候选方案；只是它不能越级成为目标环境已经验证的事实。

### 06｜复杂项目不能只靠一段聊天记忆

**页面任务**

紧接 WPS，解释复杂项目为什么需要可维护的长期记忆；这里讲的是亲身实践，不是抽象的“知识管理”。

**画面建议**

用树形结构展示这个项目中对 AI 友好的维护文件：`AGENTS.md` / `CLAUDE.md`、`README.md`、`docs/`、`skills/` 和 Git commit。不必展开项目源码；用箭头标出“下次 Agent 从哪里重新进入”。

**页面文字**

```text
聊天记录服务当前回合
项目文件服务下一次进入项目的 Agent
```

**口播**

很多人说 Agent 有上下文，好像它能一直记得我们聊过什么。小需求我往往直接开新上下文；大项目虽然可以接着聊，但上下文终究会被压缩。三小时前顺嘴说过的关键限制，未必还在它能可靠使用的范围里。

WPS 这种同时涉及 Word、Excel、PPT 的项目尤其明显。加载方式、布局尝试、Tool 的输入输出、哪些 Office 经验在 WPS 不成立，都不能靠我每次口述一遍。入口写在 `README` 或项目级 `AGENTS.md` / `CLAUDE.md`；反复发生且步骤稳定的工作可以固化成 Skill；取舍、失败和验证结果留在 `docs`；一次改动为什么发生，还可以从 commit message 再追到 diff。

它们不是越多越好，也不是把聊天记录全文贴进去。关键是让下一位 Agent 很快知道：这个项目是什么，哪条路已失败，怎么验证，以及哪些地方不能想当然。

## 第三幕：B747——从一张低清图追到可用的专业资料

### 07｜真正的起点，是一份我带不回家的 Excel

**页面任务**

让非技术听众理解为什么公开资料检索是实际业务问题，而不是搜索技巧表演。

**画面建议**

左侧制作一张明确标注“根据口述脱敏重构，非原始公司文件”的 Excel 示意，而不是伪装成真实截图。表格可使用 6–8 行全部为 B747 的假数据，列结构接近：

| 机型 | 舱位 | Deck | Position code | 长 | 宽 | 高 | 备注 | 轮廓图 |
|---|---|---|---|---:|---:|---:|---|---|
| B747-400F | M11 | Main | LR | 3.18 | 2.44 | 3.00 | 外侧收口 | 公开 contour 示意缩略图 |

数字必须来自公开资料或使用 `—`，不能伪造成公司内部数据；最后一列用公开轮廓图或自绘几何示意。右侧直接使用[顺丰公开 B747 舱位图](https://www.sf-airlines.com/sf/upload/2026-07-21/17846255080528a3887529ed38db5957019f83f82ed44fd2.png)，暂不放网页截图。中间写“信息很多，但无法直接统计”。

**页面文字**

- 内部 Excel 不能上传外网
- 字段杂、部分信息藏在低清图片里
- 回家后只能通过手机零散查看

**口播**

这个需求是做一个 3D 配载相关页面。产品给过一份 Excel，但一方面它不能传到外网，我回家之后拿不到；另一方面，里面的信息很杂，有些列直接塞图片，图片分辨率也不高。

我在公司试过让可用的小模型识图，效果并不稳定。回家以后只剩手机上的零散信息，要靠人手把每个舱位的名字、位置、大小和形状统计出来，非常痛苦。

所以我换了一个问题：这些资料有没有公开版本？我把公开页面和那张舱位分布图交给 AI，让它不要猜模型，而是沿着图上的文字去找。

### 08｜AI 不是一次搜到答案，而是逐轮学会行业语言

**页面任务**

展示可复刻的 B747 检索链，但不展开全部航空细节。

**画面建议**

一条四步时间线，每一步同时显示“查询词、有效命中、下一轮得到的新词”。搜索结果页可使用 Google 结果截图，但公司网络可能无法访问 Google，所以现场不依赖搜索页跳转；每一步另提供直接打开来源页的按钮。

在讲者提问“如果是你会怎么搜？”时，右下角短暂露出“卧槽，惊奇发现，用自己的脑子写代码不烧 token，是免费的！”梗图。只作为视觉调剂，不解释笑话，也不把它当成对观众的责备。

1. `site:sf-airlines.com "B747-400F"` → [顺丰公开舱位图](https://www.sf-airlines.com/sf/upload/2026-07-21/17846255080528a3887529ed38db5957019f83f82ed44fd2.png) → 得到 `LR / LL / PL / 11P`；
2. `"B747-400F" "LR" "LL" "PL"` → 进入 pallet position / contour 资料 → 得到 `H4M / HPL / PA1 / PA2`；
3. `"B747-400F" "H4M" "HPL" "PA1" "PA2"` → [中国货运航空设备说明](https://www.ckair.com/equipment-specification-400F.html) → 得到 position、contour 与主要尺寸。最终 HTML 可从该页面截取关键图示，配来源链接；
4. `"H4M" "3.18" "2.44"`、`"HPL" "2.87"` → [公开 Cargo Handling Manual 副本](https://www.asiandragonintl.com/inventory/other/2024/dragon-166535B.pdf) 与其他运营资料 → 交叉核对尺寸和配置。

**页面文字**

```text
顺丰舱位图
→ "B747-400F" "LR" "LL" "PL"
→ PA1 / PMD / H4M / HPL / PEB
→ Position → Contour → Geometry
```

**口播**

AI 最后确实找到了我想要的信息。我有点好奇它究竟怎么搜到的，就让它把检索过程写成一份报告。

第一步，从顺丰官网公开的 B747 舱位图里提取 LR、LL、PL、11P 等陌生代码。第二步，把机型和这些低频代码放在一起搜，结果逐渐缩到 pallet position 和 contour 资料，又得到 H4M、HPL、PA1、PA2。第三步，用新词继续搜，定位到中国货运航空的设备说明，拿到 position、contour 和主要尺寸。第四步，再用 contour code 和尺寸数字交叉核对公开的 Cargo Handling Manual。

这条链的关键不是某个搜索操作符，而是从可信材料里提取行业语言，再让每一轮结果生成下一轮查询。没有 AI，我们也能沿这条链搜索；难的是在有限时间里想到这些陌生术语，并把不同来源整理成能用于页面的配置。AI 放大的是探索和整理的宽度。

## 第四幕：三个独立故事——筛选、纠错与验证

### 10｜上一个案例帮我找资料，这一次帮我做技术选型

**页面任务**

从 B747 的资料检索自然过渡到依赖筛选，并强调产品与技术共同提供评审标准。

**画面建议**

左侧回扣 B747 的链条“搜索公开资料 → 整理成配置”，右侧切换到 Web Excel：“搜索候选依赖 → 统一实验 → 技术评审建议”。下方再把模糊气泡“像 Excel”展开成六个条件卡片。

**页面文字**

- Vue 3 能集成
- 核心功能不依赖付费版
- 排序、筛选、列设置、行列移动
- 合并与取消合并
- 大数据与虚拟滚动单列评估
- 简单 HTML + 国内可访问 CDN

**口播**

B747 是让 AI 帮我从公开世界里找到业务资料。接下来这个项目换了一种调研：我已经知道要做什么，但不知道应该选择哪个前端依赖。AI 不只是帮我搜几个库，而是扩大候选、做初步技术评审、生成同题实验，最后给出带适用条件的建议。

如果只问 AI“推荐一个像 Excel 的库”，它一定能给出一个排行榜，但那个排行榜对项目没有意义。是偏业务记录表格，还是偏真正的电子表格？核心功能能不能免费用？我们项目是 Vue 3，不要给我一套 React 才方便集成的答案。演示还希望不经过 npm 构建，直接打开 HTML。

这些不是 AI 应该替我决定的价值判断。产品目标、技术栈和商业边界必须先由人提供。AI 可以帮助把模糊描述展开成可筛选的字段。

**页面任务**

### 13｜CDN 返回 200，也可能拿错了东西

**页面任务**

**画面建议**

三级门禁：`curl/HTTP`、`文件格式`、`真实浏览器`。配一个 200 但错误产物的红色案例卡。

**页面文字**

```text

```

**口播**

简单 HTML 加 CDN 很适合快速比较，但我也被它坑过很多次。AI 写完一个地址，页面没效果；再让它改，它可能继续猜另一个地址。

后来我会明确要求它先用 curl 或 HTTP 请求确认文件到底在不在。可这还不够：这个项目里有一个文件返回 200，名字也像 min.js，但内容只是一个 CommonJS 函数，不是浏览器可直接用的完整包。

而且公司的网络环境有额外一层。有些路径在公网存在，公司访问不了；另一些是路径本来就写错了。最后要走过“地址存在、产物格式正确、公司网络可达、浏览器实际加载”几道门。

这类检查不高深，却很适合交给 Agent 自动做。模型越小、任务越长，越不能假设它会主动补上这一步。

### 15｜不要继续问“ECharts 一般怎么写”，去问当前项目

**页面任务**

给出 ECharts 故事的真实转折，同时纠正版本字段叙述。

**画面建议**

从“模型记忆/网上示例”箭头切换到本地 `node_modules` 类型定义；再放 4.9.0 / 6.0.0 的同配置 HTML 对照截图。截图分别标注“选项留空”和“显式 `true`”，不要只贴代码。

**页面文字**

```js
axisLabel: {
  showMinLabel: true,
  showMaxLabel: true
}
```

**口播**

最后不是 AI 突然灵感爆发，而是我让它停止猜，直接查当前项目 `node_modules` 里的类型定义，找到 `axisLabel.showMinLabel` 和 `showMaxLabel`，再回页面验证，问题才解决。

但这不是“旧版没字段、新版加字段”。后来我回看时发现，[官方 FAQ](https://echarts.apache.org/en/faq.html) 说这两个选项从 3.5.2 就已支持。我用 4.9.0 和 6.0.0 做了同配置对照：选项留空时，端点呈现不同；显式设为 `true`，两版才都显示 `00:12` 和 `06:12`。

能确认的是，默认呈现不能按经验互推，必须显式配置并在目标版本验证。真正的教训不是背字段，而是从“网上一般怎么写”切换到“当前项目这个版本到底如何工作”。

**证据边界**

官方依据：[Apache ECharts FAQ](https://echarts.apache.org/en/faq.html)。本地复验依据：用户提供的双版本 HTML（ECharts 4.9.0 / 6.0.0，四种时间范围，A 为选项留空、B 为显式 `true`）；已在浏览器用 SVG 渲染和页面诊断文字核对。这个对照证明具体现象，不证明差异最早出现于哪个中间版本，也不证明内部实现为何变化。公司项目经过为讲者口述，页面视觉只能制作脱敏示意，不能伪造公司代码截图。

### 16｜Deck.gl：页面能打开，不代表目标行为发生了

- 不要每帧重建无关图层
- CPU 开销可控

**口播**

Deck.gl 这个需求表面上更小：让地图上的台风图标持续旋转。

我早期用 Claude 连接 Qwen 生成过好几个 HTML。页面能打开，代码也像回事，可浏览器里的图标根本不转。Qwen 看过截图后却说“在转”。我怀疑它注意到了页面显示的角度数值，却没核对图标本身；具体误判原因没有查证。

所以人也不能完全退出。截图有用，但不能单靠页面上的状态文字证明图标真的旋转。

后来换到 Codex 中较强的模型，它做了四条独立路线，并把性能、picking 和不重建其他图层写进验收条件。差别不只是多写代码，而是先定义什么叫“真的对”。这不是严谨的模型横向评测：工具、网络、上下文和要求都不同。

这里可以看一下 AI 生成的四个结果。有的图标被拉伸，比例不对；有的效率偏低；还有一个在切到别的页面、过一会儿再回来时，会突然加速，像是在补转。

可以看出，我很喜欢先生成几个小 HTML，或者用 Vite 起一个很小的项目，让人直接试。产品交互不确定时，能点的页面比长篇描述容易讨论；库未选定时，让候选做同一道题；难点不确定时，先把 API 假设从业务项目里隔离出来。改动面更大，还可以放在 Git worktree 中试。

### 20｜为什么这些案例里 Codex 显得更强

**页面任务**

项目展示结束后，再集中拆解能力来源，不把 Codex 简化成“一个更聪明的聊天模型”。

**画面建议**

取真实 Codex 完成界面和行动轨迹的裁图，按“读资料 / 动手 / 看反馈 / 再修”串联。旁边小字标出模型能力、识图、浏览器、终端、Skills / MCP 与项目环境，避免满屏工具 Logo。

**页面文字**

```text
强模型 + 能行动的环境 + 多通道反馈
```

**口播**

回头看这几个项目，我觉得它强不是单一原因。模型本身能力强，能在长任务里保留更多约束；识图能力让它真的看见浏览器或渲染图里的问题；内置浏览器和终端让它能查资料、跑代码、看 Console；自带的 Skill 和 MCP 则能接上更具体的工作流。更重要的是，它可以把编译、lint、测试、运行时错误、截图和人工观察接成一条反馈闭环。

这不等于每一步都正确，也不等于别人只能用 Codex。刚才 ECharts 的故事就说明，再强的模型也可能在错误假设里打转。区别往往是它有没有条件自己拿到证据、有没有被要求把未验证的地方说出来。

- 给模型项目现场，而不只是通用问题
- 让它读源码、依赖、官方文档和 Issue
- 让它运行、看见、复验并留下结论

**口播**

网上有句玩笑：不要教 GPT-6 做事，反过来让它审查你写的所有 Skill。模型确实在变强；学得慢一点，说不定某些技巧还没学会就过时了。但今天的需求还得做，公司里不一定能用同样的模型、网络和工具。

理论上，我们能把刚才的行动方式拆开移植。先把只有人知道的项目背景、业务限制和过去失败告诉它；让它读源码、依赖定义、README、Git 历史，必要时再查官方文档和 Issue；让它先做小 HTML 或小 Vite 项目，把难点跑通；最后给它构建、测试、浏览器和截图，要求它回报哪些已经证实，哪些还没有。没有内置浏览器，可以接 Playwright；没有漂亮的联网搜索，可以用可达的文档镜像、源码或本地依赖。网络不通时，`node_modules`、锁文件和项目文档仍是一套资料库。

当然，小模型未必会主动完成这些步骤，所以更需要明确的任务入口、脚本和项目级 Skill 兜底。我们也可以让 AI 把中文现象改写成“库名 + 版本 + 错误层 + 必须成立的行为”，再去搜 GitHub Issue。找到相似问题后，继续看维护者回复、相关 commit 和目标版本源码，不把搜索摘要当结论。

这些动作没有 AI 也成立。有 AI 时，我们只是把查找和反馈的速度放大了。

## 第六幕：人真正需要提供的，是 AI 不知道的现场

### 22｜把过去、现在和未来一起告诉 AI

**页面任务**

明确人类不可外包的上下文，并覆盖产品经理与开发者。

**画面建议**

三栏时间轴：过去/现在/未来。每栏一个真实例子。

**页面文字**

| 过去 | 现在 | 未来 |
|---|---|---|
| 旧 Bug、兼容性、失败方案 | 完整需求、技术栈、不能做什么 | 下一机型、下一功能、扩展边界 |

**口播**

人和 AI 的分工，我最后把它归成过去、现在和未来。

过去，是这个项目发生过什么。某个浏览器、手机、操作系统或依赖组合以前出过什么问题；哪条路表面可行但已经失败。这些可能只存在于人的记忆、代码注释或一次提交里，公网模型不可能自动知道。

现在，是完整需求和现实边界。不要只说“做个表格”，要说 Vue 3、免费范围、公司网络、真实用户怎样操作。也可以把自己准备怎么实现告诉 AI，但要求它反过来审查：这个办法有什么盲点，有没有更符合当前库最佳实践的做法。

未来，是这个功能接下来会长成什么。比如今天只做 747，但以后还会接其他机型，就应该尽量把机型参数集中配置，把几何和业务规则拆开，避免把 747 常量散落在每个组件里。重点不是强行使用某种面向对象形式，而是给变化留下清晰边界。

这三类信息，是我们真正比通用模型多知道的东西。

### 23｜让项目本身成为下一位 Agent 的老师

**页面任务**

将长期文档、Skill、架构和 Commit Message 收束为一个项目维护观点。

**画面建议**

一个项目文件树，突出 `AGENTS.md/CLAUDE.md`、`docs/decisions`、`skills/`、测试、Git log；箭头指向下一次 Agent 会话。

**页面文字**

- 项目入口：做什么、怎么验证、哪些不能动
- 决策与失败：为什么这样选、什么已经试过
- 专属 Skill：重复发生且步骤稳定的工作
- Commit：定位变化，再打开 diff、Issue 与测试

**口播**

AI 时代写代码更快，项目维护反而更重要。

一个功能两三千行塞在同一个文件里，人很难读，AI 也很难只改正确的边界。比起迷信某一种架构，更实际的原则是：文件职责清楚、接口稳定、依赖方向能解释、验证入口容易找到。公司如果有自己的特殊组件写法，也要在项目里告诉 Agent 怎么用、哪些地方容易出错。

失败经历也应该留下。曾经出现过的 Bug、不能升级的原因、动这个模块会影响什么，可以进入项目文档或专属 Skill。

Commit Message 同样有用。当一个地方突然出问题，AI 可以通过 Git 找到它什么时候改过、当时为什么改，再打开 diff、相关测试和 Issue。提交说明是索引，不是事实终点；但索引写得好，半年后的排查会快很多。

真正的长期记忆，不是让模型永远记得，而是让项目保存足够好的线索。

### 24｜调研的终点，是下一次不用从零开始

**页面任务**

回收主题，给听众一个可执行的最小闭环。

**画面建议**

从 WPS、Deck.gl、大话骰、3D 配载和 Blender 飞机模型中选几张好看的项目图，以部分重叠的卡片形式组成结尾画面，不必每个项目都展示。

**页面文字**

```text
定义问题
→ 扩大候选
→ 回到原始证据
→ 用现实反馈验证
→ 把结论留在项目里
```

**口播**

今天这些项目技术栈完全不同：WPS 插件、B747 货舱、复杂表格、ECharts、Deck.gl、游戏和 Blender。

它们真正共用的是同一条链：人先提供项目现场和判断标准；AI 扩大搜索与实验空间；文档、源码、Issue、运行结果和截图分别承担不同证据；最后把有用结论变成配置、代码、测试、资产或项目记忆。

所以“让 AI 替我调研”不是把判断权交出去，而是把机械搜索、候选扩展、初步整理和重复验证交给它，让人把精力放在 AI 不知道的现场，以及资料最终能不能进入真实业务。

把“为什么这样做、查过哪里、什么失败过、怎样证明成功”留在项目里。下一次不管来的是同事、自己，还是另一个 Agent，都不用重新从零开始。
