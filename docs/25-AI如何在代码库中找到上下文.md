# AI 如何在代码库中找到上下文

## 一、问题不是“上下文够不够长”

大型代码库中的相关信息分散在入口、类型定义、调用者、测试、配置、历史和运行反馈中。把整个仓库一次塞给模型既昂贵，也会混入与当前任务无关的内容。真正的技术能力是把一个自然语言问题逐步定位成少量可验证的代码位置。

这一过程与普通 Web 调研非常相似：先建立地图，再定向搜索；第一轮结果改变下一轮查询；最后让测试和运行时而非模型语气裁决。

## 二、三个研究系统给出的互补证据

### 1. RepoCoder：第一次生成也可以成为下一次查询

[RepoCoder](https://aclanthology.org/2023.emnlp-main.151/) 研究 repository-level code completion。它不是只检索一次，而是让初步生成结果参与下一轮检索，再重新生成。论文在其代码补全基准上报告，迭代检索—生成持续优于一次性的 vanilla retrieval-augmented completion。

对技术调研的迁移不是“照抄其模型”，而是保存查询残留：第一轮看到的类型名、调用模式、错误消息和候选实现，都可以成为第二轮更精确的 `repo/path/symbol` 查询。

### 2. Agentless：先目录，再骨架，再具体位置

[Agentless](https://arxiv.org/abs/2407.01489) 用固定的 localization → repair → validation 三阶段处理软件问题，而不是让模型自由决定全部动作。其定位过程采用分层收窄：先根据简洁仓库结构找可疑文件，再查看类、函数和变量等骨架，最后定位具体编辑位置。

这支持一个很实用的阅读顺序：

```text
目录与模块边界
→ 候选文件
→ 符号骨架与关系
→ 局部实现
→ 调用者、测试与运行证据
```

但论文成绩绑定 SWE-bench Lite、特定模型和 2024 年设置。这里借用的是“层级定位”和“简单固定流程也可能有效”，不把旧榜单成绩用于当前模型排名。

### 3. SWE-agent：搜索能力也取决于给 Agent 的接口

[SWE-agent](https://papers.neurips.cc/paper_files/paper/2024/file/5a7c947568c1b1328ccc5230172e1e7c-Paper-Conference.pdf) 将 Agent-Computer Interface（ACI）视为模型与环境之间的专用界面。论文提出四条接口原则：动作应简单、动作应紧凑高效、环境反馈应信息充分但简洁、guardrail 应帮助阻止错误传播并加速恢复。

它的搜索工具限制过多结果，并在查询过宽时要求收窄；文件查看器只显示带路径、行号和上下文边界的窗口。这说明“给 AI 一个 shell”不等于“给 AI 一个适合研究的工作台”。输出格式、行号、结果上限、错误提示和自动检查都会影响其搜索行为。

## 三、从研究论文转成日常源码调研协议

### 第 0 步：先定义要回答的问题

不要问“总结这个仓库”，改问：

- 这个用户动作从哪个入口进入？
- 哪个组件拥有状态？
- 目标行为由哪个版本引入或改变？
- 哪个测试能否证伪当前假设？
- 哪个适配层承担环境差异？

### 第 1 步：建立低成本地图

只读取目录、语言/构建配置、README、入口和测试布局。产物不是完整架构，而是候选模块与未知列表。

### 第 2 步：结构化定位

组合文件名、精确字符串、symbol、import、调用点和测试名。每次搜索都写明它要证实或排除哪个假设。结果过多时收窄路径或语言；零结果时检查术语、上层封装和版本。

### 第 3 步：让第一轮结果改写第二轮查询

把发现的真实类名、错误文本、配置键、commit、Issue 号和相邻实现加入查询。不要反复用最初的自然语言同义改写碰运气。

### 第 4 步：构建任务相关局部模型

至少记录：入口、关键实体、调用/数据路径、状态所有者、环境边界、测试与未知。知识图谱只是一种可视化；一张 Markdown 表也可以承担同样职责。

### 第 5 步：用外部反馈裁决

源码阅读只能提出实现假设。类型检查、单元测试、目标版本运行、日志、像素或文件差异才回答“它是否真的成立”。

## 四、四种常见检索方式不是互相替代

| 方式 | 最适合 | 容易失败的地方 | 补救 |
|---|---|---|---|
| 精确文本/正则 | 错误消息、配置键、API 名、日志 | 命名不同、生成代码、封装层 | 查调用者、类型和相邻实现 |
| 语义/向量检索 | 自然语言意图、相似功能 | 返回“语义像但运行边界不同”的代码 | 继续用 symbol、测试和版本核验 |
| 结构/符号检索 | 定义、引用、继承、import | 动态语言、反射、运行时注册 | 日志、搜索字符串、运行探针 |
| 仓库地图/知识图谱 | 初始定向、跨模块关系 | 图过期、摘要丢失细节、边太多 | 绑定 commit，按问题生成局部子图 |

推荐组合是“地图定向 + 精确/结构检索 + 语义补漏 + 运行验证”，而不是选择一个万能检索器。

## 五、怎样连接本项目案例

### Deck.gl

从“图标不转”进入 API 名、单位、生命周期和 shader module，再由源码中的真实符号更新搜索词，是典型的迭代检索。四个最小实验承担最终裁决。

### WPS

先从 `tools.ts`、adapter、shared theme 等模块地图定位，再追工具 schema 到宿主对象。浏览器 mock 与 WPS 真机分别验证协议逻辑和环境边界。

### Dice

复盘中的 TASK-BRIEF、FACTS、DECISIONS 和 OPEN-QUESTIONS，本质上是给下一会话一张任务相关地图，避免重新扫描整个仓库。

## 六、演讲可用结论

1. **源码调研不是把仓库塞进上下文，而是把问题逐层定位成可核验的局部模型。**
2. **第一次搜索或生成的价值，不只在答案，也在产生下一轮更精确的词汇。**
3. **Agent 的研究能力由模型、检索策略、工具接口和反馈门禁共同决定。**
4. **仓库地图用于定向，不是事实终点；摘要永远要能回到源码和运行证据。**
5. **简单固定流程与开放 Agent 循环各有适用范围，复杂性本身不是能力。**

推荐度：S。适合紧接“AI 阅读源码与程序理解”，用一页漏斗呈现“目录 → 文件 → 符号 → 代码 → 运行”，再用 Deck.gl 做 2–3 分钟落地。论文指标和具体工具命令放附录。

## 七、证据边界

- RepoCoder 研究代码补全，Agentless/SWE-agent 研究软件修复；迁移到通用技术调研属于方法综合。
- 三项研究的模型、数据集和工具均有时间性，不能据此评价 2026 年具体产品强弱。
- 仓库结构、语义检索和知识图谱的相对效果高度依赖语言、任务与代码库，本项目尚无受控比较。
