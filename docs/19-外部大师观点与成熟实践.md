# 外部大师观点与成熟实践：演讲的理论主干

## 为什么需要这一层

WPS、视频、Deck.gl 和 Dice 是真实案例，但它们只能说明“这些方法在若干具体任务中怎样发生”。演讲的通用方法不能只从个人经历归纳，而应由经典思想、软件工程研究、信息素养研究和现代 Agent 团队实践共同支撑。

建议采用三层证据结构：

```text
经典思想：解释为什么要增强人的知识工作
研究与成熟方法：解释专业人员怎样检索、阅读、核验和复现
现代 Agent 实践：解释这些原则如何被编码进 AI 工作流
本地案例：展示听众可以怎样照着做
```

## 一、人机关系：AI 是知识工作的增强系统

### Douglas Engelbart：优化的是“人 + 工具 + 工作方法”的整体系统

Engelbart 在 1962 年的《Augmenting Human Intellect》中讨论的不是让机器替人回答问题，而是系统性提高人处理复杂问题的能力。他把语言、工具、方法和训练视为相互作用的增强系统。[Doug Engelbart Institute 原始报告](https://www.dougengelbart.org/content/view/138/)

对本演讲最重要的转译是：

> 不要只问模型多聪明；要问问题定义、资料入口、工作协议、工具环境和人的判断是否共同构成了一个更强的研究系统。

这可以成为全场最高层的理论依据。你的案例只是展示如何把这个系统做小、做实。

### Vannevar Bush：价值不只是存资料，而是保存可重走的知识路径

Bush 在 1945 年提出 Memex 与“associative trails”：重要的不只是检索某一条记录，而是把相关材料、个人注释和路径关联起来，并能在以后重新走过或交给别人。[《As We May Think》原文](https://www.theatlantic.com/magazine/archive/1945/07/as-we-may-think/303881/)

这与当前资料库的关系非常直接：书签集合只是仓库，主张—来源—实验—决策的链路才是“trail”。

演讲可用表达：

> AI 最有价值的产物不应只是一份摘要，而是一条以后还能重走的证据路径。

Bush 适合开场或结尾点题，不适合占用大量篇幅讲计算史。

## 二、先定义问题：软件工程也需要证据化决策

### Barbara Kitchenham 等：把经验偏好转成可回答的问题

Kitchenham、Dybå、Jørgensen 在 2004 年提出 Evidence-Based Software Engineering，讨论如何让软件工程决策使用可获得的最佳研究证据，同时承认软件工程受人员技能和生命周期差异影响。[ICSE 2004 原论文](https://www.st.cs.uni-saarland.de/edu/empirical-se/2006/PDFs/kitchenham04_.pdf)

Kitchenham 与 Charters 的系统综述指南进一步要求：预先定义研究问题、协议、纳入/排除条件、质量评价和综合方法，使过程严谨、可审计，并尽量减少研究者偏差。[EBSE 2007 指南](https://www.cin.ufpe.br/~in1037/leitura/kitchenham2007guidelines.pdf)

适合迁移到技术调研的部分：

- 搜索前先写 Research Brief；
- 明确要支持什么决策，而不是只写宽泛主题；
- 预先声明来源范围和纳入/排除条件；
- 记录搜索词、筛选理由与停止理由；
- 区分“研究证据”和“在当前项目中的适用性判断”。

这里不需要把普通调研包装成学术系统综述。应明确：我们借用的是可审计性原则，而不是声称达到系统综述的完整性。

## 三、不要通读一切：分层筛选，再决定阅读深度

### S. Keshav：三遍阅读法

Keshav 的《How to Read a Paper》建议最多分三遍阅读：第一遍获得全貌并判断是否值得继续；第二遍理解内容和证据；第三遍尝试重建作者工作、识别假设与缺口。[University of Waterloo 原文](https://cs.uwaterloo.ca/~Brecht/courses/856/readings/how-to-read/keshav-paper-reading.pdf)

可直接改写为 AI 技术资料筛选协议：

| 阅读层 | AI 提取什么 | 人决定什么 |
|---|---|---|
| 第一遍：资格筛选 | 标题、摘要、目录、版本、作者、结论 | 是否与决策问题相关 |
| 第二遍：证据提取 | 方法、关键事实、代码入口、限制、引用 | 是否足以进入候选方案 |
| 第三遍：工程复现 | 调用链、隐含假设、数据和实验 | 是否值得做 spike 或采用 |

这比“让 AI 总结一百篇文章”更专业：不是每份材料都配得上同样的 token、时间和注意力。

## 四、不要困在来源内部：横向核验发布者和原始上下文

### Sam Wineburg 与 Sarah McGrew：专业事实核查者会 lateral reading

他们观察了 10 名专业事实核查者、10 名博士历史学者和 25 名 Stanford 本科生。事实核查者往往快速离开原站，打开其他标签调查发布者、资助关系和外部评价；研究者将其称为 lateral reading。[原始研究 PDF](https://papers.ssrn.com/sol3/Delivery.cfm/SSRN_ID3701739_code2785140.pdf?abstractid=3048994&mirid=1)

Mike Caulfield 后来把相近实践整理成 SIFT：Stop、Investigate the source、Find better coverage、Trace claims to original context。[SIFT 原始说明](https://hapgood.us/2019/06/19/sift-the-four-moves/)

技术调研中的转译：

- 不在一个项目 README 内部判断它是否可靠；
- 另开页面检查维护者、许可证、Release、Issue、引用和替代实现；
- 不因搜索排名靠前就点击，先浏览结果地形；
- 把教程、新闻稿和 AI 摘要追溯到文档、源码、论文或数据。

这可以成为“来源筛选”部分最有记忆点的外部研究。

## 五、让计算机做重复工作，但保留可复现记录

### Greg Wilson 等：自动化、增量修改、版本控制与断言

《Best Practices for Scientific Computing》由多位 Software Carpentry/科研软件实践者总结，核心建议包括：让计算机执行重复工作、保存命令以便复用、使用构建工具、做小步修改、使用版本控制、加入断言与测试。[PLOS Biology 原论文](https://doi.org/10.1371/JOURNAL.PBIO.1001745)

它为“AI 自动化技术调研”提供一个重要边界：自动化不是让过程消失，而是把重复步骤写成可以复跑、检查和修改的程序。

可映射到本演讲：

- 查询矩阵、抓取、转写和格式整理可以自动化；
- 搜索命令、过滤规则和版本必须留下；
- 小批量跑通后再扩大；
- 中间产物和失败日志进入版本化目录；
- 自动化的输出仍需断言、抽样和人工验收。

## 六、现代研究 Agent：规划、动态搜索、压缩和证据对齐

### Anthropic：研究是动态、路径依赖的搜索

Anthropic 的多 Agent 研究系统由主代理规划问题，再让多个代理探索独立方向，随后压缩和汇总结果。其工程复盘强调：开放研究会随中间发现调整方向；多代理尤其适合可独立并行的广度问题，同时成本高、依赖共享上下文的任务并不适合。[Anthropic 工程复盘](https://www.anthropic.com/engineering/multi-agent-research-system)

适合演讲的原则：

- 搜索计划应能随发现更新；
- 并行任务必须范围互斥、可独立交付；
- 汇总者要检查重复、冲突和遗漏；
- 多 Agent 是预算选择，不是默认最佳实践；
- 每个研究者应该回传高信号证据，而不是完整浏览历史。

### Anthropic：上下文是有限资源，按需读取比一次塞满更可靠

Anthropic 的 context engineering 复盘建议寻找“最小的高信号 token 集合”，并描述 just-in-time retrieval：保留文件路径、链接和查询等轻量标识，需要时再由工具载入原文；长任务则使用结构化笔记、压缩和多 Agent 等方式保持连贯。[Anthropic Context Engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

这正面回答了“最终 PPT 会不会只看短 Markdown”：短文档是地图，原文件是按需加载的证据。最佳状态既不是只看摘要，也不是把所有原文一次塞入上下文。

### Anthropic：先用最简单、可组合的模式

《Building Effective Agents》总结其客户实践：先选择最简单可行方案，只在需要灵活决策时增加 Agent 自主性；明确任务可以使用可预测 workflow，开放问题才需要更动态的 Agent。[Anthropic](https://www.anthropic.com/engineering/building-effective-agents)

这能支持你的重要观点：即使没有 Skill/MCP，也可以先用普通 Markdown、搜索、shell 和验收脚本实现有效研究协议。

### OpenAI：人负责意图和反馈回路，仓库成为 Agent 可读的系统记录

OpenAI 的 Harness Engineering 复盘强调，将产品原则、工程规范、架构约束和执行计划放进 Agent 可访问、可版本化的仓库；文档提供地图，lint、测试与工具负责机械约束；人的注意力用于设定意图、验收标准和反馈。[OpenAI 工程复盘](https://openai.com/index/harness-engineering/)

适合演讲的转译：

> 模型能力决定上限，研究脚手架决定它能否稳定够到这个上限。

厂商自报的效率数字不应作为本演讲的普遍结论；真正可引用的是工作系统的组成和公开的限制。

### Google Research：把文献检索接到代码实验和评价目标

Google 的 ERA 接受科学问题和成功度量，然后搜索文献、写代码、组合技术并评价结果；AlphaEvolve 类工作则把生成候选与可计算 evaluator 结合。[Google ERA](https://research.google/blog/empirical-research-assistance-era-from-nature-publication-to-catalyzing-computational-discovery/)

它支持一个关键升级：

> AI 调研的终点不是报告，而是一个能影响选择的实验、数据或可执行方案。

科学 benchmark 与普通应用开发不同，因此只借鉴“问题 + 成功度量 + 搜索 + 实验 + 评价”的闭环，不搬用其性能宣传。

## 七、从这些资料能再获得哪些演讲内容

### 1. 一段更有根基的历史开场

从 Bush 的知识路径到 Engelbart 的增强系统，再到研究 Agent：AI 不是突然出现的“自动搜索框”，而是知识工作增强长期脉络中的新执行层。

### 2. 一套专业阅读协议

用 Keshav 三遍法解释 AI 如何先筛选、再深读、最后复现，避免“每个链接都总结一遍”的低效做法。

### 3. 一套来源侦查协议

用 lateral reading/SIFT 解释为什么要离开 README、教程和厂商文章，查作者、利益关系、Release、Issue 与原始证据。

### 4. 一套可审计搜索协议

用 Kitchenham 的思路说明：先有研究问题、纳入/排除标准和停止理由，再让 AI 扩展搜索空间。

### 5. 一套 Agent 架构选择规则

- 明确稳定的任务：固定 workflow；
- 开放且路径依赖的任务：Agent 循环；
- 多个独立方向：有限并行；
- 高依赖或共享上下文：单一主线程顺序推进；
- 没有复杂工具：五文件协议也能工作。

### 6. 一套知识沉淀观

摘要是索引，不是证据替身；保存路径、来源和决策关系，最终按需回读原始材料。

## 八、推荐进入演讲的层级

| 观点 | 主要外部支撑 | 推荐度 | 推荐篇幅 |
|---|---|:---:|---:|
| AI 应增强人的复杂问题处理系统 | Engelbart | S | 1 页 |
| 保存可重走的知识路径，而不只是资料堆 | Bush | A | 半页或结尾呼应 |
| 搜索前定义决策问题和筛选协议 | Kitchenham | S | 1 页 |
| 分层阅读，不给所有来源同等成本 | Keshav | S | 1 页 |
| 离开原站做横向核验 | Wineburg/McGrew、Caulfield | S | 1 页 |
| 自动化应可复跑、可版本化、可检查 | Wilson 等 | A | 1 页 |
| 开放研究会动态改写搜索路径 | Anthropic research system | S | 1 页 |
| 上下文采用地图 + 按需读取 | Anthropic context engineering | S | 1 页 |
| 简单 workflow 优先，必要时才上 Agent | Anthropic effective agents | S | 1 页 |
| 仓库知识与反馈回路比单个 Prompt 更重要 | OpenAI Harness Engineering | S | 1 页 |
| 调研要接入可评价的实验 | Google ERA | A | 1 页 |

正式演示不需要做成“名人名言墙”。每位作者只服务一个清楚的操作原则，随后立即接本地案例片段。

## 九、证据边界

- 经典文章用于解释思想来源，不自动证明现代 AI 工作流的效果。
- 厂商工程复盘是一手实践，但存在产品宣传、内部评测和成功案例选择偏差。
- 系统综述和科学计算的方法迁移到日常技术调研时，应降低完备性表述。
- 本地案例用于说明可行性和过程，不用于证明普遍提效或模型优劣。
- 正式演讲前应重新核验 2025–2026 年产品能力、链接和任何效率数字。
