# 案例二：把视频变成可检索、可验证的技术资料

## 问题不是“总结视频”

视频调研包含三个不同问题：

1. 在大量视频中找到值得看的候选；
2. 把音视频转换成机器可搜索的文本；
3. 从文本中提取可执行技术信息，并回到原始来源核验。

只做第三步会导致非常漂亮但不可追溯的摘要。

## 现有流程

### 1. 查询矩阵

本地方案按 7 个维度设计约 65 个关键词，包括通用任务、海外与国产 AI 工具、游戏引擎、游戏类型、工作流和趋势。这比反复搜索“AI 做游戏”更能覆盖不同术语和用户表达。

本地证据：`tmp/docs-ditto/docs/superpowers/plans/2026-08-07-bilibili-ai-game-research.md`

### 2. 元数据初筛

每个候选先收集标题、BV 号、UP 主、发布时间、简介、标签、播放和评论。优先信号包括项目链接、提示词、具体工具名、教程和完整工作流；纯资讯和纯广告被排除。

这一步的价值是把昂贵的音频下载与转写留给高潜力候选。

### 3. 多级获取策略

```text
标题与搜索摘要
    ↓
简介 / 标签 / 热评
    ↓
官方字幕或自动字幕
    ↓（不可用时）
下载音频 → ASR 转写
```

这种设计承认平台接口与字幕覆盖不稳定，并准备了降级路径。Google NotebookLM 的官方说明也明确：YouTube 导入依赖公开字幕，只导入文本 transcript；本地音频则会在导入时转写。[NotebookLM 来源说明](https://support.google.com/notebooklm/answer/16215270)

这可以形成一个很好的演示对比：有字幕的平台可以直接进入 source-grounded 工具；没有可靠字幕的平台需要自建音频—ASR 管线。

### 4. 不要按视频顺序整理，而要按决策字段整理

适合提取的字段包括：

- 工具与版本；
- 任务目标；
- 完整步骤；
- 命令、配置和提示词；
- 项目地址和依赖；
- 成功条件与失败条件；
- 作者主张与可观察证据；
- 需要回到源码或官方文档核验的事项。

最终输出应按工具、引擎、工作流和资源重组，让多个视频可以回答同一个问题，而不是产生几十篇孤立摘要。

### 5. 视频是发现来源，不一定是最终证据

一条视频可以帮助发现：

- 一个此前不知道的项目；
- 一个特定版本的 bug；
- 一种工作流或提示词；
- 作者实际操作中的隐含步骤。

但关键 API、兼容性和性能结论仍应回到官方文档、源码、Issue、Release 和本地实验。视频中的界面也可能对应旧版本。

## 推荐资料卡

```markdown
### 视频标题

- 链接 / BV 号：
- 作者、日期、时长：
- 入选原因：
- 使用工具与版本：
- 可执行步骤：
- 项目与文档链接：
- 转写时间戳：
- 关键主张：
- 主张对应的可见证据：
- 外部核验结果：
- 未解决问题：
- 演示推荐度：S/A/B/C/D
```

## 适合演示的最小闭环

现场不需要批量跑完几十个视频。选择一个包含项目链接和实际操作的视频，展示：

1. 它如何从查询矩阵被找到；
2. 为什么元数据评分让它进入深读；
3. 字幕不可用后如何下载音频并转写；
4. 如何从转写中提取项目、命令和流程；
5. 如何回到 GitHub 或官方文档核验；
6. 最终如何写入结构化资料卡。

## 风险与边界

- ASR 会错认产品名、命令、英文缩写和数字；
- 自动摘要可能删除作者的保留条件；
- 视频日期不等于所用工具版本；
- 播放量只能表示传播程度，不能表示技术正确；
- 评论可提供故障信号，但不能自动升级为权威事实；
- 下载、转写和展示应尊重平台条款与版权，演示只使用必要片段和转述。

## 恢复材料后的新增发现

macOS 原生 `ditto` 已成功恢复压缩包中的中文文件名。完整材料显示：

- 搜索阶段声称覆盖 65 个关键词、约 400 个候选并精选约 80 个；
- 后续阶段进一步聚合了 123 份视频口播转写；
- 输出按总览、工作流、AI 工具、引擎、资源和独立洞察重新组织；
- 聚合文档主动标记无有效口播、纯 Demo、BV 号待补和 ASR 同音字风险；
- 资源汇总中仍存在占位链接、未匹配来源和大量需要重新核验的时效数据。

这使案例同时具备正面和反面教材价值：它证明 AI 可以把海量非结构化材料压缩成主题知识，也说明“大规模自动整理之后，来源治理工作才刚开始”。

## 候选单视频样例

### 候选 A：BV1DVwLz2EGv

本地标题为《裸辞回国做独立游戏，花了2万8摸索出的AI编程工作流》。聚合转写中提取了“文档是第一公民”、PRD 包含术语表/交互方式/验收标准、plan+review、worktree 并行和固定流程 Skill 化等信息。

推荐度：S。理由是它横跨需求、研究、实现、测试和沉淀，最贴合演讲主线。风险是标题成本数字、逐字引述和作者身份仍需回看原视频或原始转写核验。

### 候选 B：BV1g4MS67ECB

本地标题为《AI 到底替人做完了哪一段？我对照了六段游戏制作记录》。核心判断是 AI 缩短“想法到可测试”的距离，而“可测试到可交付”仍需要人工判断、整合、验证和维护。

推荐度：S。适合做演讲结论的第三方呼应。风险是当前公开网页抓取受 B 站 412 限制，需要本地原始转写或人工打开页面核验。

### 候选 C：BV1PTTs6cEwi

本地标题为《不写一行代码！0基础用AI开发修仙游戏【全流程教程】》。它提供了分步生成、每步验收、把报错反馈给 AI 的直观流程。

推荐度：A。适合做最易懂的流程演示，但方法深度不如候选 A，且“不写代码”标题容易让主题滑向工具宣传。

## 当前核验状态

B 站页面通过研究工具直接访问时返回 412，因此上述内容暂时属于“本地调研材料所记录的事实”，尚未升级为已重新核验的公开网页事实。正式演示前应至少完成：

1. 手动打开视频确认标题、作者和发布日期；
2. 找到对应原始转写文件和时间戳；
3. 对拟展示引述回听音频；
4. 对成本、版本和项目链接做外部核验；
5. 删除或降级无法定位的引述。
