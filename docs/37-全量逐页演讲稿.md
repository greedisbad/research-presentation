## 第一幕：AI 很聪明，但它不知道你的现场

### 01｜AI 过上了打工人梦想中的生活

**本页唯一判断**

AI 的工作条件看似优越，但结果责任仍然留在人手里。

**屏幕文字**

> 需求必须明确；出错领导负责；钱到位才上班。  
> 它偶尔还会偷懒——而且你骂它，也要花钱。

**完整口播**

AI 终于过上了打工人梦想中的生活。

上级必须把任务说清楚，最好连格式和验收标准也写明白。工作出错了，领导要负最终责任。钱到位才上班，额度用完，它就可能直接罢工。

更过分的是，它偶尔还会摸鱼。少读一个文件、跳过一次验证、看到一个像答案的结果就提前交差。你发现以后当然可以骂它——但是你骂它的每一个字，也要花钱。

玩笑归玩笑，这里面有一个非常现实的问题：我们总觉得 AI 应该知道怎么做，但它不知道我们公司以前踩过什么坑，不知道这个项目当前安装的版本，不知道这个需求和普通需求哪里不一样，也不知道谁最终要为结果负责。

今天我不讲一个“万能 Prompt”。我想分享的是：当我们把只有自己知道的现场信息交给 AI 后，搜索、阅读、比较、试验和整理，还有多少可以让它自己完成？

**画面占位**

- **[示意图]** 极简“AI 员工合同”：需求明确、领导负责、按 token 计费、骂人也计费。
- 页面只保留四个短句，不放角色漫画或复杂背景。

**证据与边界**

这是修辞性开场。“偷懒”“罢工”是拟人化说法，后文会还原为上下文不足、工具调用被省略、用量中止和验收未执行等可观察现象。候选版本见 [`39-开场与结尾候选.md`](39-开场与结尾候选.md)。

**转场**

> 那么，AI 到底不知道什么？先看四个非常普通的项目现场。

**编排标签**：核心；默认 hook；彩排时控制在 60–90 秒。

### 02｜四个“看起来已经完成”的结果

**本页唯一判断**

完整的输出形状不能证明目标已经达成。

**屏幕文字**

> 配置写了，但效果没出现。  
> 页面打开了，但动画没发生。  
> 功能能玩，但画面很难看。  
> 候选很多，但问题还没定义。

**完整口播**

这四句话分别来自我最近几个项目。

ECharts 的配置写进去了，页面不报错，可两端 label 没出现。Deck.gl 的 HTML 可以打开，目标对象却没有按预期运动。大话骰的规则和交互已经能跑，但没有视觉反馈的 Agent 做出了一个很难看的页面。Web Excel 找到了很多库，可我们后来才发现，“像 Excel”根本不是一个完整需求。

这些都不是 AI 什么都没做。相反，它已经做出了很完整的结果。危险恰恰在这里：完成的代码、完整的文档、漂亮的解释和一串链接，很容易让人误以为问题已经结束。

接下来这场分享会反复区分两件事：AI 完成了一个动作，和项目达成了目标。

**画面占位**

- **[示意图]** 四张症状卡：图表无变化、地图静止帧、暗色游戏截图、表格候选列表。
- **[项目图片]** 若大话骰早期截图可公开，使用真实画面替换第三张示意。

**证据与边界**

ECharts 目前是讲者一手回忆，没有可公开代码和截图；必须标注示意。Deck.gl、大话骰和 Web Excel 有本地项目记录，详细边界见 [`38-案例演讲素材母稿.md`](38-案例演讲素材母稿.md)。

**转场**

> 为什么 AI 会停在“动作完成”？因为它缺少我们脑子里的项目现场。

**编排标签**：核心；四个故事只报症状，不在此处解释解法。

### 03｜模型知道公共知识，人知道项目现场

**本页唯一判断**

人最不可替代的输入，是模型无法自行获得的过去、现在和未来。

**屏幕文字**

```text
过去：以前出过什么问题？
现在：这次需求哪里不同？
未来：还要兼容什么场景？
```

**完整口播**

模型掌握大量公共知识。它可能知道一个库通常怎样配置、一个框架通常怎样组织、网上的人通常怎样解决类似问题。

但项目真正困难的部分，往往不在“通常”。

只有我们知道，公司以前因为某种方案出过什么事故；哪些代码不能这样写；这次需求为什么和一般场景不同；数据能不能离开内网；半年以后还要支持哪个流程；什么结果即使技术上成立，业务也不会接受。

我把这些信息分成项目的过去、现在和未来。人不需要亲自研究所有候选，但要把这三个时间维度告诉 AI。否则 AI 找到的只是一个平均世界里的平均答案。

这也是产品经理、业务人员和领域专家进入技术调研的位置：不是替开发查 API，而是提供公共资料里没有的现场。

**画面占位**

- **[示意图]** 三段时间轴：旧事故/现有约束/未来扩展，中间连接“AI 公共知识”。
- 每段只放一个航空或软件例子，避免文字墙。

**证据与边界**

这是跨案例抽象，不表示把信息给完后人就无需判断。最终权重、冲突裁决和验收仍由人负责。演讲定位见 [`00-演讲定位.md`](00-演讲定位.md)。

**转场**

> 有了现场，AI 能替我们做什么？先从一个几乎没有代码的航空问题开始。

**编排标签**：核心；面向非技术听众的职责定位。

### 04｜ECharts：问题不是不会写，是查错了对象

**本页唯一判断**

版本相关问题应优先回到当前项目安装的事实，而不是继续让模型猜。

**屏幕文字**

> 从“ECharts 一般怎么写”  
> 到“这个项目安装的版本允许怎么写”

**完整口播**

公司里有一次需求，是让折线图 X 轴左右两端的 label 必须显示数据端点的值。

AI 给了配置，写进去没有效果。项目不是 TypeScript，所以错误字段也没有编译提示。接下来最自然的反应是继续调整配置，而模型每次都能给出一个听起来合理的新解释。

后来真正改变结果的动作很简单：不让它继续猜，直接去看项目 `node_modules` 里当前安装版本的定义。

这里最值得记住的不是某个字段，而是检索对象发生了变化。网上示例和模型记忆回答的是“某个版本可能怎样”，本地依赖回答的是“这个项目现在允许什么”。运行画面已经告诉我们原方向不成立，下一步应该换证据，不是换措辞。

**画面占位**

- **[示意图]** 左侧“网上示例/模型记忆”，右侧“当前依赖定义”，下方一张无变化的折线图。
- **[待补证]** 若未来能做脱敏最小复现，再替换示意。

**证据与边界**

来源为讲者一手回忆，见 [`34-演讲叙事取舍与ECharts口述案例.md`](34-演讲叙事取舍与ECharts口述案例.md)。不展示字段名、版本号、公司代码和修改次数。

**转场**

> 版本是软件项目里的“现场”。航空资料里的现场，则叫机型、构型和业务语境。

**编排标签**：核心或可删；若使用 B747 图开场，本页可移至第五幕回响。

### 05｜今天不是教搜索框，而是教“去哪里问”

**本页唯一判断**

技术调研的核心不是搜索次数，而是让问题进入能直接回答它的证据。

**屏幕文字**

> 平台事实、版本事实、运行事实、业务事实  
> 不应该问同一个来源。

**完整口播**

很多时候我们把“调研”理解成打开搜索框，然后不断优化关键词。

但 ECharts 的故事已经暴露了另一个问题：就算关键词写得很好，如果问错了对象，得到的答案依然不适用于当前项目。

平台允许什么，官方文档最直接；当前版本怎么实现，本地依赖和同版本源码更直接；为什么某次修改发生，可以看 Issue、PR 和 Commit Message；页面实际上发生了什么，只能运行；一个方案是否符合业务，需要用户和领域专家。

所以今天会有搜索，但不会只讲搜索。我们会看代码、维护文档、线上文档、Issue、提交历史、运行错误和截图。它们不是权威排行榜，而是不同问题的不同传感器。

**画面占位**

- **[示意图]** 五类问题分别连接文档、源码、Git、运行和用户。
- 此处只给轮廓，第五幕再给完整来源路由。

**证据与边界**

来源分工由 WPS、Deck.gl、Tabloom 和 Web Excel 多案例支持；并不表示首选来源永远正确或充分。交叉证据见 [`evidence/C01-Codex项目复盘交叉提炼.md`](evidence/C01-Codex项目复盘交叉提炼.md)。

**转场**

> 接下来我们就用一张 B747 货舱图，看看“去哪里问”怎样发生。

**编排标签**：可删；现场版也可直接从第 04 页进入第二幕。

### 06｜全场问题：还有多少选择可以交给 AI

**本页唯一判断**

这场分享要探索的不是 AI 能否替代人，而是哪些调查动作可以安全外包。

**屏幕文字**

> 人给现场、权重和验收。  
> AI 找、读、比、试、记。

**完整口播**

到这里，我把全场问题说完整。

人把目标、过去的经验、当前限制、未来场景和风险权重告诉 AI。然后，找候选、读文档、定位源码、比较许可证、跑一个最小实验、记录失败路线，这些动作能不能大部分交给 AI？

我的答案是可以，而且已经可以做得非常深。但有一个前提：我们不能只看它最后写出的答案，还要看它去了哪里、拿到了什么证据、怎样被现实纠正，以及最后留下了什么可复用资产。

下面四个项目分别回答四个问题：B747 讲怎么进入陌生资料；WPS 讲怎么从多个轮子拿局部；Web Excel 讲怎么替人扩大选择；Deck.gl 讲失败后怎样继续行动。

**画面占位**

- **[示意图]** 四个案例图标排成路线，不出现大量方法术语。

**证据与边界**

这是叙事导航，不预先承诺每个项目都适用于所有组织。四个案例的事实边界见 [`38-案例演讲素材母稿.md`](38-案例演讲素材母稿.md)。

**转场**

> 第一站，是一张我最初并不能完整读懂的货舱图。

**编排标签**：核心；可与第 05 页合并。

## 第二幕：B747——从一张看不懂的图，找到能行动的资料

### 07｜起点不是参数表，而是一张业务图

**本页唯一判断**

真实调研经常从不完整、未解释的业务材料开始。

**屏幕文字**

> 我需要一个 3D 货舱。  
> 手里只有一张满是代码的图。

**完整口播**

这个案例来自一个 3D 配载相关需求。要在页面里放置 ULD 或货物，首先得知道货舱位置、轮廓和大致可用空间。

理想输入当然是一份结构化数据：每个位置的坐标、截面、限制和构型。但现实起点是一张业务图。上面有位置、有线条、有数字，还有很多没有解释的缩写。

如果直接让 AI “给我 B747 货舱尺寸”，它很快会给出一个看起来完整的答案。问题是，我们不知道它对应哪一种 747、哪一种改装、哪个航空公司的构型，也不知道这些数字是否适合当前业务图。

所以第一步不是请它补全参数，而是承认我们还不知道图上的语言。

**画面占位**

- **[待补证]** 原始货舱图的合规裁切；若不可公开，使用结构相近的重画示意。
- 先整体展示 3 秒，再逐渐淡化，只留下几个代码。

**证据与边界**

完整过程见 [`B747-400F_information_retrieval_method.md`](B747-400F_information_retrieval_method.md)。公开资料只服务 3D 预判，不能替代内部装载手册。

**转场**

> 图上的陌生代码看起来是障碍，后来却成了最好的搜索入口。

**编排标签**：核心；航空听众的业务入口。

### 08｜最看不懂的代码，信息量可能最高

**本页唯一判断**

低频术语和罕见代码比通用需求描述更能缩小搜索空间。

**屏幕文字**

> A1 / A2 / B1  
> LR / LL / PL  
> 11P

**完整口播**

图中最显眼的是一些我无法立即解释的符号。

普通人的第一反应可能是把它们忽略，只保留“B747”“货舱”“尺寸”这些熟悉词。但熟悉词往往也是最拥挤的词。它们会把我们带到百科、新闻、模型和大量重复页面。

相反，一个罕见位置代码和另一个缩写同时出现，能迅速过滤无关结果。AI 在这里适合做两件事：批量提取图上的低频 token；组合多个 token 和机型语境，观察它们在哪些专业资料中共同出现。

这和排查错误日志很像。最有价值的往往不是“系统出错了”，而是那一段独特的错误文本。

**画面占位**

- **[示意图]** 原图中的通用词变灰，三个罕见 token 被圈出。
- **[搜索图片]** 一个脱敏后的低频共现查询与结果类型，正式制作时重新捕获。

**证据与边界**

罕见代码只是检索线索，不自动证明含义。含义需回到同一资料体系中的定义、图例和上下文。案例摘要见 [`35-案例-B747货舱资料检索.md`](35-案例-B747货舱资料检索.md)。

**转场**

> 当代码终于开始有名字，我们就能从位置编号继续追到轮廓语言。

**编排标签**：核心；可与下一页做连续动画。

### 09｜搜索词不是一句话，而是一组共现约束

**本页唯一判断**

有效查询可以由对象、位置、罕见代码和资料类型组合生成。

**屏幕文字**

```text
机型 + 货舱层级 + 位置代码 + contour code + manual
```

**完整口播**

很多人让 AI 搜索时，会反复润色同一句中文问题。

这个案例更像构造一个查询矩阵。对象是 B747 的哪种货运构型；位置是主舱还是下舱；图上有哪些代码；我们要找的是 contour、loading manual、position 还是 envelope。

AI 可以把这些维度组合成多组查询，快速观察哪些词会把结果带入同一个专业资料群。比如某些 contour code 一旦出现，资料就不再是整机宣传，而开始讨论具体截面和可用轮廓。

这里人的价值仍然很明确：业务人员能判断结果有没有进入正确语境。AI 负责扩大组合和读取，人负责指出“这张图说的是我们要的那一层”。

**画面占位**

- **[示意图]** 四列查询矩阵，动画展示一行如何组合。
- 不直接展示所有历史查询，避免观众阅读负担。

**证据与边界**

查询矩阵是一种方法重画，不是搜索引擎内部工作过程。完整查询演化见 B747 方法文档；演讲只保留一条代表路径。

**转场**

> 有时标题和文字仍然不够。这时，一组数字比名称更诚实。

**编排标签**：核心；方法可迁移到法规、设备型号和错误排查。

### 10｜数字也可以当搜索指纹

**本页唯一判断**

当资料命名不一致时，一组共同出现的尺寸可以帮助反查同源材料。

**屏幕文字**

> 标题会改，转述会变。  
> 一组尺寸同时出现的概率很低。

**完整口播**

专业资料还有一个困难：同一张图可能被裁切、转载、改标题，网页正文也未必包含我们熟悉的业务叫法。

但图里的多组尺寸很难全部巧合。把其中两三个数字与机型、contour code 组合起来，就像给资料按了一次指纹。

这不是说数字天然可靠。相反，数字更需要单位、构型和来源上下文。它的价值是帮助我们重新定位资料，然后回到原始页面或 PDF 检查，而不是把搜索摘要里的数字直接抄进模型。

这种做法也可以迁移到错误码、协议字段、硬件尺寸和标准条款：当名称变化很大时，寻找不容易同时重复的特征组合。

**画面占位**

- **[示意图]** 三个数字形成指纹，命中一张专业 PDF 页。
- **[网站图片]** 若权限允许，展示原 PDF 中相同数字的局部并保留来源页脚。

**证据与边界**

数字指纹用于定位，不等于完成验证。单位、配置和版本必须在原始资料中确认。未归档原 PDF 页面时使用示意，不伪造搜索截图。

**转场**

> 找到资料之后，新的问题来了：为什么不同资料给出的轮廓不完全一样？

**编排标签**：核心；航空案例中最具记忆点的方法之一。

### 11｜冲突不是噪声，它可能代表不同构型

**本页唯一判断**

专业资料冲突时，应保存适用条件，而不是让 AI 强行选一个数字。

**屏幕文字**

> 同名机型 ≠ 同一构型  
> 冲突 → 标签 → 待确认

**完整口播**

当多个资料终于被放到一起，我们可能期待它们互相印证。但现实里经常出现不同数字和不同轮廓。

这时最危险的动作，是让 AI “综合一下”，最后给出一个没有来源的平均答案。差异可能来自货机原生型与改装型、航空公司构型、位置定义、左右侧、上下舱或者手册版本。

更可靠的整理方式是给每条结论加适用标签：它来自哪种构型、哪个位置、哪个来源，哪些冲突还需要内部资料确认。

从开发角度看，这意味着数据结构里要允许多个候选和置信度，而不是只留一个 `height` 数字。未知并不是文档写得不够漂亮，而是产品需要处理的状态。

**画面占位**

- **[示意图]** 两张轮廓卡并列，中间不画红叉，而标注“构型 A / 构型 B / 待内部确认”。
- **[待补证]** 原始冲突图表需确认展示权限。

**证据与边界**

案例中部分左右折点、Q 位高度和 Bulk 边界仍未确认。未知项必须保留，见 [`sources/local/B747-400F_SF_cargo_positions_contours.md`](sources/local/B747-400F_SF_cargo_positions_contours.md)。

**转场**

> 调研到这里还没有结束。下一步是把资料翻译成开发真正能消费的东西。

**编排标签**：核心；面向业务和开发共同解释“为什么不能只要一个答案”。

### 12｜资料只有进入约束，才开始影响项目

**本页唯一判断**

技术调研的产物应能进入模型、接口或决策，而不只是链接收藏。

**屏幕文字**

```text
来源 → 事实 → 适用构型 → 几何约束
                    ↘ 置信度 / 未知项
```

**完整口播**

找到专业图表只是中间状态。3D 项目不能直接消费“我看过一份 PDF”，它需要坐标、轮廓折点、适用位置和碰撞边界。

所以 AI 的下一项工作，是把资料转换成结构化约束，同时保留来源和不确定性。哪些点来自明确数字，哪些由图形推断，哪些只是为了当前概念模型做的简化，都要分开。

这一步特别适合 AI，因为它可以批量整理位置、代码和字段；但它也特别需要人，因为业务人员要决定哪些未知可以暂时容忍，哪些必须在进入生产前回到内部手册确认。

我认为“技术参考”真正变成“开发资源”，就是从这一刻开始。

**画面占位**

- **[示意图]** 一张几何约束卡：位置、折点、来源、置信度、未知。
- **[项目图片]** 如果后续 3D 页面有轮廓展示，可作为右侧结果图，但要标注概念模型。

**证据与边界**

公开资料支持预判和原型，不支持正式装载批准。事实、推断和待确认项必须在画面上使用不同标记。

**转场**

> 这个案例没有大量代码，却已经展示了搜索、筛选和结构化。接下来进入软件项目：找到很多轮子之后，怎样只拿需要的部分？

**编排标签**：核心；第二幕的工程落点。

### 13｜B747 案例复盘：AI 做了什么，人做了什么

**本页唯一判断**

AI 可以扩大和整理资料，人负责语境、冲突和行动边界。

**屏幕文字**

| AI | 人 |
|---|---|
| 提取代码、组合查询、批量整理 | 判断业务语境、风险与内部确认 |

**完整口播**

我们暂停一下，看这条链里谁做了什么。

AI 做了大量适合机器的工作：从图片提取 token，组合查询，阅读多份材料，把位置和轮廓整理成表，发现冲突，生成几何字段草案。

人做的工作数量更少，但权重更高：确认搜索是否进入正确业务语境；判断某个差异是不是构型差异；决定公开资料只能用于原型，哪些地方必须回到内部 W&B 或装载手册；最终验收模型是否适合当前用途。

这不是“人做判断、AI 做苦力”那么简单。AI 也会提出人没有想到的查询路线；人也不必手工读完每一份资料。更准确的说法是：人负责那些只有组织现场才能决定的分叉。

**画面占位**

- **[示意图]** 同一条流程上用两种颜色标 AI 与人，而不是左右完全割裂。

**证据与边界**

职责划分来自本案例的实践，不是组织流程标准。不同公司对数据、合规和签字责任的边界不同。

**转场**

> 下一幕我们面对另一种资料：不是一张图，而是 11 个看起来都很有用的开源项目。

**编排标签**：可删；可在压缩时并入第 12 页口播。

### 14｜可迁移的方法：先找进入资料体系的钥匙

**本页唯一判断**

面对陌生领域，先寻找专业资料使用的语言，再扩大阅读。

**屏幕文字**

> 罕见术语 → 共现查询 → 数字指纹 → 来源分工 → 可执行约束

**完整口播**

B747 案例可以压缩成五个动作。

先从现有材料中寻找罕见术语；用多个低频特征做共现查询；名称不稳定时用数字或结构指纹反查；找到材料后让不同来源分别回答业务、定义、版本和运行问题；最后把结论写成开发可消费的约束，而不是一段百科摘要。

这套方法并不只适用于航空。陌生协议的错误码、硬件的型号组合、监管文件的条款号、某个库的独特类型名，都可以成为进入资料体系的钥匙。

但有一点不会自动化消失：你仍然要决定，这把钥匙打开的是不是自己真正要进的那扇门。

**画面占位**

- **[示意图]** 五节点路径，背景淡化使用货舱图局部。

**证据与边界**

这是案例后抽象，不应扩展成搜索技巧清单。正式现场版若节奏紧，可只保留第 12 页末尾的一句话。

**转场**

> 当资料不再是一张图，而是十几个成熟项目，问题从“怎么找到”变成“到底拿走什么”。

**编排标签**：可删；第二幕总结页。

## 第三幕：WPS——找巨人的肩膀，不等于找到一个巨人

### 15｜找到 11 个项目，没有一个是答案

**本页唯一判断**

候选很多并不意味着存在一个可以整体复制的解决方案。

**屏幕文字**

> 11 个参考项目  
> 0 个可以直接搬进 WPS

**完整口播**

做 WPS 插件时，我让 AI 调查了 11 个 PPT 和文档相关项目。

它们并不差。有的生成效果很好，有的内容组织成熟，有的布局和主题做得漂亮，有的测试体系值得学习。但当前项目有自己的宿主：代码要在 WPS 加载项环境运行；输出还要继续编辑；Word、Excel 和 PPT 又有不同对象模型。

于是一个很容易犯的错误出现了：我们把“来源质量高”误认为“可以直接作为当前方案”。实际上，一个非常好的 Python 项目可能完全不能进入 WPSJS；一个个人仓库可能不够权威，却展示了值得验证的接口结构。

这 11 个项目的价值，不是选出冠军，而是帮助我们看见有哪些局部资产可以借。

**画面占位**

- **[项目图片]** 候选项目表裁切，只突出宿主、输出、可编辑性和可借资产四列。
- **[示意图]** 11 张卡片上方标“不是淘汰赛”。

**证据与边界**

候选研究见 [`02-案例-WPS插件.md`](02-案例-WPS插件.md) 与原项目 Phase 02。正式制作不需要展示 Star 数；若展示，必须在冻结日重查。

**转场**

> 所以我们不再问哪个项目最好，而是问每个项目能贡献什么。

**编排标签**：核心；WPS 主案例入口。

### 16｜把“轮子”拆成四类可借资产

**本页唯一判断**

参考项目中的代码、设计参数、架构模式和验证方法需要不同迁移方式。

**屏幕文字**

```text
代码 / API 用法
设计参数
架构模式
验证方法
```

**完整口播**

“不要重复造轮子”这句话太容易让人想到复制代码。

但一个项目真正可借的东西至少有四种。第一是代码或 API 用法，可以在同一技术边界内直接改写。第二是设计参数，比如布局坐标、字号层级和字符预算。第三是架构模式，比如内容协议、Agent Loop 和 adapter。第四是验证方法，比如如何发现溢出、怎样做质量门禁。

这四种资产的迁移成本完全不同。代码最具体，也最容易受运行时和许可证影响；模式更抽象，需要重新实现；设计参数可以进入 Theme；验证方法甚至不需要带走原项目的任何运行代码。

AI 的优势是能快速阅读多个仓库，把资产从“项目品牌”里拆出来。人的任务是决定哪一类资产适合当前约束。

**画面占位**

- **[示意图]** 一个仓库盒子拆成四个抽屉，每个抽屉用不同颜色。
- **[项目图片]** 若可读，配一小块真实映射表裁切。

**证据与边界**

映射见 [`02A-WPS参考到代码映射.md`](02A-WPS参考到代码映射.md)。分类不意味着每项都可合法复制，仍需检查许可证、来源和当前实现。

**转场**

> 拆完以后，WPS 项目并没有变成拼贴，而是重新建立了自己的稳定边界。

**编排标签**：核心；中心方法页之一。

### 17｜这里借一点，那里借一点

**本页唯一判断**

多个参考可以分别补齐一个当前项目，而无需共享同一技术栈。

**屏幕文字**

```text
内容协议 ─┐
设计参数 ─┤
Agent 编排 ┼→ WPSJS Adapter + Tool Schema + Tests
验证方法 ─┤
宿主边界 ─┘
```

**完整口播**

这张图是 WPS 案例最核心的一张。

一个项目贡献内容 Schema，让模型描述“这一页要表达什么”；另一个项目贡献设计 token 和布局经验；另一个项目贡献 Agent 的步骤历史与工具调用模式；官方文档和真实宿主告诉我们 WPS 到底支持什么。

最后它们没有被拼成一个依赖怪兽，而是被翻译成项目自己的 WPSJS adapter、工具 schema 和测试。

所以我现在理解的“站在巨人的肩膀上”，不是找到一个巨人以后整个人搬过去。更像是：从很多成熟实践里分别拿到一块经过验证的认知，再按照当前宿主重新装配。

**画面占位**

- **[示意图]** 使用屏幕文字中的多来源汇流图，逐条动画进入当前项目。
- **[项目图片]** 背景可淡化使用 WPS 插件真机截图。

**证据与边界**

这张图重组自 WPS 参考到代码映射。它表达资产流向，不表达代码复制比例或模型独立贡献比例。

**转场**

> 这些外部经验进入项目时，需要一个共同语言。WPS 里这个语言不是坐标，而是语义协议。

**编排标签**：核心；建议现场停留并逐条讲解。

### 18｜先让模型说语义，再让工具负责坐标

**本页唯一判断**

模型与确定性工具之间需要一个稳定协议，而不是让模型直接承担所有渲染细节。

**屏幕文字**

> 模型：这页是什么、有什么内容  
> 工具：放在哪里、怎样生成、如何检查

**完整口播**

如果让模型直接输出每个文本框的坐标、字号、间距和颜色，它当然能生成，但每一页都可能重新发明布局规则。

WPS 项目从外部参考中借鉴的一个重要思想，是把页面内容先写成语义协议。模型负责这一页的类型、标题、要点、强调关系和素材需求；稳定的 Theme、布局规则和 executor 再把它翻译成 WPS 对象。

这不是为了限制模型创造力，而是把高频、可验证、容易重复出错的部分交给确定性工具。模型更擅长内容和意图，工具更擅长坐标、批量执行和对象生命周期。

协议还有一个好处：浏览器 mock 与 WPS adapter 可以消费同一种输入，前者快速验证工具语义，后者验证真实宿主。

**画面占位**

- **[示意图]** 左侧一张简洁 SlideSpec 卡，右侧分成 Browser Adapter 与 WPS Adapter。
- 不展示完整 JSON，保留 4–5 个语义字段。

**证据与边界**

协议和 Theme 映射见 [`evidence/W04-WPS模板迁移到运行门禁.md`](evidence/W04-WPS模板迁移到运行门禁.md)。浏览器 adapter 不能替代 WPS 真机。

**转场**

> 但是，仅仅在 Prompt 里告诉模型“请遵守规则”，并不总是有效。

**编排标签**：核心；技术细节保持在协议层，不讲类名。

### 19｜Prompt 反复失效，就把规则下沉

**本页唯一判断**

需要稳定执行的规则，应进入 schema、规范化和 executor，而不是只留在提示词里。

**屏幕文字**

```text
Prompt：请批量操作
        ↓ 仍逐个调用
Schema：参数直接接受数组
```

**完整口播**

项目曾经在 Prompt 里明确要求模型批量处理段落。模型理解这句话，也可能在回答里说自己会批量，但实际调用时仍逐段执行。

这类问题很容易诱发“把 Prompt 写得更严厉一点”。可如果一条规则稳定、重复、可以由代码表达，它就不应该继续依赖模型自觉。

最终做法是让工具参数直接接受索引数组，在规范化和执行层完成批量循环。模型只需要表达“这些对象一起处理”，接口本身提供这种能力。

我很喜欢这个例子，因为它提醒我们：提示词是意图层，不是强制层。真正重要的规则应尽量下沉到机器可检查的结构里。

**画面占位**

- **[项目图片]** Learnings 中“Prompt 已要求批量仍逐段调用”的裁切。
- **[示意图]** Prompt → Schema → Executor 三层，规则逐层变硬。

**证据与边界**

证据见 [`evidence/W02-WPS从提示约束到工具约束.md`](evidence/W02-WPS从提示约束到工具约束.md)。历史记录中的调用数量不作为现场夸张数字。

**转场**

> 规则下沉以后，测试容易了。但 WPS 真实宿主仍然保留最后一票。

**编排标签**：核心；非常适合迁移到公司内部 Agent。

### 20｜同一协议，两种 adapter，两种证据

**本页唯一判断**

模拟环境与真实宿主承担不同验证责任，不能互相替代。

**屏幕文字**

| Browser Adapter | WPS Adapter |
|---|---|
| 协议、参数、状态 | 对象模型、兼容、真机画面 |

**完整口播**

WPS 环境不适合每改一行都做完整真机回归，所以项目建立了两类 adapter。

Browser Adapter 在普通浏览器或测试里模拟文档状态，用来验证工具参数、索引、批量操作和 Agent Loop。它快、可重复，很适合阻止低级回归。

WPS Adapter 连接真实 Word、Excel 和 PPT 对象。它负责回答 mock 无法回答的问题：对象模型是否真的这样工作、宿主是否兼容、最终画面是否正确。

这不是“先自动测试，最后随便点一下”。两种证据回答的是不同问题。Browser 全绿只说明协议层有把握；真机画面也不能证明所有边界都有自动回归。

**画面占位**

- **[示意图]** 同一 Tool/AgentLoop 向下分叉到 Browser 与 WPS，两边列出证明范围。
- **[项目图片]** WPS 历史截图作为右侧背景。

**证据与边界**

历史截图证明 2026 年 5 月当时的客户端画面，不证明当前版本门禁。见 [`evidence/W05-WPS历史真机截图.md`](evidence/W05-WPS历史真机截图.md)。

**转场**

> 真实宿主还有一个重要作用：它会否定那些“相邻生态里看起来合理”的经验。

**编排标签**：核心；若时间紧可与第 18 页合并。

### 21｜相邻经验只是候选，不是 WPS 事实

**本页唯一判断**

VBA、Office 或其他库的相似 API 只能生成假设，必须由目标宿主验证。

**屏幕文字**

> 相似对象模型 → 候选假设  
> WPS 运行结果 → 保留 / 修改 / 放弃

**完整口播**

在资料稀疏的环境里，AI 很自然会借用相邻生态的经验。Word、Office、VBA 和 WPS 的概念看起来相近，很多调用也长得相似。

这种知识非常有用，因为它能快速提出一个实现候选。但它不能直接升级为 WPS 事实。

项目里有段落插入和 PPT 图表路线：从相邻经验看都很合理，进入真实宿主后却没有产生预期对象或数据绑定。最后一个被修正，一个被明确放弃。

优秀调研不是永远找到支持原方案的资料，而是允许运行证据否定计划，并把否定原因留下来。

**画面占位**

- **[示意图]** 假设进入 WPS 后分成“保留 / 修改 / 放弃”。
- **[项目图片]** Phase 07 “已放弃”文档裁切。

**证据与边界**

失败路线见 [`evidence/W03-WPS保存失败路线.md`](evidence/W03-WPS保存失败路线.md)。缺少原始真机错误截图时，不重建伪终端或伪 UI。

**转场**

> 被否定的方案如果只留在聊天里，下一个 Agent 还会重新尝试。

**编排标签**：核心；把“失败也是产物”带入长期记忆。

### 22｜把失败写进项目，下一次才不用重来

**本页唯一判断**

高价值项目记忆应包含失败路线和启动约束，而不只记录最终答案。

**屏幕文字**

> Learnings / AGENTS.md  
> 下一个 Agent 的起跑线

**完整口播**

如果一条失败路线只存在于聊天记录，它几乎等于没有发生过。换一个会话、换一个人或换一个模型，项目很容易重新搜索、重新实现，再次撞到同一个宿主边界。

WPS 项目把对象模型差异、Ribbon 需要同时修改的文件、类型陷阱和被放弃路线写进 Learnings 与项目规则。

这些文档不是通用教程。它们保存的是这个仓库特有的局部地图：在这里，哪条相邻经验已经被反证；新增一个功能必须经过哪些入口；哪些测试通过仍不能代表真机。

AI 的长期价值从这一步开始出现。不是每次回答更聪明，而是项目不再从同一个未知点重新开始。

**画面占位**

- **[项目图片]** Learnings 与项目规则的短裁切。
- **[示意图]** 第一次会话撞墙，第二次会话从规则处绕开。

**证据与边界**

项目规则会过时，不能只追加不审查。第五幕会讨论让更强模型反向检查 Skill 与规则。

**转场**

> 最后看一眼真实结果，但也要说清楚这张图能证明到哪里。

**编排标签**：核心；与第六幕长期记忆形成前后呼应。

### 23｜WPS 案例真正留下了什么

**本页唯一判断**

调研的产物是一套可复用工程结构，而不只是最终界面和链接清单。

**屏幕文字**

> Theme + Schema + Adapter + Tests + Learnings

**完整口播**

这一幕最后，我当然可以展示 WPS 真机中的多页生成画面。它很重要，因为它证明项目不只活在 Markdown 里。

但如果只展示成品，观众会以为价值是“AI 帮我做了一个插件”。真正值得带走的，是成品背后的结构：外部设计经验进入 Theme，内容组织进入 Schema，宿主差异进入 Adapter，稳定规则进入测试，失败路线进入 Learnings。

这些东西让项目以后可以继续演化，也让下一个 Agent 能知道哪些肩膀已经找过、哪些部分已经被翻译、哪些仍然需要真机确认。

所以“不重复造轮子”的高级版本，不是复制更多代码，而是复用更多经过验证的结构。

**画面占位**

- **[项目图片]** 一张最清晰的 WPS 历史真机截图。
- **[示意图]** 底部五个工程资产标签，避免展示代码量。

**证据与边界**

真机截图不能证明对象全部可编辑、当前版本兼容或内容事实正确。完整截图边界见 W05；当前门禁仍需目标 WPS 环境复验。

**转场**

> WPS 是从很多参考里拿零件。下一个项目再往前一步：连“比较标准”本身，也让 AI 帮我们搭出来。

**编排标签**：核心；第三幕收束。

## 第四幕：人给标准，AI 替我们扩大选择

### 24｜“找一个像 Excel 的库”不是需求

**本页唯一判断**

模糊选型必须先拆成会改变决策的差异。

**屏幕文字**

> 记录表格？  
> 还是电子表格？

**完整口播**

Web Excel 项目的原始需求很常见：Vue 3 里需要一个像 Excel 的复杂表格。

如果直接搜索，AI 会迅速列出一堆知名库，再按功能多少给出推荐。但“像 Excel”到底指什么？是业务记录表格，需要排序、筛选、列设置和行移动；还是电子表格，需要单元格、选区、公式和工作簿？

这两类产品都可以长得像 Excel，却解决不同问题。没有先做这个分叉，后面的候选越丰富，排行榜越误导。

所以选型的第一步不是列工具，而是问：哪些差异真的会让我们选不同方案？

**画面占位**

- **[示意图]** 一个“像 Excel”分叉为记录表格与电子表格，两边放一张真实项目截图。

**证据与边界**

需求拆解与实验见 [`33-新增案例-飞机建模与表格选型.md`](33-新增案例-飞机建模与表格选型.md) 和原项目 `IMPLEMENTATION-NOTES.md`。

**转场**

> 产品类型只是第一层，真正的筛选标准还来自公司的交付条件。

**编排标签**：核心；非技术听众也能理解的选型入口。

### 25｜人不必研究 14 个库，但要定义筛选条件

**本页唯一判断**

人负责指出哪些差异重要，AI 可以承担大规模候选调查。

**屏幕文字**

```text
免费边界 / Vue 3 / 排序筛选 / 行列移动
合并语义 / 性能 / 无构建 HTML / CDN
```

**完整口播**

项目把原始需求拆成了一组可判断条件：核心功能不能付费解锁；能集成 Vue 3；需要排序、筛选、列设置、行列移动；合并到底是固定区域还是用户选区；演示最好无需 npm 构建；CDN 在当前环境要能访问。

AI 根据这些条件调查了 14 个方案。人不需要亲自完整阅读 14 套文档，但要负责告诉 AI：许可证是硬门槛还是偏好；选区合并是不是核心流程；数据规模尚未确定时，不能凭空拿某个最大行数淘汰候选。

这就是我理解的“把选择交给 AI”的边界。人不是逐项做功课，而是设计评分的含义；AI 负责把大量候选放进同一张可比较的桌面。

**画面占位**

- **[项目图片]** 候选研究表，只显示条件列和保留/排除理由。
- **[示意图]** 人写筛选器，AI 把 14 张卡片通过筛选器。

**证据与边界**

候选数量绑定当次项目。最终建议只适用于 2026-09-12 的版本和需求基线，不作为永久排名。

**转场**

> 但筛选表还有一个陷阱：很多产品使用同一个词，实际语义却完全不同。

**编排标签**：核心。

### 26｜功能名称相同，不代表用户任务相同

**本页唯一判断**

选型应比较任务语义，而不是比较营销词数量。

**屏幕文字**

> “支持合并”  
> 固定区域 / 行跨度 / 用户选区

**完整口播**

候选文档都可能写着“支持合并单元格”，但这个词可以指完全不同的行为。

有的库允许预先配置一个固定区域；有的主要提供纵向行跨度；有的允许用户在页面里选择任意单元格后合并。对产品经理来说，它们不是三个实现细节，而是三种不同用户任务。

同样，“支持 Vue”可能是原生 Vue 组件，也可能只是能在 Vue 页面里挂载；“大数据”可能是官方虚拟渲染机制，也可能只是一次装载了一万行。

AI 很适合批量提取这些差异，但输出字段必须从业务动作出发。否则我们得到的是一个功能词频表，不是选型依据。

**画面占位**

- **[示意图]** 同一个“合并”标签下展示三种不同操作动画帧。
- **[项目图片]** Jspreadsheet 用户选区合并区域裁切。

**证据与边界**

具体库能力应绑定当次版本和官方 API。截图只展示外观，功能状态需回到浏览器结果和实例断言。

**转场**

> 文档筛完以后，六个候选进入同一套实验，而不是继续写更长的比较表。

**编排标签**：核心；产品与开发共通页。

### 27｜让六个候选完成同一个任务

**本页唯一判断**

同数据、同任务实验比功能清单更能暴露方案差异。

**屏幕文字**

> 6 个独立 HTML  
> 同数据、同操作、各自原生能力

**完整口播**

经过资料筛选后，项目没有直接宣布赢家，而是为六个候选生成了独立 HTML。

每页使用同一批合成订单数据和相近操作：切换数据规模、排序、筛选、移动、显隐和候选支持的合并。统一任务让差异变得可见，同时又不强迫所有库伪装成同一类产品。

这一步把调研从“文档说它能做”推进到“在当前版本、当前资源形态和当前浏览器里，它怎样完成我们的动作”。

更重要的是，实验本身可以留下。以后需求变化时，不必重新阅读整套生态，可以在同一基线上追加一个问题。

**画面占位**

- **[项目图片]** 选型实验室索引页裁切，六个 Demo 卡片同屏。
- **[项目图片]** 两个代表页面并排，不显示全部六张小缩略图。

**证据与边界**

统一任务不代表原生能力完全相同；部分顶部操作由演示适配逻辑提供。必须在讲稿中区分库原生能力与实验层适配。

**转场**

> 接下来发生了一个很典型的误判：资源请求成功，但资源根本不能按我们预期运行。

**编排标签**：核心；视觉素材丰富。

### 28｜HTTP 200：我拿到了东西，但不一定拿对了

**本页唯一判断**

获取成功、格式可用和真实运行是三道不同门。

**屏幕文字**

```text
200 OK
  ≠ 完整浏览器包
  ≠ 页面可运行
```

**完整口播**

项目先检查固定版本 CDN 地址，记录状态、内容类型、体积和耗时。有一个名为 `min.js` 的文件返回了 HTTP 200，看起来已经解决。

打开内容后才发现，它只是一个单独的 CommonJS 函数，并不是页面需要的完整浏览器构建。

这个细节很适合说明证据层级。搜索结果给我们 URL；HTTP 200 证明服务器返回了内容；检查产物格式回答它是不是目标包；真实浏览器再回答脚本和 CSS 能不能一起运行。

每一层都不是多余测试，而是在排除不同的错误解释。

**画面占位**

- **[示意图]** 四道闸门：元数据、存在、格式、运行；200 只通过第二道。
- **[项目图片]** CDN 检查记录局部，隐藏冗长 URL。

**证据与边界**

当次网络验证只发生在一台 macOS 机器，不代表全国运营商或生产网络。项目建议生产考虑自托管。

**转场**

> 页面运行以后，下一种假成功来自按钮：点了、没报错，但结果不对。

**编排标签**：核心；“动作成功不等于目标达成”的第一例。

### 29｜按钮没报错，不代表业务状态正确

**本页唯一判断**

交互验收应检查目标状态，而不是只检查动作是否执行。

**屏幕文字**

> 点击成功 ≠ 移动正确  
> 查询最终状态

**完整口播**

表格实验里有一个行移动操作。调用没有报错，页面也发生了变化，但目标记录最后所在的位置与初始假设不同。

如果测试只检查按钮被点击、函数没有抛异常，系统会把它判定为成功。后来项目改成读取真实实例状态，直接断言那个订单最后应该出现在第几行，并补充真实鼠标拖动。

这类问题不限于表格。AI 很容易把“工具调用返回成功”写成“用户目标已完成”。更可靠的验收要问：目标对象的状态发生了什么？业务不变量是否成立？

动作只是过程，状态才接近结果。

**画面占位**

- **[示意图]** 一个按钮绿勾，旁边最终行顺序红框。
- **[项目图片]** 实例状态 JSON 的短裁切，不展示整份日志。

**证据与边界**

项目并未逐一自动验证所有库的全部原生鼠标路径。讲述应限定为已保存的实例状态与部分交互结果。

**转场**

> 状态断言仍看不见遮挡和滚动条，所以还需要另一种证据：截图。

**编排标签**：核心；第二个“假成功”例子。

### 30｜自动断言和截图，谁也替代不了谁

**本页唯一判断**

功能状态与视觉状态需要不同的观察方式。

**屏幕文字**

| 状态断言 | 截图观察 |
|---|---|
| 行序、合并、筛选 | 遮挡、溢出、滚动区 |

**完整口播**

浏览器脚本可以查询排序结果、合并区域和列顺序，却不容易判断页面是否拥挤、滚动条是否被挤掉、移动端是否出现遮挡。

截图可以看见这些问题，但一张截图又不能证明筛选真的正确，也不能证明拖动行为持续可用。

Web Excel 项目把两种证据并列：实例状态负责功能不变量，截图负责外观和布局。后来正是目视宽表截图，发现某个滚动区域高度不合适，再回到页面修正。

这也是第五幕会进一步展开的 Codex 闭环：不是测试越多越好，而是失败发生在哪一种媒介，就用能观察那个媒介的反馈。

**画面占位**

- **[项目图片]** 左侧结果 JSON，右侧宽表截图，各圈出一个问题。
- **[示意图]** 中间写“互补，不是替代”。

**证据与边界**

宽表滚动条当时属于目视复核，没有记录真实鼠标滚动断言；不能在台上升级为自动验收。

**转场**

> 那么，AI 最后给出了哪个“最佳库”？答案是：没有脱离条件的最佳库。

**编排标签**：核心；提前铺垫第五幕反馈通道。

### 31｜结论不是排行榜，而是一组条件句

**本页唯一判断**

好的选型结论应绑定需求和证据边界，而不是宣布通用冠军。

**屏幕文字**

> 如果是业务记录表格……  
> 如果需要单元格与选区……  
> 如果目标是完整工作簿……

**完整口播**

这个项目最终没有做一张“第一名到第十四名”的榜单。

它给出的是条件性建议：如果主要是 Vue 3 业务记录表格，优先看某类方案；如果核心是选区和单元格操作，进入另一类；如果需求已经变成完整电子表格工作区，就应单独评估更重的产品和部署方式。

后来用户问到 Univer 的体积，项目没有推翻原研究，而是针对依赖组合和 CDN 资源做了一个窄调查，并明确没有制作浏览器演示，所以只讨论文档和体积，不声称实际编辑流畅。

这就是 AI 可以替人完成很多选择后的正确收口：不是替我们拍板，而是把拍板需要的条件变得可见。

我还尝试过让 AI 搜 B站视频、下载音频、转文字再总结。它很适合快速了解大家在讨论什么、发现关键词，但通常先得到的是主流观点和候选线索，不是最终技术依据。

**画面占位**

- **[示意图]** 三条“如果……那么……”路线，不放冠军奖杯。
- **[可删示意]** 右下角一条很小的视频→文字→关键词链，配“候选材料”。

**证据与边界**

选型绑定当次需求、版本和单机实验。B站尝试的转写会误识别专名和数字，不作为关键结论的唯一依据，见 [`03-案例-视频转知识.md`](03-案例-视频转知识.md)。

**转场**

> 到这里，AI 已经替我们找资料、拆需求、筛候选、做实验。下一步更有意思：让它像一个工程师一样，面对失败继续行动。

**编排标签**：核心；B站只占最后一段，不单独开幕。

## 第五幕：Codex 怎样行动，以及怎样把这种能力搬回公司

### 32｜Codex 的优势，不只是“会写代码”

**本页唯一判断**

Codex 的可迁移价值来自完整工作环境，而不只是模型回答能力。

**屏幕文字**

```text
项目上下文 + 工具 + 现实反馈 + 隔离实验 + 长期记忆
```

**完整口播**

前面三个案例已经出现了很多 Codex 式的动作：读项目、找资料、写实验、开浏览器、看截图、保存文档。

如果只把这些归纳为“Codex 模型比较强”，我们就很难把经验带回公司。因为公司可能主要使用 Claude CLI，可能只有小模型，可能网络不稳定，也可能不能把内部资料交给外部服务。

所以这一幕不猜厂商内部怎么搜索，也不做品牌排名。我只拆解项目里能观察到的条件：它能进入工作区读取上下文；能操作终端和浏览器；能接收编译、测试和画面反馈；能在分支或 worktree 中试验；还能把结论写回项目。

真正可迁移的是这个环境。模型能力不够，就让环境、流程和反馈更明确。

**画面占位**

- **[示意图]** 五个环形模块围绕 Agent：上下文、工具、反馈、隔离、记忆。

**证据与边界**

能力提炼来自多个本地项目复盘，见 [`evidence/C01-Codex项目复盘交叉提炼.md`](evidence/C01-Codex项目复盘交叉提炼.md)。不能由这些案例推出 Codex 普遍优于其他模型。

**转场**

> 先看一个完整闭环：AI 生成的 Deck.gl 页面能打开，但就是不按预期工作。

**编排标签**：核心；第五幕导航。

### 33｜Deck.gl：页面能开，但目标行为没发生

**本页唯一判断**

“没有报错”和“页面可见”不能替代对目标行为的验收。

**屏幕文字**

> HTML 已生成  
> 页面已打开  
> 目标动画：没有成立

**完整口播**

Deck.gl 项目的目标是让地图图标持续旋转，同时保持可拾取、减少不必要的 CPU 工作，并避免每帧重建无关图层。

早期 HTML 看起来很完整，页面也能打开，但目标对象没有按预期运动。

如果把任务理解成“写一个 HTML”，模型已经完成了。如果把任务理解成“在指定版本和约束下实现可验证的持续动画”，它才刚刚暴露第一个信息缺口。

这就是 Codex 闭环的起点：完成标准不由输出文件存在决定，而由目标行为和约束决定。

**画面占位**

- **[项目图片]** Deck.gl 对照实验静态截图，标题明确“单帧不能证明旋转”。
- **[示意图]** 文件完成绿勾与目标行为红问号并列。

**证据与边界**

当前保存的基线截图是后来建立的诊断页，不是最早失败 HTML 的原始截图。不能伪装成历史现场。案例见 [`17-案例-Deckgl从失败到证据链.md`](17-案例-Deckgl从失败到证据链.md)。

**转场**

> 第一个真正重要的动作，不是再生成一版，而是把“它不转”拆成可以被证据回答的问题。

**编排标签**：核心；技术锚点开始。

### 34｜症状不是查询，症状要先被重写

**本页唯一判断**

宽泛失败应拆成对象、数据、生命周期、版本和验收问题。

**屏幕文字**

```text
对象边界 / 数据语义 / 生命周期 / 版本接口 / 非功能验收
```

**完整口播**

“图标不转”本身不是一个高质量搜索问题。

它可能意味着：我们操作错了对象层；传入数据的单位或语义不对；状态更新没有触发正确生命周期；当前版本接口与网上示例不同；或者动画其实发生了，只是验收方式看不出来。

Codex 在这里最有价值的不是立即选一个答案，而是同时保留多个解释，并把每个解释变成可以查证的问题。

这和 B747 的低频代码、ECharts 的本地版本其实是同一个动作：把“我看见的症状”翻译成“我缺少哪一类事实”。新的问题表示，会决定下一步应该打开文档、源码还是浏览器。

**画面占位**

- **[示意图]** “不转”在中心，向外分成五类信息缺口。
- 动画逐条展开，不放具体 API 答案。

**证据与边界**

五类问题来自 Deck.gl 原始需求和复盘。具体字段和角度细节留在证据库，不进入主体。

**转场**

> 每一种问题都有更合适的来源。搜索引擎不是唯一入口。

**编排标签**：核心；与第二幕查询重写形成呼应。

### 35｜代码、维护文档、线上文档、Issue、Commit，各回答什么

**本页唯一判断**

来源不是一条权威排行榜，而是不同事实的分工网络。

**屏幕文字**

| 想知道 | 先看 |
|---|---|
| 公开支持什么 | 官方线上文档 |
| 实际怎样实现 | 目标版本源码 |
| 哪些场景会失败 | Issue / PR |
| 为什么发生变化 | Commit / Changelog |
| 当前项目允许什么 | 本地依赖 / 运行结果 |

**完整口播**

这是全场最接近“方法表”的一页，但我建议把它理解成导航，而不是排名。

项目维护文档告诉你作者希望用户怎样接入；官方线上文档是公开契约；源码说明这个版本实际做了什么；Issue 暴露真实用户遇到的边界；PR 和 Commit Message 能帮助定位一次变化为什么发生；Changelog 告诉我们版本跨度；本地依赖和运行结果则回答当前项目究竟处在哪个世界。

Commit Message 很有用，但它只是历史索引。看到“fix timer lifecycle”并不能证明问题已经正确修复，还要打开 diff、测试和对应 Issue。Git 历史能重建变化顺序，不能还原完整思维。

Codex 看起来像“会搜索”，很大一部分原因是它会在这些来源之间切换，而不是把所有问题都丢给 Web Search。

**画面占位**

- **[示意图]** 左侧问题，右侧来源；避免画金字塔。
- **[项目图片]** 一条真实、无敏感信息的提交记录，点击后展开 diff/测试示意。

**证据与边界**

来源分工由 WPS、Deck.gl、Dice 和 Tabloom 共同支持。不能由这些外部动作推断任何厂商未公开的检索实现，也不能仅凭提交标题证明作者意图。

**转场**

> Deck.gl 里，文档确认了公开契约，但真正决定版本行为的是目标版本源码。

**编排标签**：核心；也可拆为主体简表 + 附录详表。

### 36｜当前文档不能替代目标版本源码

**本页唯一判断**

版本化工程问题需要绑定目标版本的一手实现。

**屏幕文字**

> 今天的文档  
> 不一定能解释昨天安装的版本

**完整口播**

Deck.gl 的公开文档先帮助确认 API 语义和生命周期。但为了排除版本差异，项目继续查看目标版本源码。

源码不是为了炫耀“AI 会读代码”。它回答的是一个非常具体的问题：这个版本内部到底如何处理输入，官方自己的相邻扩展又怎样使用同一套接口。

后来的运行错误尤其说明这一点。一个旧式写法静态看起来合理，在当前版本的真实 WebGL 环境里却链接失败。此时最有价值的参考不是一篇多年以前的教程，而是同版本官方仓库里已经工作的相邻实现。

ECharts 的本地依赖、Deck.gl 的目标 tag、WPS 的真实宿主，都是同一原则：让证据与项目版本对齐。

**画面占位**

- **[示意图]** 当前网页文档与目标 tag 两条时间线对齐。
- **[项目图片]** 目标版本源码的极短裁切，只圈出版本和关键转换，不要求观众读代码。

**证据与边界**

具体 API 语法留在复盘。源码能确认实现，不代表依赖内部 API 就是最佳生产方案。

**转场**

> 但源码阅读仍然只是静态证据。真正把错误暴露出来的是浏览器。

**编排标签**：核心；适合技术听众，非技术场可缩短口播。

### 37｜错误发生以后，搜索词终于变准了

**本页唯一判断**

运行时错误可以把宽泛问题压缩成目标版本的具体边界。

**屏幕文字**

> 泛化问题：怎样做 GPU 动画？  
> 精确问题：这个版本的官方扩展如何声明同类输入？

**完整口播**

GPU 路线第一次进入浏览器时发生了链接错误。

如果没有真实运行，静态代码和结构测试可能会把它当成完成。错误出现以后，问题突然变得精确：不是“怎样写 shader 动画”，而是“Deck.gl 当前版本的 shader module 怎样声明和传递这一类参数”。

项目随后查看同版本官方扩展源码，按照当前范式修正，再回到浏览器运行。

这就是我很想迁移给小模型的一种工作纪律：保存原始错误；标记它发生在哪一层；加上目标版本和预期不变量；然后再搜索。不要让 Agent 在同一个宽泛症状上连续改五版代码。

**画面占位**

- **[示意图]** 一条宽搜索框被错误文本、版本和发生层逐步收窄。
- **[待补证]** 原始错误日志未保存，不制作伪终端截图。

**证据与边界**

错误到查询的转折可从原复盘重建，但初版控制台原始日志缺失。只展示重画流程和当前源码证据。

**转场**

> 修好以后，还要证明它真的在持续变化，而且变化来自正确对象。

**编排标签**：核心；第五幕的研究转折。

### 38｜截图为什么不能证明旋转

**本页唯一判断**

验证媒介必须能够观察目标行为的时间维度和对象边界。

**屏幕文字**

> 一张截图只能证明一帧。

**完整口播**

Deck.gl 动画有一个很直观的验收陷阱：截图可以证明画面里有一个图标，却不能证明它持续旋转。

所以项目设计了几条互补信号。采样图标附近的像素随时间是否变化；在同一位置能否拾取到目标 Deck.gl 对象；无关静态图层是否只初始化一次；暂停后状态是否真的停止；控制台有没有错误。

没有哪一条单独证明全部目标。像素变化可能来自别的动画；picking 只能证明对象存在；帧数也不能证明方向和语义正确。多个信号组合，才足以支持当前实验的结论。

这不是要所有项目都做复杂的自动视觉检测，而是提醒我们：验收方式必须能看见我们声称发生的事情。

**画面占位**

- **[项目图片]** 一张运行截图，旁边是像素变化、picking、初始化次数和暂停状态四个小指标。
- **[示意图]** “截图 = t₀；动画 = t₀…tₙ”。

**证据与边界**

运行发生在短时间、本地浏览器和指定版本，不是性能基准。验证器也可能误报，项目曾识别与核心行为无关的噪声。

**转场**

> 现在把 Deck.gl 放回更大的闭环：写代码之后，AI 还会接收哪些现实反馈？

**编排标签**：核心；视觉解释优先，不展示指标细节表。

### 39｜编译、lint、测试、运行、截图不是重复劳动

**本页唯一判断**

不同反馈通道会暴露不同层次的错误。

**屏幕文字**

```text
代码 → 编译/类型 → lint → 测试 → 运行时 → 截图/观察
                                      ↘ 新的信息缺口
```

**完整口播**

Codex 的闭环大致是这样：写代码，接收编译或类型错误，运行 lint 和测试，打开浏览器，看控制台和真实状态，再通过截图或录屏观察视觉结果。

它们看起来都在“检查”，其实负责的层次不同。编译能发现类型和语法；lint 能发现一类静态问题；测试验证我们写下的不变量；浏览器暴露资源、生命周期和真实交互；截图发现遮挡、比例和审美。

ECharts 没有类型反馈，所以错误字段能安静存在。Web Excel 的状态断言能发现行顺序，截图能发现滚动区域。飞机建模的构建通过后，仍在浏览器里发现贴图和货舱开口问题。

失败信号不是“AI 没做好”的结束语，而是下一轮应该去找什么资料的输入。

**画面占位**

- **[示意图]** 横向反馈链，每个节点下只放一个真实案例图标。
- 可用红色箭头从错误回到“查资料/改实现”。

**证据与边界**

测试和验证器本身也可能错，不能把“全绿”当作绝对真相。失败媒介与证据媒介匹配的主张由多个项目支持。

**转场**

> 这一整套反馈很耗 token。然后我发现了一项零 token 的技术。

**编排标签**：核心；跨案例闭环总图。

### 40｜惊奇发现：自己的脑子不烧 token

**本页唯一判断**

调研自动化仍有成本，优化目标应是把成本花在能改变判断的反馈上。

**屏幕文字**

> 用自己的脑子写代码，不烧 token。免费的。

**完整口播**

后来我惊奇地发现：用自己的脑子写代码，不烧 token。免费的。

当然，免费的脑子也会忘、会猜、会跳过测试。这个笑话不是要得出“还是人写最便宜”，而是提醒我们：让 AI 读完整源码、跑浏览器、看截图、修测试，会消耗真实的时间和额度。

成本并没有因为自动化消失。真正值得优化的不是每次都用最少 token，而是把 token 花在会改变决策、暴露错误和留下复用资产的地方。

让模型连续生成五个相似方案可能很便宜，却没有增加证据；让它跑一次真实浏览器可能更贵，却能结束整个错误方向。

**画面占位**

- **[示意图]** 一侧“连续生成 ×5”，另一侧“运行一次 → 暴露真实错误”。
- 笑话大字出现后快速转入成本判断。

**证据与边界**

这是修辞，不做具体 token 效率数字。不同模型、工具和任务的成本无法由这些案例统一量化。

**转场**

> 除了 Deck.gl，其他项目还展示了 Codex 的哪些行动习惯？

**编排标签**：可删；适合后半场恢复注意力。

### 41｜三个短例：建模、Dice、Tabloom

**本页唯一判断**

Codex 的行动方式可以跨越资料、资产、产品反馈和长期任务。

**屏幕文字**

| 项目 | 可观察能力 |
|---|---|
| 飞机建模 | 资料 → 参数化资产 → 视觉复查 |
| Dice | 高风险切片 → 负知识 → 交接 |
| Tabloom | 反馈 → 新信息缺口 → 再取证 |

**完整口播**

Deck.gl 是完整闭环，另外三个项目各补充一个能力。

飞机建模把航空公司和制造商资料转换成参数化 Blender 脚本、GLB 和可编辑工程；MCP 连不上时改用本机 CLI，构建以后仍通过渲染和浏览器找视觉问题。

Dice 先用一个真实角色做最高风险纵向切片，验证来源、许可证、加载、骨骼、动画和体积，再扩展四个角色；每次复盘还明确保存“不要重复研究”和“下次优先验证”。

Tabloom 则说明调研不是开发前的一次动作。用户反馈、平台错误和真实模型空结果都会产生新的信息缺口，项目再回到文档、源码、Git 或边界实验。

它们不是三个新项目介绍，而是同一个 Agent 工作方式在不同媒介里的表现。

**画面占位**

- **[项目图片]** 飞机渲染、Dice 三栏状态、Tabloom 循环各占三分之一。
- 每块只显示一个动作箭头，不列技术栈。

**证据与边界**

原始复盘已重新回读，交叉矩阵见 C01。飞机渲染不证明工程精度；Dice 复盘不是完整实时日志；Tabloom 单次模型输出不能外推长期行为。

**转场**

> 这些项目还有一个共同的工程设施：它们不会把所有实验直接堆在同一个工作目录里。

**编排标签**：核心或可删；案例图片丰富，适合混合听众。

### 42｜Commit Message 和 worktree 到底帮了什么

**本页唯一判断**

Git 历史和隔离工作区让 Agent 的试验可比较、可回退、可审查。

**屏幕文字**

```text
main：可运行基线
worktree A：视觉重制
worktree B：新资产管线
小提交：每次变化的检查点
```

**完整口播**

worktree 听起来像一个 Git 技巧，但它在 Agent 工作流里的价值非常直白：同一个仓库可以拥有多个独立目录，每个任务从明确基线开始，不必把未完成修改混在一起。

Dice 的视觉重制、资产管线和新功能都留下了独立分支与小提交。这样可以比较前后、逐项回退，也可以让审查者只看一个范围。

Commit Message 则像历史目录。它能帮助下一位 Agent快速定位“哪一次在修座椅”“哪一次在处理 timer”。但提交标题不是事实终点；还要打开 diff、测试和复盘，确认改了什么、为什么以及是否验证。

对公司里的轻量 CLI Agent，可以把创建分支、运行门禁和生成交接报告写成固定流程。隔离降低风险，但不会自动消除冲突和错误。

**画面占位**

- **[示意图]** 一个仓库分出两个 worktree 目录，各自有三枚提交节点。
- **[项目图片]** 一段真实 `git log --oneline`，选择无敏感信息的 Dice 或本项目提交。

**证据与边界**

Git 历史不是完整 reasoning；worktree 不替代测试、审查和合并处理。证据见 Dice 三份复盘与 C01。

**转场**

> 现在回到公司的现实：如果没有完整 Codex 环境，怎样让小模型做出相似动作？

**编排标签**：A 级可删页；技术听众适合保留。

### 43｜把 Codex 的工作环境拆给小模型

**本页唯一判断**

小模型可以通过明确的来源顺序、工具脚本和反馈门禁复刻部分 Agent 能力。

**屏幕文字**

| 强模型 | 小模型 / 轻量 CLI |
|---|---|
| 目标、现场、工具、验收 | 来源顺序、固定字段、脚本、检查表、停止条件 |

**完整口播**

公司只有 Claude CLI 或更小模型时，不需要复刻某个产品界面，可以先复刻工作条件。

把源码、依赖定义、内部文档和项目规则放进允许读取的目录；预先生成文件地图；为“平台问题、版本问题、运行问题”规定首选来源；把编译、lint、测试、启动服务和截图封装成明确命令；任务结束强制写出 Confirmed、Rejected、Unverified 和下一步。

强模型可以只给目标、现场、权限和验收，让它自行规划。小模型更容易偏航，就提供来源顺序、资料卡字段、失败后的降级路线和停止条件。

小模型不必拥有 Codex 全部能力。只要它不再把每次错误都当成重新生成的理由，已经能显著接近这套工作方式。

**画面占位**

- **[示意图]** Codex 五环环境被拆成公司内的文件目录、脚本、浏览器、Git 和 Markdown。
- **[示意图]** 强模型与小模型使用不同粗细的护栏。

**证据与边界**

这是从本地案例抽取的迁移建议，尚未在相同任务上做受控模型对比。公司内资料仍需遵守访问、脱敏和日志规则。

**转场**

> 那已经写好的 Skill 怎么办？强模型来了，还要不要继续教它每一步？

**编排标签**：核心；第五幕真正面向公司落地的一页。

### 44｜“不要教 GPT-6 做事”——可以当段子，不能当铁律

**本页唯一判断**

模型越强，越应减少微观指令；但项目事实、权限和验收永远不能省。

**屏幕文字**

> 不要教 GPT-6 做事。  
> 让 GPT-6 帮你审查：你以前教的那些事还对不对。

**完整口播**

最近有一种说法：不要教 GPT-6 做事。

我觉得它很适合当段子，也有一半很有道理。能力更强的模型确实不需要几十条微观步骤；过度规定每一个动作，可能让它无法根据现场调整。

但另一半也很重要。再强的模型也不知道公司内部旧事故，不知道哪些目录不能碰，不知道什么数据不能发出去，也不知道怎样才算业务验收。这些不是“教它思考”，而是提供项目事实和责任边界。

Skill 也不应该成为永恒真理。更好的做法是定期让更强模型反向审查：哪些规则已经过时，哪些只适合旧工具，哪些把一次事故过度推广成了永久禁令。

对小模型，清单仍然有价值；对强模型，保留目标、现场、工具、权限和验收，减少不必要的动作控制。

**画面占位**

- **[示意图]** 左侧一本很厚的旧 Skill，右侧强模型用“过时/组织特有/必须保留”三色批注。

**证据与边界**

“GPT-6”在此是面向未来强模型的修辞，不是对具体产品能力的实测结论。Skill 审查建议来自项目规则可能过时的风险，而非受控实验。

**转场**

> 当这些动作被写进项目，下一次任务就不再从空白上下文开始。这也把我们带到最后一幕：记忆。

**编排标签**：核心或可删；适合有 AI Agent 使用经验的听众。

## 第六幕：今天还要学，因为这种交互方式正在到来

### 45｜聊天会结束，项目不能失忆

**本页唯一判断**

跨会话能力来自外部项目记忆，而不是期待模型记住整段历史。

**屏幕文字**

```text
Confirmed   已确认
Rejected    已排除
Unverified  待验证
```

**完整口播**

AI 会话很容易给人一种错觉：它好像完整理解了项目。可一旦换会话、换模型、换同事，很多上下文都会消失。

Dice 项目最值得保留的不是游戏代码，而是三份复盘持续写下：哪些决策已经确认，哪些资产和路线已经比较并排除，哪些风险还没有验证，以及下一位 Agent 应该从哪里继续。

我建议最少保留三个区块：Confirmed、Rejected、Unverified。

只保存成功答案不够。Rejected 能防止重复消耗；Unverified 能防止猜测在多次转述后变成“大家都知道的事实”。这三栏比把整段聊天复制给下一位 Agent 更像一个可执行接口。

**画面占位**

- **[示意图]** 三栏状态板，每栏只放一个跨领域例子。
- **[项目图片]** Dice 复盘交接段落短裁切。

**证据与边界**

复盘可能包含事后重建，不能冒充完整实时日志。三栏状态只是最小结构，关键结论仍需来源和验收入口。见 [`18-案例-Dice调研记忆与任务交接.md`](18-案例-Dice调研记忆与任务交接.md)。

**转场**

> 记忆不只是保存答案，还要保存为什么、凭什么，以及下一步能做什么。

**编排标签**：核心；第六幕主要工具。

### 46｜一个最小的项目研究包

**本页唯一判断**

长期记忆应让下一位人或 Agent 能重建决定并继续行动。

**屏幕文字**

```text
目标与约束
来源与版本
已确认 / 已排除 / 待验证
验收与运行结果
下一步任务
```

**完整口播**

如果要把今天所有方法压成一个最小研究包，我会保存这些内容。

当前目标和硬约束，防止任务悄悄变形；来源、版本和访问日期，保证结论能回查；已确认、已排除和待验证，保存研究状态；验收方法和真实运行结果，解释为什么可以暂时行动；最后是一条下一位 Agent 可以直接执行的任务。

它不需要是复杂知识库。几个 Markdown、测试、脚本和 Git 提交已经足够有用。关键是它们位于项目里，会被下一次任务读取，而不是散落在聊天、收藏夹和个人脑子中。

结构化文档不是为了把一切写得更长，而是让高价值上下文不必每次重新购买。

**画面占位**

- **[示意图]** 项目目录逐个出现 `BRIEF / EVIDENCE / EXPERIMENTS / ACCEPTANCE / LEARNINGS`。
- **[项目图片]** 本研究仓库 README 导航的一小块，作为真实示例。

**证据与边界**

文件名称可以因团队而异，不建议把这五个名字变成新的形式主义。标准是下一位执行者能否理解边界、来源和下一步。

**转场**

> 当然，保存更多上下文也要付成本。于是我们有了今天最后一个双关。

**编排标签**：核心；可作为课后模板入口。

### 47｜AI has made memory more expensive

**本页唯一判断**

项目记忆需要存储和维护成本，但能避免更昂贵的重复调查。

**屏幕文字**

> AI has made memory more expensive.  
> 爱让记忆变得更加珍贵。AI 让存储变得更加昂贵。

**完整口播**

今天学到一句翻译：AI has made memory more expensive。

爱让记忆变得更加珍贵——AI 让存储变得更加昂贵。

这是一个故意的双关。现在上下文、向量库、文档读取和长期记忆都要成本；资料越多，如果没有结构，也会让 Agent 在噪声里消耗更多 token。

所以长期记忆不是把所有东西都塞进去。它应该优先保存那些会改变未来决策的内容：来源、版本、失败路线、验收和未知。

记忆确实更贵了。但如果它能让下一次任务跳过已经失败的路线，直接从当前证据继续，它也真的变得更珍贵。

**画面占位**

- **[示意图]** 左侧不断膨胀的聊天记录，右侧少量结构化项目文件。
- 英文句子与双关翻译大字呈现，其他内容淡化。

**证据与边界**

这是语言游戏，不涉及具体硬件、API 或 token 价格比较。不要加入未经核验的成本数字。

**转场**

> 即使没有 AI，这套做法也并不陌生。它只是把优秀工程师的动作扩展了。

**编排标签**：核心或可删；推荐保留作结尾回响。

### 48｜没有 AI 时，也可以照着做

**本页唯一判断**

AI 改变了调查成本和范围，没有改变工程事实成立的方式。

**屏幕文字**

> 信息觅食 / 假设调试 / 源码考古  
> 最小复现 / 测试反馈 / 决策记录

**完整口播**

如果把 AI 从今天所有案例里拿掉，这套方法仍然成立。

优秀工程师本来就会先问清需求，会查官方文档和源码，会从错误里生成假设，会做最小复现，会记录为什么选这个方案，也会告诉接手的人哪些路不要再走。

AI 改变的是成本和规模。它能同时展开更多查询，批量读更多候选，快速建立实验，整理跨文件证据，并把文档变成下一次输入。

所以我们真正要学习的不是依赖某个模型记住答案，而是把这些传统动作显式化、可操作化，让 Agent 也能执行，并让人仍然看得懂它为什么这样做。

**画面占位**

- **[示意图]** 左侧传统工程动作，右侧 AI 扩大并加速，中间“证据标准不变”。

**证据与边界**

不声称 AI 必然提高所有团队效率；本演讲没有统一时间对照实验。价值主要由真实案例和可追踪产物说明。

**转场**

> 既然工具还在快速变化，我们今天到底要不要花时间学这些？

**编排标签**：可删；适合防止演讲变成产品宣传。

### 49｜学得慢不用太焦虑，今天的需求还是得做

**本页唯一判断**

工具会继续自动化，但当前工作仍需要人学会组织现场、工具和验收。

**屏幕文字**

> 几个月后，也许工具自己补上了。  
> 但是今天，需求还在排期里。

**完整口播**

我越来越觉得，这就是未来使用软件的一种方式：我们不再亲自点完所有步骤，而是告诉 Agent 目标、现场和验收，让它自己找资料、操作工具、观察结果，再回来报告。

学得慢也不用太焦虑。也许几个月后，今天这些麻烦的工具连接、浏览器截图和长期记忆，产品自己就补上了。

但是今天需求还在排期里，所以我们还是得学。

我们要学的不是某个按钮，也不是背某个模型的 Prompt。要学的是怎样描述只有我们知道的项目现场，怎样给 Agent 接上现实反馈，以及怎样判断它找到的证据是否足以行动。

等工具真的变简单以后，这些能力也不会浪费。因为它们本来就是把事情做可靠的方法。

**画面占位**

- **[示意图]** 今天的人手动连接文档、终端、浏览器、Git；未来这些能力收进统一 Agent 工作区。
- 页脚注明“趋势判断，非时间预测”。

**证据与边界**

“几个月后”是讲者幽默和主观预期，不是产品发布时间或行业预测。不能在对外材料中改成确定承诺。

**转场**

> 最后，我不想用一个工具名字结束，而想回到项目本身。

**编排标签**：可删；经验分享气质较强。

### 50｜真正产生复利的，是项目记住了为什么

**本页唯一判断**

AI 调研的最终价值，是让项目以后不必从同一个未知重新开始。

**屏幕文字**

> 真正产生复利的，不是一次回答。  
> 是项目从此记住自己为什么这样做。

**完整口播**

我们最容易高估的是一次回答，最容易低估的是项目记忆。

一个答案今天看起来很完整，几周以后我们可能已经不知道它对应哪个版本，为什么排除了另一个方案，也不知道当时还有什么没有验证。

所以我现在更看重的产物，不只是代码，而是项目能不能留下：查过哪些来源，确认了什么，否定了什么，最后怎样验收，以及下一位 Agent 从哪里继续。

AI 可以替我们搜索、阅读、比较、试验和记录。人把项目的过去、现在和未来告诉它，并对最终行动负责。

真正产生复利的，不是一次回答，而是项目从此记住自己为什么这样做。

**画面占位**

- **[示意图]** B747、WPS、Web Excel、Deck.gl 四个案例最终都汇入一个项目目录；下一位 Agent 从目录继续向前。
- 最后一屏只保留核心句，停顿后结束。

**证据与边界**

这是全场价值判断，不声称自动化能够替代组织责任。开场和其他结尾候选见 [`39-开场与结尾候选.md`](39-开场与结尾候选.md)。

**转场**

> 谢谢。问题和案例细节可以在附录与项目资料中继续展开。

**编排标签**：核心；默认结尾。
