# 案例：Tabloom 的信息搜集与决策轨迹

## 1. 为什么纳入

Tabloom 是一个整理 Chrome 当前窗口标签页的侧边栏扩展。产品本身不是本次演讲的重点；它的研究价值在于，同一个项目留下了从可行性、原型、设计、实施、缺陷定位、真实模型实验到发布审计的连续记录，可以观察 AI Agent 在开发过程中如何反复提出信息缺口、选择证据、修正判断并把结论固化为代码、测试与文档。

它补充了现有案例没有完整覆盖的一层：

| 现有案例 | 主要回答的问题 |
|---|---|
| WPS | 如何从多个外部项目中筛选并迁移局部资产 |
| 视频 | 如何把不可搜索媒介转成可检索、可回链语料 |
| Deck.gl | 一个实现问题如何沿文档、同版本源码和实验收敛 |
| Dice | 如何保存负知识和跨会话任务状态 |
| Tabloom | 技术调研如何贯穿原型、实现、调试、模型实验和发布，而非只发生在编码前 |

因此 Tabloom 不宜作为“AI 又写了一个插件”的第四段产品演示；它更适合作为方法论的元案例或贯穿案例。

## 3. 这个案例提出的调研模型

### 3.1 从“主题搜索”改为“信息缺口”

“如何开发 AI 标签分组插件”太宽，无法直接指导检索。项目逐步把它改写成可被证据回答的问题：

- Chrome 是否允许扩展读取和修改原生标签组？
- Side Panel 需要什么 Manifest 与最低浏览器版本？
- 零标签组会不会被 Chrome 自动删除？
- module Service Worker 能否使用动态 `import()`？
- API Key 是未保存，还是只在界面上没有回填？
- 非 Thinking 不分组发生在请求、流式传输、解析、结构校验还是模型输出？
- 本地提交与 GitHub 远端是否真的一致？

这些问题共同说明：搜索词应由“当前决策还缺什么信息”产生，而不是由项目名称产生。

### 3.2 信息源不是一条排行榜，而是一套路由

原项目使用以下来源分类：

| 标记 | 来源 | 能回答什么 |
|---|---|---|
| `U` | 用户输入 | 目标、偏好、错误现场、可接受取舍和真实试用反馈 |
| `K` | 模型通用知识 | 架构候选、调试假设、可尝试的工程模式 |
| `D-doc` | 官方文档 | API、权限、版本、枚举与明确平台限制 |
| `D-code` | 源码、测试、Manifest、README | 当前实现、数据流、不变量和静态边界 |
| `D-runtime` | 错误、测试、真实 Chrome/API 输出 | 当前环境实际发生了什么 |
| `D-git` | 提交、身份、remote、远端引用 | 变更顺序、发布内容和本地/远端一致性 |
| `S` | Skill 与项目规则 | 计划、测试、验证、安全和授权纪律 |

`K` 只是保守的来源归因：表示无需本项目专属资料即可提出的候选方案，并不声称能够观测模型内部记忆。

更适合演示的简化版是：

| 问题 | 首选证据 |
|---|---|
| 平台“允许什么” | 当前官方文档 |
| 项目“现在怎么做” | 源码、配置、测试 |
| 为什么发生变化 | 用户反馈、ADR、计划与 Git |
| 真实边界“到底返回什么” | 固定输入的最小运行实验 |
| 是否满足业务目标 | 用户验收与业务级 evaluator |
| 哪些动作不能跳过 | Skill、自动门禁和审批规则 |

### 3.3 调研与开发是往返循环

Tabloom 的真实形态不是：

```text
调研完成 → 设计 → 实现 → 结束
```

而是：

```text
提出候选
→ 原型或实现
→ 用户反馈 / 错误 / 模型原始输出
→ 生成新的信息缺口
→ 文档 / 源码 / Git / 运行实验
→ 更新判断和实现
→ 用测试、说明或 Skill 固化
→ 下一轮
```

这与 Information Foraging / Sensemaking 双循环一致：一边寻找更有信息气味的材料，一边重组问题表示；新表示又决定下一次检索。

## 4. 十六阶段归档

| 阶段 | 决策问题 | 主要信息源 | 证据如何改变行动 | 等级 |
|---|---|---|---|:---:|
| 1 可行性 | 使用原生组还是自建数据系统 | 用户场景、Chrome 官方文档 | 选择 MV3 Side Panel 与原生 `tabs/tabGroups` | B |
| 2 HTML 原型 | 狭窄侧边栏应保留什么 | 假数据原型、连续用户试用 | 删除低价值控件，统一手动与 AI 草稿 | A |
| 3 设计约束 | 哪些状态可恢复，何时写入 Chrome | 用户反馈、平台边界、状态管理模式 | 建立不可变快照、可编辑草稿和显式保存 | B |
| 4 实施计划 | 如何拆成可独立验证的单元 | 已批准设计、规划 Skill | 六任务、精确文件/接口、RED/GREEN 与提交点 | B |
| 5 核心实现 | 哪些逻辑可以脱离 Chrome 测试 | 领域建模、Chrome 文档、测试结果 | 纯函数/网关/模型协议/界面分层 | B |
| 6 动态导入错误 | Manifest 错还是 Service Worker 限制 | 用户错误、Chrome 官方文档、回归测试 | 保留 module worker，动态导入改静态导入 | A |
| 7 空组错误 | UI 空组如何映射到底层实体 | 错误、API 文档、用户语义 | 空组留在草稿，保存/更新/排序跳过 | A |
| 8 Key 看似丢失 | 是存储失败还是反馈错误 | 用户观察、代码数据流、威胁模型 | 回填密码框，并明确 password 不是密钥库 | A |
| 9 九色调色盘 | 任意颜色还是平台枚举 | 用户需求、Chrome 枚举 | UI 只呈现原生支持的九色 | A |
| 10 `null.color` | 防御一行还是修正组件边界 | 错误、渲染调用链、测试 | 未分组不进入依赖 group 的调色盘逻辑 | A |
| 11 流式进度 | 慢在哪里，怎样可观察 | 用户体验、供应商文档、SSE/Port 测试 | 长连接展示阶段、耗时与 reasoning | A |
| 12 不分组 | 解析丢数据还是模型给空方案 | 固定假数据真实 API、原始 JSON、开发者输出 | 保留解析器，默认 low Thinking，暴露诊断边界 | A |
| 13 未保存提醒 | 如何识别真正的表单变化 | 用户需求、字段集合、行为测试 | 稳定指纹覆盖改回原值和保存后基线 | A |
| 14 GitHub 发布 | 是否含秘密/身份，远端是否一致 | 全历史审计、Git/GitHub 运行证据、发布 Skill | 备份后改邮箱、再次授权、push 后双向验证 | A |
| 15 开发复盘 | 冷读者是否能理解隐含前提 | Git/代码/文档、独立读者测试 | 补架构、运行条件、威胁模型与恢复骨架 | B |
| 16 研究轨迹 | 如何区分知识、证据和 Skill 影响 | 全历史、Skill、事后官方复核 | 建立来源分类、时间性质和证据等级 | A |

等级沿用原追踪文档：A 有同时期代码、测试、提交或用户反馈相互印证；B 有单一产物或官方文档但缺完整工具日志；关于 `K` 的细粒度归因仍按 C 看待。

## 5. 五个高价值研究切片

### 5.1 原型是信息获取工具

项目最早不是搜索更多 UI 最佳实践，而是制作带假标签、假 AI 的可点击 HTML。八轮原型提交把模糊反馈转成可以实现和测试的约束。

这里的证据分工是：

- 官方文档回答“Side Panel 能不能做”；
- 原型回答“在真实宽度下什么有价值”；
- 用户反馈回答“哪些行为符合团队工作方式”；
- 设计文档和测试把反馈转成可复用约束。

由此可得：技术调研不只发生在网页搜索，也可以通过构造一个低成本、可交互的测量工具获得信息。

### 5.2 错误文本是高质量查询生成器

`import() is disallowed on ServiceWorkerGlobalScope` 和 `No group with id` 都把宽泛问题压缩为一个平台边界。正确动作不是让模型连续重写代码，而是：保留错误原文 → 确定发生边界 → 查该边界的一手文档 → 写最小回归测试 → 修改实现。

这个模式可泛化为：

```text
症状 ≠ 查询
症状 + 发生层 + 目标版本 + 预期不变量 = 可验证查询
```

### 5.3 UI 模型可以比底层实体更丰富

Chrome 不保留零标签组，但用户希望空组作为未来拖入目标继续显示。项目没有让其中一方“服从”另一方，而是区分：

- 草稿实体：允许空组，是用户意图；
- 原生实体：不能空，是平台事实；
- 映射规则：保存时跳过空组，未来拖入标签再创建。

这类决策必须同时读取产品证据与平台证据。只查 API 会删除有价值的 UI 概念；只听产品反馈又会调用不存在的底层能力。

### 5.4 结构正确不等于业务有效

AI 分组结果要通过 JSON 提取、类型、颜色白名单、ID 不虚构/不重复/不遗漏等检查。然而 `groups: []` 加全部 `ungroupedTabIds` 仍然可以完全合法，却没有整理价值。

因此至少要分四层 evaluator：

| 层 | 问题 | Tabloom 证据 |
|---|---|---|
| 传输 | 响应是否完整到达 | SSE 分片测试与开发者输出 |
| 结构 | 能否解析且满足不变量 | schema、颜色和 ID 完整性测试 |
| 业务 | 是否真的产生有意义分组 | 无变化/空分组检测仍需增强 |
| 人 | 分组名称和归属是否帮助工作 | 草稿允许人工修改后再保存 |

### 5.5 用真实但安全的边界实验停止猜测

非 Thinking 不分组无法靠 mock 裁决，因为 mock 只能证明客户端按预设响应工作。项目建立 live harness：

- 使用固定的 9 个假标签，不读取真实浏览器标签；
- Key 只来自 Git 忽略的 `.env.local`；
- 分别测试三种整理模式与 Thinking 开关；
- 记录耗时、推理字符数、组名/颜色/标签数和未分组数量；
- 不打印 Key；供应商结果明确标注可能波动。

当真实返回显示空 `groups` 后，原先的“解析器可能丢数据”假设被降级，行动转向业务提示、默认参数和可观察性。实验价值不在一次结果，而在让错误层次可见。

## 6. Skill 在这里提供了什么

这个案例避免把一切成功归因于模型能力。模型通用知识可以提出草稿模式、纯函数、流式反馈和调试假设；Skill 更主要地约束工作纪律：

- 创意工作先原型/设计，再实施；
- 复杂实现从 spec 拆成逐文件计划；
- 修复先出现可观察的失败测试；
- 完成声明需要当次新鲜验证；
- GitHub 发布前检查当前树、全部历史、身份、大文件和秘密；
- 高风险历史改写要备份并单独授权；
- 文档要让无上下文读者测试。

这支持一个重要判断：

> Skill 的价值常常不是告诉 Agent 某个 API 答案，而是让它在时间压力下仍选择正确的信息获取与验证动作。

## 7. 可审计性：应该记录什么

不追求保存模型隐藏推理，而保存能让他人重建决定的外部对象：

1. 当时要做的决定；
2. 缺少什么信息；
3. 搜索式、打开的来源和访问日期；
4. 来源是同时期使用还是事后复核；
5. 初始假设和置信度；
6. 原始错误、响应、源码或用户反馈；
7. 哪条证据支持或否定了什么；
8. 决策后采取的代码、测试或文档动作；
9. 被排除路线与仍待验证项；
10. 可复现命令、固定输入、版本、哈希与隐私边界。

本资料库新增 [`decision-research-log.yaml`](templates/decision-research-log.yaml)，把上述字段变成机器可读模板。

## 8. 与现有方法论的合并点

现有八阶段流水线可以从“前期研究管线”升级为“贯穿交付的循环”：

```text
Research Brief
→ 查询与候选池
→ 来源分层与证据卡
→ 方案/实现
→ 原型、错误、用户与运行反馈
→ 新的信息缺口
→ 定向文档/源码/实验
→ 更新决定与门禁
→ 归档为代码、测试、ADR、Skill
↺
```

Tabloom 还要求每次循环显式回答两个问题：

- 当前缺的是平台事实、产品事实、代码事实、运行事实还是流程约束？
- 这次新证据是否真的改变了置信度、结论或下一步动作？

## 9. 证据边界与不能外推的内容

- 单个项目不能证明这套流程必然提高所有团队效率。
- 提交顺序能证明变化发生的先后，不能完整证明当时为什么这样想。
- 原追踪文档部分内容是事后重建，不能冒充实时 telemetry。
- 用户反馈能决定本产品价值，不能替代其他团队的用户研究。
- 固定假数据真实 API 只裁决当次供应商行为，不能证明模型长期稳定。
- mock 和 Node 测试不能代替真实 Chrome 生命周期、尺寸和权限验收。
- Skill 加载证据必须保守；流程相似不等于能确认当时确实加载。
- Chrome 与模型能力会变化，进入演示的版本化事实需要在冻结日前重查。

## 10. 演示候选（暂不压缩）

### 候选 A：搜索前先写信息缺口

- 画面：宽泛主题与六个可验证问题的对照。
- takeaway：不要让 AI 搜主题，让 AI 填信息缺口。
- 证据：阶段 1、6、7、12。
- 推荐度：S。

### 候选 B：来源路由矩阵

- 画面：问题类型 → 用户/官方文档/源码/Git/运行/Skill。
- takeaway：最权威来源不一定回答当前问题，证据必须匹配问题。
- 推荐度：S。

### 候选 C：调研不是开发前的一次性阶段

- 画面：实现 → 反馈 → 新缺口 → 定向取证 → 修正 → 固化的环。
- takeaway：错误与用户反馈持续生成下一轮查询。
- 推荐度：S。

### 候选 D：合法 JSON 但无业务价值

- 画面：四层 evaluator。
- takeaway：格式正确、结构合法、业务有效与用户有用是不同门禁。
- 推荐度：A。

### 候选 E：真实边界实验

- 画面：mock 全绿与真实 API 空分组并列。
- takeaway：静态证据无法裁决时，用固定假数据观察真实边界。
- 推荐度：A。

### 候选 F：可审计轨迹而非隐藏思维

- 画面：输入—动作—证据—决策—产物。
- takeaway：记录可复核对象，不伪造完整思维日志。
- 推荐度：S/A。

### 候选 G：机器可读 Research Log

- 画面：`information_need / sources / confidence_before / result / action`。
- takeaway：只有会改变决策的资料才值得进入核心上下文。
- 推荐度：S，适合结尾交付模板。

## 11. 归档结论

Tabloom 最适合支持的核心主张是：

> AI Agent 的技术调研能力，不应只按搜索了多少网页评价；更重要的是它能否识别当前缺少哪类证据、选择匹配的信息源、在证据否定假设时改变结论，并把决定留下可回查、可执行的产物。
