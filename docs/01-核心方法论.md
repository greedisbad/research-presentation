# 核心方法论：从问题到工程资产

## 总览

```text
Research Brief
    ↓
查询矩阵与种子来源
    ↓
候选池与来源分层
    ↓
源码 / 文档 / 视频深读
    ↓
主张—证据矩阵
    ↓
可运行实验与工程方案
    ↓
测试、评审与反证
    ↓
仓库文档、Skill、脚本、模板
```

这条流水线的核心不是“每一步都交给 AI”，而是让每一步产生下一步可以检查的中间产物。

## 第一阶段：定义决策，而不是定义主题

“调研 WPS 插件”是主题，不是决策问题。更可执行的写法是：

> 在 WPS PPT 加载项中实现可编辑幻灯片生成，目标环境为 JavaScript/Vue；需要比较直接操作 WPSJS、生成 PPTX、HTML 截图等路径，并用 3 天内可完成的原型验证关键 API。

Research Brief 至少包含：

- 最终要做的决策；
- 使用环境与版本；
- 必须满足与明确排除的条件；
- 时间和成本预算；
- 需要什么形式的证据；
- 输出格式；
- 完成标准和停止条件。

OpenAI 的 Deep Research 官方流程同样把“描述结果、选择来源、审阅研究计划”放在搜索之前，并要求用户在结果产生后检查引用。[OpenAI Help Center](https://help.openai.com/en/articles/10500283-deep-research-in-chatgpt)

## 第二阶段：生成查询矩阵

单个关键词只能看到一个结果切面。查询矩阵至少沿以下维度展开：

| 维度 | 示例 |
|---|---|
| 目标行为 | generate / edit / parse / migrate / debug |
| 对象与平台 | WPS PPT / PowerPoint / Office add-in / WPSJS |
| 资产类型 | API docs / source / example / issue / benchmark |
| 约束 | JavaScript / editable / offline / cross-platform |
| 失败词 | unsupported / bug / limitation / workaround |
| 时间与版本 | 2025 / v2.2.3 / latest |
| 语言与同义词 | 加载项 / add-in / plugin / extension |

信息检索研究将 Query Expansion 定义为用相关术语重写或扩展初始查询，以解决同义词、多义词和词汇不匹配造成的召回与精度问题。[Azad & Deepak, 2019](https://arxiv.org/abs/1708.00247)

这里 AI 的优势非常直接：它可以一次生成不同角色、语言、技术层级和失败方向的搜索词。人的责任是删去偏题词，并根据第一批结果做 relevance feedback。

## 第三阶段：种子来源与滚雪球

先找 3–5 个高质量种子，而不是立刻追求一百条结果。种子可以是：

- 官方文档入口；
- 维护活跃的代表仓库；
- 原始论文；
- 高质量技术会议演讲；
- 问题跟踪器中信息完整的 Issue/PR。

然后进行两种滚雪球：

- **向后追踪**：它引用了哪些文档、库、论文和实现？
- **向前追踪**：后来哪些项目、论文、Issue 或迁移采用/批评了它？

Wohlin 在软件工程系统文献研究中给出了 backward/forward snowballing 的系统化步骤，并指出它可以成为数据库搜索的有效替代或补充。[Wohlin, 2014](https://www.wohlin.eu/ease14.pdf)

对开源项目，还可以增加“横向滚雪球”：查看依赖、Fork、贡献者其他项目、Awesome 列表、同类 benchmark 和被引用的代码路径。

## 第四阶段：来源分层与初筛

建议把来源分为五层：

| 层级 | 典型来源 | 用途 |
|:---:|---|---|
| L1 | 源码、标准、官方 API、原始论文、可执行测试 | 关键事实与最终验证 |
| L2 | 官方工程博客、维护者设计文档、Issue/PR | 设计动机、边界和真实故障 |
| L3 | 高质量独立技术分析、会议分享 | 建立解释框架、发现线索 |
| L4 | 教程、视频、问答、社区帖子 | 学习路径和异常线索 |
| L5 | AI 摘要、搜索摘要、无来源转载 | 仅用于发现，不作为证据 |

来源质量不是固定标签。官方营销案例可能有一手数据但存在选择偏差；社区 Issue 可能不权威，却是某个版本故障的直接证据。

## 第五阶段：从“来源摘要”升级为“证据卡”

不要只问“这篇文章讲了什么”。对每个重要来源提取：

- 它回答哪个研究问题；
- 哪些是可核验事实；
- 哪些是作者意见或我们的推断；
- 使用的版本、样本和环境；
- 能否定位到代码、段落、图表或测试；
- 与其他来源是否冲突；
- 可以转化成什么工程动作。

Google DeepMind 的 SAFE 方法把长回答拆成独立事实，再逐项搜索证据判断是否被支持。这提供了一个适合技术分享的简洁验证模型：**先原子化主张，再逐项核验。** [Long-form factuality](https://deepmind.google/research/publications/85420/)

## 第六阶段：把参考翻译成当前约束

“这个项目很厉害”没有实施价值。应该改写成：

| 参考资产 | 当前项目约束 | 转化方式 | 验证方法 |
|---|---|---|---|
| Python PPT 布局引擎 | WPS 插件为 JavaScript | 复用布局参数与设计规则，不复用运行时 | 对照渲染结果 |
| HTML 主题 Tokens | WPS 形状 API | 映射颜色、字体、间距 | 主题快照和人工检查 |
| python-docx 对象模型 | WPS Word 缺少完整 TS 类型 | 借用工具语义，运行时探针验证对象 | mock + WPS 真机 |
| Agent 多步规划 | 上下文和费用有限 | 精简为计划—工具—观察循环 | 步骤历史测试 |

这正是 WPS 案例中最强的一点：它不是“找到一个相同项目”，而是从不同项目分别抽取可迁移的局部结构。

## 第七阶段：用执行结果反过来修正研究

真正的技术研究不是线性的。实现阶段常会发现：

- 官方文档与运行时不一致；
- 类型声明不覆盖真实 API；
- 相邻平台的同名对象语义不同；
- Prompt 指令不如工具参数可靠；
- 单个示例可运行，多实例或边界条件失败。

因此应把构建、类型检查、测试、日志和真机行为写回证据卡。Google 的 AlphaEvolve 将 LLM 生成与自动 evaluator 结合，只保留能被客观评分的候选程序；它说明“生成能力”必须与“可自动验证的目标”配对。[Google DeepMind](https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/)

Deck.gl 案例进一步展示了一个适合陌生技术的证据升级顺序：

```text
模型知识提出假设
    ↓
官方文档确认公开契约
    ↓
目标版本源码确认真实实现
    ↓
同仓库可运行代码提供当前范式
    ↓
最小实验确认本地环境行为
```

这里的重点不是每个问题都必须读源码，而是让来源匹配问题：API 语义先查文档，版本差异追源码和 Release，运行时兼容必须在真实环境中验证。

## 第八阶段：沉淀为仓库内知识

一次调研的高价值产物包括：

- Research Brief 与查询矩阵；
- 来源索引和证据卡；
- 被否决方案及否决原因；
- 可运行 Spike 与测试；
- 架构决策记录；
- AGENTS.md、Skill、脚本和模板。

OpenAI 的 Harness Engineering 案例指出，代理看不到的聊天和脑内知识等于不存在；仓库内、可版本化、可检查的 Markdown、Schema 和执行计划才会持续产生杠杆。同时它也提醒，一个巨大的说明文件会挤占上下文，应该给代理“地图”而不是“一千页手册”。[OpenAI](https://openai.com/index/harness-engineering/)

Dice 项目的连续复盘说明还应显式保存“负知识”：已经排除的路线、失败原因、已确认无需重查的事实和仍待验证的风险。对没有长期记忆的轻量 Agent，这些内容比再次附上一整段聊天记录更有用。

建议把轻量 Agent 的最小研究脚手架固定为五份文件：

| 文件 | 作用 |
|---|---|
| `01-PROBLEM.md` | 决策问题、硬约束和未知项 |
| `02-EVIDENCE.md` | 来源、版本、事实、推断与冲突 |
| `03-EXPERIMENTS.md` | 候选路线、控制变量和运行结果 |
| `04-ACCEPTANCE.md` | 验收标准和完成证据 |
| `05-LEARNINGS.md` | 已排除路线、失败原因和下次优先项 |

## 人机分工底线

| 可以大量交给 AI | 必须由人把关 |
|---|---|
| 查询扩展、批量抓取、格式转换、初步聚类 | 决策目标和组织约束 |
| 文档/源码/转写内容的结构化提取 | 证据是否足以支持高风险结论 |
| 生成候选方案、实验和测试草案 | 安全、合规、隐私和不可逆影响 |
| 寻找冲突证据和版本差异 | 最终架构选择与上线验收 |
| 把经验改写成模板或 Skill | 判断哪些经验具有普适性 |
