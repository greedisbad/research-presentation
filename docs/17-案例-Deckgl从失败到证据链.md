# 案例：Deck.gl——从“继续生成”转向定向调研

## 案例定位

这个案例不用于证明某个模型更强，也不用于讲解 Deck.gl API。它回答的是一个更通用的问题：

> 当 AI 连续生成的实现都不能运行时，怎样把“再试一次”改造成一轮可追溯的技术调研？

原始需求是让 Deck.gl 图标持续旋转，同时保持可拾取、接近 60 FPS、避免每帧重建图层，并产出多种可独立运行的 HTML 实验。早期生成结果看似完整，却没有达到实际运行效果。真正的转折不是换一句 Prompt，而是把现象拆成研究问题，分别寻找文档、同版本源码和运行时证据。

原始复盘：`<本地案例目录>/deckgl-rotation/IMPLEMENTATION-NOTES.md`。

## 一、从模糊失败提取可搜索问题

“图标没有按预期旋转”本身不适合直接搜索。案例中实际拆出了几类问题：

| 问题类型 | 可检索问题 | 应查来源 |
|---|---|---|
| 对象边界 | 当前直接使用的是哪个 Layer？它真正支持哪个 accessor？ | 官方 API、类型声明、源码 |
| 数据语义 | 角度值使用度还是弧度？ | 官方文档、同版本源码 |
| 生命周期 | 状态应该由外部重建还是内部逐帧更新？ | 生命周期文档、示例、源码 |
| 版本兼容 | 当前版本的 shader 注入接口如何声明 uniform？ | 同版本源码、同仓库扩展实现 |
| 非功能约束 | 怎样证明没有重复初始化并保持流畅？ | 运行时指标、自动化实验 |

这一步的教学价值高于具体答案：先识别“缺的是哪一类知识”，再决定去哪里搜，而不是把所有问题都交给通用网页搜索。

## 二、模型知识只负责提出假设

第一轮分析提出了两个竞争假设：API 名称可能属于另一个抽象层；角度单位可能理解错误。它们都很合理，但此时仍只是待核验假设。

建议采用三段式记录：

```text
观察：页面加载，但目标行为不明显。
假设：属性名、单位或更新生命周期可能不符合当前组件契约。
验证：分别查公开契约、同版本实现，并做只改变一个变量的实验。
```

这样可以避免把模型“听起来像答案”的解释直接写入方案。

## 三、文档、源码和实验各自回答不同问题

这个案例形成了一条清楚的证据升级路径：

1. **官方文档**确认公开 API、参数语义和推荐更新方式；
2. **目标版本源码**确认文档背后的真实转换、生命周期和内部实现；
3. **同仓库可运行代码**提供当前版本已经走通的接口范式；
4. **最小实验**判断这些结论在实际浏览器和 WebGL 环境中是否成立。

其中一个关键纠错来自运行时：静态阅读看起来可接受的 shader 写法，在目标环境发生链接失败。继续搜索同版本相邻扩展的实现后，才得到正确的 uniform 声明方式。

因此适合演讲的结论不是某条 API，而是：

> 教程告诉你“有人曾这样做”；同版本官方源码告诉你“这个版本实际怎样做”；运行环境告诉你“在你的约束下能不能做”。

## 四、把候选答案变成对照实验

最终没有只保留一个“标准答案”，而是建立四条路线：内部逐帧状态、低频目标值加属性过渡、GPU uniform 动画，以及用于诊断单位问题的基线对照。

在演讲中不必逐条解释 Deck.gl 实现，只需展示候选比较方法：

| 比较维度 | 要问的问题 |
|---|---|
| 正确性 | 是否真的产生目标行为？ |
| 侵入性 | 是否要求改动现有架构？ |
| 生命周期 | 是否造成重复创建或状态漂移？ |
| 性能 | 工作发生在 CPU、属性更新还是 GPU？ |
| 可维护性 | 是否依赖内部 API或版本细节？ |
| 适用场景 | 适合现有封装、批量对象还是高频动画？ |

四个实验页面的意义是让不同路线共享同一组约束和观察指标，从而把“我觉得这个方案好”变成可比较的工程选择。

## 五、最值得迁移到轻量 Agent 的工作协议

这个流程并不依赖专有 Skill 或 MCP。一个只有搜索、读写文件和运行命令能力的 Agent，也可以遵守以下协议：

1. 先写硬约束和完成标准；
2. 把模型判断标为假设，不标为事实；
3. 每个关键结论记录来源、版本和适用范围；
4. 多个解释竞争时，设计只改变一个变量的对照实验；
5. 运行结果写回证据记录；
6. 保存失败路线以及被排除的原因；
7. 只有验收证据满足完成标准，才宣布结束。

可以用五个普通 Markdown 文件实现：

```text
01-PROBLEM.md       问题、硬约束、未知项
02-EVIDENCE.md      文档、源码、版本和证据定位
03-EXPERIMENTS.md   候选路线、变量、运行结果
04-ACCEPTANCE.md    验收标准和最终证据
05-LEARNINGS.md     失败路线、限制和下次不要重复的工作
```

## 六、演讲抽象层

### 推荐进入正文（S）

- 连续生成失败后，停止改 Prompt，先把失败拆成可检索问题；
- 模型用于提出假设，文档确认契约，源码确认版本实现，实验确认环境行为；
- 当多个解释都合理时，用控制变量实验筛选，而不是继续争论；
- 最好的参考有时不是教程，而是同版本官方仓库中已经运行的相邻实现；
- 调研的最终产物应包括可运行样例、决策依据和失败记录，而不只是一段回答。

### 可进入附录（A/B）

- 四条路线的完整比较；
- WebGL 像素变化、自动 picking、初始化计数和 FPS 等验收设计；
- 暂停、单步和结构测试怎样帮助排错；
- 目标版本源码的具体定位。

### 不进入 PPT 主体（D）

- `IconLayer` 的具体 accessor 名称；
- 度数与弧度的具体换算位置；
- shader uniform 的版本语法；
- 测试文件名、断言数量和每个 HTML 的内部结构。

这些内容保留在证据层，用于证明案例真实、回答现场追问和供课后复现。

## 七、证据边界

- 这是一个真实工程案例，不是受控模型能力评测；不能据此比较模型排名。
- 成功来自模型、问题分解、工具、可观察环境和验收协议的组合，无法把结果归因给单一因素。
- 自动测试能够证明若干工程属性，不能替代所有视觉与产品判断。
- 原项目当前没有可引用的稳定 Git HEAD，引用时应以文件、目标版本和实验记录为边界，不把未提交状态包装成不可变版本证据。
