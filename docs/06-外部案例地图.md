# 外部案例地图：AI 如何“先找资料，再动手”

这份材料不是产品排行榜，而是不同领域中同一工作模式的案例库。

## 模式一：先理解代码库，再修改

### Anthropic：Explore → Plan → Code → Commit

Claude Code 的官方最佳实践建议先阅读相关文件、图片或 URL，并明确要求暂不写代码；然后生成计划，再实施和提交。[Anthropic](https://www.anthropic.com/engineering/claude-code-best-practices)

可借鉴点：把“先别动手”写成明确阶段，避免模型在证据不足时过早锁定实现。

### OpenAI：用 Codex 理解陌生代码

OpenAI 的内部用例包括定位功能核心逻辑、映射服务或模块关系、追踪数据流和发现文档缺口。[How OpenAI uses Codex](https://openai.com/business/guides-and-resources/how-openai-uses-codex/)

可借鉴点：代码理解的输出应该是调用链、数据流、模块图和缺口，而不只是文件摘要。

### Sora Android：代表实现成为 Agent 的活文档

团队先人工确定架构、依赖注入、导航、认证和网络基础，再写若干代表功能；Codex 根据这些模式扩展，并通过 AGENTS.md 复用规则。[OpenAI](https://openai.com/index/shipping-sora-for-android-with-codex/)

可借鉴点：与其写抽象长规范，不如给 AI 一个被团队认可、经过测试的邻近实现。

## 模式二：先确定影响范围，再批量迁移

### Spotify Honk：lineage + code search + Agent

在迁移数据集消费者前，Spotify 先通过 Backstage lineage 找到下游依赖，再用 Code Search 确定目标仓库，最后由 Agent 修改和创建 PR；需要业务判断的情形被明确排除。[Spotify Engineering](https://engineering.atspotify.com/2026/4/background-coding-agents-dataset-migrations-honk-part-4)

可借鉴点：搜索不仅用于找“怎么改”，还用于回答“哪些地方必须改”。影响范围本身是实施输入。

### Cisco：跨仓库构建优化与迁移

OpenAI 发布的 Cisco 案例称，Codex 分析了多个互联仓库的构建日志和依赖图，也用于 React 版本迁移与 C/C++ 缺陷修复。[OpenAI / Cisco](https://openai.com/index/cisco/)

可借鉴点：让 Agent 读取日志与依赖图，比只给 Issue 描述更接近真实问题。

限制：厂商客户案例中的效率数字属于合作方自报，除非有独立方法说明，不作为演讲核心数据。

## 模式三：先搜索知识，再运行实验

### Google ERA

ERA 给定科学问题和成功度量后，可以搜索科学文献、编写代码、探索方案、组合技术并评价结果。[Google Research](https://research.google/blog/empirical-research-assistance-era-from-nature-publication-to-catalyzing-computational-discovery/)

这是最贴合标题的外部案例：检索不是报告终点，而是实验候选的来源。

### AlphaEvolve

AlphaEvolve 用语言模型提出候选程序，通过自动 evaluator 运行、验证与评分，并用优秀结果继续演化。[Google DeepMind](https://deepmind.google/blog/alphaevolve-a-gemini-powered-coding-agent-for-designing-advanced-algorithms/)

可借鉴点：如果成功不能被量化，Agent 就无法稳定自主迭代。日常开发中的等价物是测试、benchmark、lint、视觉检查和验收脚本。

### OpenAI 科学计算案例集

OpenAI 汇总了八个 Agent 辅助科学软件项目，覆盖维护、迁移、优化和重写，并把研究者角色概括为定义、验证和维护责任。[OpenAI](https://openai.com/index/scientific-computing-agentic-ai/)

可借鉴点：实现速度不是唯一结果，长期所有权和上游协作决定新实现会成为基础设施还是下一个弃置项目。

## 模式四：先构建来源库，再综合

### OpenScholar

OpenScholar 不是直接依赖通用模型记忆，而是从专用论文语料检索、重排、生成引用答案，再通过 self-feedback 改进。[Nature](https://www.nature.com/articles/s41586-025-10072-4)

可借鉴点：研究系统的性能来自“语料 + 检索 + 综合 + 反馈 + 评价”的组合。

### PaperQA2

PaperQA2 将论文搜索、证据收集、引用遍历和答案生成设计成 Agent 工具链，并用专门 benchmark 评价科学研究任务。[PaperQA2](https://arxiv.org/abs/2409.13740)

可借鉴点：如果资料之间存在引用网络，Agent 应主动沿引用扩展，而不是只按关键词搜索。

### Elicit Systematic Review

Elicit 把系统综述拆成检索、标题摘要筛选、全文筛选、数据提取和报告，并为筛选/提取提供原文支持。[Elicit](https://elicit.com/blog/systematic-review/)

可借鉴点：把高成本流程拆成可抽查、可覆盖和可人工覆盖的表格步骤。

限制：效果数字主要来自厂商评测；适合展示流程，不宜作为通用准确率承诺。

## 模式五：多视角搜索后再写作

### Stanford STORM

STORM 通过多视角问题生成和检索先构建主题大纲，再产生带引用长文。[GitHub](https://github.com/stanford-oval/storm)

可借鉴点：先问“不同角色会问什么”，能减少大纲只反映单一视角。

### Anthropic Research

主代理拆分研究方向，子代理并行搜索并根据结果继续追踪，最后由 CitationAgent 定位引用。[Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)

可借鉴点：研究的并行单位应是互斥的问题族，而不是让多个 Agent 搜同一个模糊主题。

## 模式六：把失败和人工修正变成下一轮能力

### 自改进税务 Agent

OpenAI 与合作方的案例把从业者修正转换成 eval，再由 Codex 针对失败进行改进。[OpenAI](https://openai.com/index/building-self-improving-tax-agents-with-codex/)

可借鉴点：高质量人工修正不应只解决当前一次回答，而应转成回归样例和评价标准。

### Harness Engineering 的持续“垃圾回收”

Agent 会复制仓库中的坏模式，因此团队把 golden principles 写入仓库并持续扫描偏差。[OpenAI](https://openai.com/index/harness-engineering/)

可借鉴点：知识库不是只增不减；旧规则、重复文档和错误范例也需要持续清理。

## 一页对比

| 案例 | 搜什么 | 动什么手 | 如何验证 | 人的核心角色 |
|---|---|---|---|---|
| WPS 本地案例 | API、类型、参考项目 | 插件工具与适配器 | 类型、测试、真机 | 环境约束与最终取舍 |
| Spotify Honk | lineage、代码引用、仓库范围 | 跨仓库迁移 | CI、Schema、PR review | 排除需业务判断的场景 |
| Google ERA | 科学文献与技术方法 | 编写和组合实验代码 | 成功度量与 benchmark | 定义问题和评价指标 |
| AlphaEvolve | 已有程序与候选策略 | 演化算法实现 | 自动 evaluator | 设计可测目标 |
| OpenScholar | 论文与引用网络 | 综合研究报告 | 专门 benchmark 与引用检查 | 判断研究问题和适用性 |
| 视频案例 | 视频、简介、评论、项目链接 | 下载、转写、结构化 | 回听、源码和官方文档 | 入选标准和最终核验 |
