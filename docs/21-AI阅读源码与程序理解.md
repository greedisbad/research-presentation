# AI 阅读源码与程序理解：不要让它“解释整个仓库”

## 核心判断

阅读源码不是从头到尾压缩文本，而是围绕任务连续提出问题、找到焦点、扩展关系、形成局部模型，再用运行或历史证据校验模型。

这为 AI 阅读陌生代码提供了一个更专业的提示方式：不要先让它“总结整个仓库”，先告诉它我们要作出的改变或判断，以及必须回答的源码问题。

## 一、开发者阅读代码时实际在寻找什么

Ko、DeLine、Venolia 对 17 名软件开发者的日常工作观察识别了 21 类信息需求。经常被推迟的需求包括设计与程序行为：为什么代码这样写、程序本来应该做什么、某个状态为何出现。部分任务被阻塞，是因为唯一知识源是暂时不可用的同事。[ICSE 2007 论文](https://www.cs.cmu.edu/~marmalade/papers/Ko2007InformationNeeds.pdf)

同一研究报告了陌生代码调查中的三个基础问题：

1. 哪段代码可能造成这个行为？
2. 哪些代码与它存在静态关系？
3. 哪段执行过程造成了这个程序状态？

开发者会从假设出发，使用源码搜索、日志、bug report、同事经验与调试器逐步检验；高层问题往往必须翻译成一组低层工具操作。[Microsoft Research 收录版本](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/icse07_ko.pdf)

这直接解释了为什么 AI 只读当前文件容易给出“合理但不够”的答案：行为、结构、历史意图和运行状态分散在不同证据载体里。

## 二、源码问题有层级，Agent 的搜索也应逐层扩展

Sillito、Murphy 与 De Volder 通过两个定性研究整理出程序员在变更任务中提出的 44 类问题，并归纳为四组：[FSE 2006 原论文](https://citeseerx.ist.psu.edu/document?doi=3dda5d9a5e4eb27760e8a4a381a1057ce0ba7d65&repid=rep1&type=pdf)

| 问题层级 | 典型问题 | AI 可调用的证据 |
|---|---|---|
| 找到初始焦点 | 哪个类型代表这个领域概念？错误文本在哪里？ | `rg`、symbol search、路由和入口文件 |
| 围绕焦点扩展 | 谁调用它？继承、持有或修改它的是谁？ | references、call sites、类型关系 |
| 理解局部子图 | 这些类型共同提供什么行为？数据如何流动？ | 调用链、状态更新、测试、运行日志 |
| 跨子图整合 | UI、模型、协议与持久化如何对应？改动会影响哪里？ | 架构、diff、Issue/PR、端到端实验 |

研究还观察到两种常见轨迹：围绕同一实体呈“星形”追问，或者从新发现的实体继续形成“链式”追问。现有工具即使各自能回答窄问题，也常让开发者自己拼接多个孤立结果。

这恰好是轻量 AI Agent 能发挥作用的地方：维护任务上下文，把多个窄工具结果组织成针对高层问题的证据链。

## 三、理解不是生成一段自然语言摘要

Wyrich 在回顾数十年程序理解理论后指出，研究中经常通过不同任务隐式定义“理解”，因此不同实验测到的构念未必相同。他提出以心理模型、状态变化和实验变量来描述源码理解，并区分例如“代码应该做什么”和“给定输入实际做什么”。[2023 年论文](https://arxiv.org/abs/2310.11301)

对工程实践的启示是：必须在提示中把“理解到什么程度”操作化。

下面五种任务需要的理解深度并不相同：

- 定位配置入口；
- 解释某个函数的表面作用；
- 判断运行时行为；
- 修改功能并评估影响面；
- 解释设计缘由和版本变化。

因此，应把“请理解这个仓库”改写为可验收的问题，例如：

> 找出控制图标旋转的公开 API、目标版本实际实现、同仓库调用范式和最小可运行验证；对每项给出文件位置，并区分文档事实、源码推断和运行结论。

## 四、源码不是唯一来源

LaToza、Venolia 与 DeLine 对 Microsoft 开发工作的观察报告：调查代码时，受访者平均把最多时间放在源码本身，同时还使用调试器、check-in comment、版本 diff、运行结果与 trace；当源码无法解释设计缘由时，开发者往往转向社会网络，而有价值的解释又很少被持久记录。[Microsoft Research 技术报告](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-2005-140.pdf)

这支持“整个程序不是只有源码文本”的观点。一个面向调研的 Agent 应按问题选择证据：

```text
现在是什么：目标版本源码、配置、类型和测试
为什么这样：blame、commit、Issue、PR、设计文档
实际怎样：可运行样例、日志、调试器、截图和断言
用户能否获得：tag、Release、包版本和发布渠道
```

注意：论文中的百分比来自特定时期、组织与自报调查，不应当作今天所有团队的固定比例。演讲更适合引用“多种证据载体共同参与理解”这一观察。

## 五、可复制的 AI 源码调研协议

### 1. 先写任务，不先读全仓库

- 要修复、实现或判断什么？
- 目标版本、运行平台和不可改变的边界是什么？
- 最终需要代码修改、技术结论，还是方案比较？

### 2. 建立仓库地图

只获取高信号入口：README、manifest、目录树、构建脚本、核心模块、测试与历史约定。地图用于导航，不代替源码证据。

### 3. 用问题树驱动工具

```text
焦点在哪里？
  → 它与谁相连？
    → 局部行为如何发生？
      → 多个局部如何共同完成用户流程？
        → 哪个实验能够证伪当前解释？
```

### 4. 给每个答案标注证据类型

- `DOC`：公开契约或使用说明；
- `CODE`：目标版本静态实现；
- `HISTORY`：变更缘由和版本边界；
- `RUNTIME`：真实行为；
- `INFERENCE`：尚待检验的解释。

### 5. 输出局部模型，而不是仓库百科

合格产物至少包含：任务相关入口、关键实体关系、数据/控制路径、版本和失败边界、未验证项、下一次最小实验。

## 六、与 Deck.gl 案例的连接

Deck.gl 案例之所以适合本主题，不是因为某个具体 API 名称，而是它完整展示了源码问题树：

1. 以“为什么图标方向不符合预期”确定初始焦点；
2. 从公开文档查能力契约；
3. 从目标版本源码核对属性如何进入 shader/绘制路径；
4. 查同仓库示例，判断官方预期用法；
5. 用四条实现路线做运行时对照；
6. 把成功与失败条件记录为可交接知识。

`IconLayer` 的具体属性名应留在证据页或演示截图中。正文要讲的是：当自然语言解释无法区分“应该做什么”和“实际做什么”时，要把问题逐级落到 DOC、CODE、HISTORY 和 RUNTIME。

## 七、推荐加入演说的点

推荐度：S，建议放在“搜索之后如何读源码”部分，并紧接 Deck.gl 或 WPS 案例。

建议保留三句话：

1. **不要让 AI 解释整个仓库，让它回答一棵源码问题树。**
2. **源码理解是在构建任务相关的局部模型，不是在压缩全部文件。**
3. **高层问题通常不能被一次搜索回答，需要组合源码、历史、运行与发布证据。**

可展示一个四层问题漏斗，再用 Deck.gl 的证据升级过程落地；不需要在主 PPT 罗列 44 个问题。

## 八、证据边界

- Ko、Sillito 和 LaToza 等研究来自 2000 年代的软件团队与工具环境；问题类型仍有解释力，但具体频率不能直接外推到 2026 年的 AI 开发流程。
- Wyrich 的论文主要建立程序理解研究的概念框架，不是对 AI Agent 理解能力的验证。
- “AI 适合跨工具拼接证据”是基于研究缺口和本地案例形成的工程推断，后续应通过新案例记录准确率、遗漏和人工修正成本。
- 文件位置和自然语言解释只证明可追溯，不自动证明运行正确。
