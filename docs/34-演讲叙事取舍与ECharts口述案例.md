# 演讲叙事取舍与 ECharts 口述案例

> 2026-09-16 根据讲者讨论归档。本文件是**正式版选材与叙事约束**，不是已核验的新增技术证据，也不直接改写 55 页内容母版。开场 hook 尚未选定。

## 最重要的方向变化

正式演讲不宜按“搜索—筛选—验证—归档”罗列方法和工具。更自然的叙事单元是：**我做了什么项目 → 遇到什么具体问题 → AI 先怎么帮忙、哪里没解决 → 去哪里找到了决定性信息 → 如何把结论用于项目 → 留下什么可复用资源**。每个案例只承担一个新判断；方法步骤在故事之后用一张小图抽象，不为每个步骤另开定义页。

听众不限于程序员。产品经理也会参与调研和选型，因此“信息缺口”至少包括技术能否实现、产品是否值得做、素材/业务事实是否可靠。代码、文档、用户反馈和运行画面不能互相代替。避免把演讲做成纯 API 调试报告。

## 口述案例：ECharts 版本字段猜测

### 讲者回忆的事实

公司内部项目曾要求：**折线图 X 轴左右两端的 label 必须显示数据端点的 X 值**。AI 给出的 ECharts 配置字段在当前项目里没有效果，随后又改了多版，仍在猜测。该项目不是 TypeScript，错误字段未产生编译报错。最终让 AI 查看项目安装依赖的 `node_modules` 中类型/定义文件，才发现目标版本的字段与先前参考的版本不同，并使用当前版本正确的字段解决。

这是讲者的一手回忆，目前**没有提供公司代码、依赖版本、前后配置、类型定义片段或截图**。本资料库不得写出猜测的具体字段名、版本号、修改次数和“必定”成功率；也不应将公司源码或图表数据放入公开项目。若未来允许补证，优先使用脱敏后的最小复现：依赖版本、原字段、当前版本定义、修正后的配置与前后截图。未补证前适合作为 60–90 秒口述故事，不作技术细节教学或可引用案例卡。

### 它说明的研究方法

问题不是“AI 不会写 ECharts”，而是**检索对象选错了**：网上示例或模型记忆回答的是“某版本可能怎样”，本地 `node_modules` 定义回答的是“这个项目安装的版本允许什么”。无类型检查时，运行画面成为第一条失败信号；AI 应据此停止猜字段，转向本地依赖定义与目标版本文档，再回到图表验证。

可用的简短表达：

> AI 连改几版配置都没效果。真正改变结果的不是更会提示，而是让它去读当前项目安装版本的定义。

不要从这一个故事推出“所有图表问题都应看 `node_modules`”；它支持的是“版本相关问题优先查目标版本的一手实现/定义”。

## 案例在正式版中的职责

| 素材 | 最适合承担的判断 | 画面与边界 |

| WPS 历史截图与参考项目 | 不照搬整个轮子，从不同仓库借局部，翻译进当前宿主；真实画面仍须校验 | 可画“这里借参数、那里借协议/工具/验证”的来源到资产图；[历史真机截图](evidence/W05-WPS历史真机截图.md)只证明当时的 WPS 客户端画面，不替代当前门禁 |
| Web Excel | 从需求约束筛到可比较实验，而不是 AI 给一个通用排行榜 | [案例档案](33-新增案例-飞机建模与表格选型.md)和已归档浏览器截图；适合产品经理与开发者共同理解 |
| Deck.gl | 页面能开但目标行为失败；错误促成同版本源码/最小实验的定向检索 | 可用原 HTML 现场运行或预录；静态截图只能证明单帧，不能证明动画持续 |
| B 站视频 | 在网页受阻或无字幕时，通过结构化数据、媒体与转写建立候选语料 | 这是“先寻找页面背后的结构化数据”的网站研究样例，不保证其他站点接口、权限或条款相同 |
| 飞机建模 | 先找业务事实和视觉参考，再生成可编辑资产；事实、参考图与创作性模型边界不同 | 有真实渲染图，适合短插页；不能滑向三维建模产品展示 |

“Codex 写代码 → 编译错误 → 浏览器运行时错误 → 截图视觉校验”应作为横跨案例的**反馈闭环**出现，不单独扩成 AI 编程流程章节。重点讲每个失败信号怎样改变下一步该找的资料；技术结论由匹配媒介的证据裁决。具体编译、运行和截图案例应选已有真实记录，不用抽象全绿勾选图冒充一次完整执行。

## 搜索与网络环境：可以说什么

公司主要使用 Claude，讲者观察到单纯 Web Search 或访问网页时会遇到网络不通、资料获取受限。正式版可讲“**访问通道失败时，不要把它等同于证据不存在**”：查本地依赖、已下载源码、官方仓库、包元数据、可访问的结构化接口或最小实验，并记录来源与版本。B 站从页面到 JSON、字幕、音频的降级链是具体例子。

目前没有对 Codex 与 Claude 在相同网络、相同来源、相同任务上的受控比较，也不知道两者内部搜索实现细节。因此**不讲“Codex 搜索机制更好”**，也不把网络可达性差异说成模型能力差异。若要演示，只对比可观察的动作与结果，不推测厂商内部机制。

## 编排与注意力约束

1. 一个项目片段只讲一个问题与一个转折；背景介绍以观众理解问题所需为限。
2. 先给看得见的失败或结果，再交代搜索路径；别先投影长方法目录。
3. 方法用少数几张“案例之后的小结图”表达，如“现象 → 新信息缺口 → 对应来源 → 可执行产物”。
4. WPS、Web Excel 承担主要篇幅；Deck.gl、B 站、ECharts、飞机按主线缺口选择短例，不要求全部进入 45 分钟现场版。
5. 不把验证抬成演说主体；它是让搜索结果足以行动的必要收口。
6. 具体 API 字段、ECharts 配置名、Deck.gl accessor、WPS 类名默认留在问答或证据附录，除非一个细节本身就是认知转折。
