# 《AI 辅助技术调研实践》六幕全量演讲稿结构设计

> 状态：待讲者审阅。  
> 用途：指导后续全量逐页演讲稿、案例演讲素材母稿和开场/结尾候选稿的写作。  
> 边界：本设计不覆盖既有 55 页方法论故事板，也不提前压缩到 45 分钟，更不决定最终使用 HTML、PPTX 或 PDF。

## 一、这次重构要解决什么

既有 [`30-完整长版故事板.md`](30-完整长版故事板.md) 以“定义问题—搜索—筛选—验证—归档”为主轴，适合作为研究课程和方法索引，但作为现场经验分享存在三个问题：

1. 方法定义先出现，真实项目较晚才进入，开场缺少可见冲突；
2. WPS、Deck.gl、Web Excel 等完整经历被拆散，讲者的一手经验优势被削弱；
3. 听众容易记住步骤名，却未必记住什么时候应去读源码、Issue、本地依赖或运行画面。

新稿改为**项目驱动的混合叙事**：先讲项目中真实发生的困难和转折，再从故事里抽出方法。不是把所有项目平均介绍一遍，而是让三个主案例构成骨架，其他案例负责补充一种新的资料形态、反馈媒介或长期记忆方式。

全量稿追求“丰富、真实、可筛选”。现场版的时长、页数和案例数量留到冷读与彩排后处理。

## 二、演讲的中心问题

全场围绕一个问题展开：

> 当人把只有自己知道的项目现场告诉 AI 后，搜索、阅读、比较、试验和整理中，还有多少工作可以交给 AI？

这里的“项目现场”包括：

- 以前发生过的问题和已经失败的路线；
- 当前需求与常见需求的差异；
- 公司内部的权限、网络、合规和表达限制；
- 当前安装版本、宿主环境和交付形式；
- 未来可能扩展的业务场景；
- 结果最终由谁使用，以及怎样才算成功。

演讲不主张“这些信息给完后，人就无需思考”。更准确的职责边界是：

> 人提供目标、现场、风险权重和最终验收；AI 扩展候选、寻找证据、执行低成本比较，并把过程变成可审查的资产。

## 三、六幕结构

### 第一幕：AI 给得出答案，但不知道你身处哪里

#### 本幕任务

不用长篇解释“什么是技术调研”，先用几个可感知的失败让观众发现：模型的一般知识与当前项目事实之间存在间隙。

#### 候选故事

1. **ECharts 版本字段**：AI 连改几版配置仍无效果；真正改变结果的是停止猜测，转而读取当前项目 `node_modules` 中的定义。
2. **Deck.gl 页面能开却不转**：完整 HTML 和无报错外观并不能证明目标行为已经实现。
3. **大话骰视觉结果**：没有视觉观察能力的 Agent 可以完成功能，却难以发现页面难看或布局不合理。
4. **Web Excel 模糊需求**：“找一个像 Excel 的库”没有说明究竟需要记录表格还是电子表格。

ECharts 适合作为最短的开场案例，但 hook 尚不在本设计中定稿；关于 AI 的幽默开场仍保留为候选。

#### 本幕产生的判断

> 模型知道大量公共知识，人知道当前项目的现场。

从这里提出全场中心问题，而不是立即展示一张八步骤流程图。

#### 建议画面

- 一张“配置改了但画面不变”的示意图，必须明确标注为示意；
- Deck.gl 失败 HTML 或失败状态截图；
- 大话骰早期页面与后续页面对照；
- 四张小卡片只出现症状，不提前给方法答案。

### 第二幕：WPS——找巨人的肩膀，不等于找到一个巨人

#### 本幕任务

用最完整的一手案例回答：AI 怎样从多个来源取得不同局部资产，并把它们翻译进当前工程，而不是寻找一个可以整包复制的项目。

#### 故事顺序

1. 交代 WPS 插件要解决的问题和宿主限制；
2. 展示最初为什么需要寻找外部参考；
3. 展示候选仓库，而不是直接公布“最佳项目”；
4. 解释为什么没有一个项目同时满足宿主、输出、编辑性和迁移成本；
5. 从不同项目分别提取 API 用法、架构模式、设计参数和验证方法；
6. 将外部经验翻译为 Theme、内容协议、工具接口和 adapter；
7. Prompt 反复失效后，把稳定规则下沉到 schema、规范化和 executor；
8. 区分自动测试、浏览器 mock 与 WPS 真机截图能够证明的范围；
9. 展示最终留下的不只是代码，还有文档、失败路线和门禁。

#### 本幕第一次明确来源分工

| 来源 | 更适合回答的问题 |
|---|---|
| 项目源码 | 实际怎样实现，真实接口和边界在哪里 |
| 项目维护文档 | 作者希望使用者怎样接入与理解项目 |
| 官方线上文档 | 对外承诺支持什么能力和用法 |
| GitHub Issue | 哪些真实环境、版本或边界会失败 |
| PR 与 Commit Message | 行为为什么改变，当时在修复什么 |
| Release 与 Changelog | 哪个版本引入或移除了能力 |
| 本地依赖与类型定义 | 当前项目实际安装版本允许什么 |
| 编译、运行和真机画面 | 当前环境实际上发生了什么 |

后续案例可以再次使用这些来源，但不重复讲完整表格。

#### 本幕产生的判断

> 不要问“哪个项目最好”，要问“哪个来源能补上当前哪个信息缺口”。

#### 建议核心图

```text
仓库 A ── API 用法 ───────┐
仓库 B ── 页面协议 ───────┤
仓库 C ── 设计参数 ───────┼─→ 当前 WPS 项目
仓库 D ── 验证方法 ───────┤
官方文档 ─ 能力边界 ──────┘
```

画面优先使用已归档的 WPS 历史真机截图、仓库裁切和本项目结构图，不用大段代码占满屏幕。

### 第三幕：AI 可以替人完成多少选择

#### 本幕任务

把“AI 辅助调研”从搜索资料推进到候选生成、初筛、对比实验和条件性建议，同时让产品经理也能看到自己的参与位置。

#### 主案例：Web Excel

故事主链：

```text
“找一个 Vue 3 的复杂表格”
→ 记录表格还是电子表格
→ 免费、交互和部署分别意味着什么
→ 14 个候选
→ 许可、维护和能力初筛
→ 6 个同数据、同任务实验
→ 浏览器状态与截图
→ 绑定当前约束的条件性建议
```

必须保留的两个转折：

- HTTP 200 只证明取得了响应，不证明资源形态适合浏览器；
- 拖动操作没有报错，不证明最终记录顺序满足业务目标。

这两个转折共同支持：

> 动作成功与目标达成是两件事。

不把单次加载时间做成库性能排行榜，也不把当次建议推广成永久通用排名。

#### 短案例：B747 货舱资料检索

只讲搜索技术，不展开航空知识：

```text
业务截图
→ 提取罕见代码和行业缩写
→ 低频词共现搜索
→ 尺寸数字指纹
→ 专业资料与构型冲突
→ 带置信度和未知项的几何约束
```

它用于证明代码之外的业务事实也可以被系统调查，产品经理和领域人员同样处在这条链路中。

#### 本幕产生的判断

> 人定义哪些差异会影响决策；AI 可以扩大候选空间、执行第一轮排除，并生成可比较实验。

### 第四幕：失败不是终点，而是下一次搜索的输入

#### 本幕任务

用 Deck.gl 展示调研与开发不是先后两段流程。生成、编译、运行和视觉观察会不断产生新的信息缺口。

#### 主案例：Deck.gl

故事主链：

```text
目标：让对象沿路径正确运动和旋转
→ AI 生成 HTML
→ 页面能打开，但目标行为失败
→ 把现象拆成对象边界、数据语义、生命周期和版本问题
→ 阅读官方文档
→ 查看目标版本源码和相邻实现
→ 运行时出现新错误
→ 新错误生成更精确的搜索词
→ 最小对照实验
→ 浏览器运行、截图和报告裁决
```

具体 accessor、API 名和版本细节默认留在证据库或问答。正文关注“失败怎样改变检索对象”。

#### 横跨案例的反馈闭环

```text
写代码
  ↓
编译 / 类型检查 / lint
  ↓
测试
  ↓
浏览器运行与控制台
  ↓
截图、录屏和视觉观察
  ↓
新的信息缺口
  └────────→ 再搜索、再修改
```

必须诚实说明：这些动作消耗 token 和时间，但消耗换来的是外部反馈，而不是更长、更自信的文本。

#### 可穿插短例

- ECharts：非 TypeScript 项目中错误字段没有提供编译反馈；
- 大话骰：缺少视觉反馈时，功能完成不等于可用或好看；
- 飞机建模：构建通过后，浏览器和渲染仍暴露贴图、开口与布局问题；
- Web Excel：实例状态断言和截图分别发现不同问题。

#### 本幕产生的判断

> AI 的可靠性不来自第一次答对，而来自它能否持续接收到与失败媒介匹配的现实反馈。

### 第五幕：不是 Codex 才能做，而是把它的工作方式拆出来

#### 本幕任务

回答公司主要使用 Claude、轻量 Agent、小模型或网络访问受限时，哪些能力仍然可以复制。避免模型品牌宣传，也不推测厂商内部搜索机制。

#### 只讲可观察到的工作方式

1. 进入项目后读取项目规则和既有文档；
2. 建立源码、依赖、测试和文档地图；
3. 用文件结构、关键词和调用关系缩小范围；
4. 区分公共最新文档与当前安装版本；
5. 在官方文档、源码、Issue、PR 和提交历史之间路由问题；
6. 修改后主动运行编译、测试和浏览器验证；
7. 根据新错误继续调查；
8. 将结论、失败和未知写回项目；
9. 下一次任务先读取这些长期记忆。

#### 两类 Agent 的不同约束粒度

```text
能力较强的模型
目标 + 项目现场 + 工具 + 权限边界 + 验收标准
→ 允许自行规划，并让它审查既有 Skill

能力较小的 Agent
明确来源顺序 + 固定输出字段 + 检查清单
+ 降级路径 + 停止条件
→ 用外部流程补足规划和自检能力
```

对于“不要教 GPT-6 做事情”的说法，演讲采取条件性判断：

- 不用几十条微观动作束缚更强模型；
- 项目特有的事实、权限、风险和验收仍必须明确；
- Skill 不是不可质疑的真理，应由更强模型定期审查是否过时或过度约束；
- 对小模型和轻量 Agent，显式步骤、来源顺序与检查表仍有很大价值。

推荐表达：

> Skill 不负责教模型如何思考，而负责保存这个组织特有的环境、边界、失败经验和验收方式。

#### 公司网络受限时的边界

不声称 Codex 的内部网络搜索机制优于其他模型。只讲可以观察和复刻的降级路线：本地源码、本地依赖、已下载官方资料、内部知识库、仓库历史、包元数据、可访问的结构化接口和最小实验。访问网页失败不等于证据不存在，但绕过访问限制也不自动获得使用权限。

#### 本幕产生的判断

> 真正可迁移的不是一个 AI 品牌，而是“项目上下文、可操作工具、现实反馈和长期记忆”构成的工作环境。

### 第六幕：让一次调查成为下一次调查的起点

#### 本幕任务

将视频、跨会话状态和项目文档串成“研究复利”，并说明无 AI 时也可以沿用这套方法。

#### B站：把不可搜索媒介变成可搜索材料

```text
搜索视频和元数据
→ 低成本筛选
→ 页面失败时寻找结构化数据
→ 字幕优先
→ 无字幕则获取音频并转写
→ 对数字、专名和版本抽样回听
→ 按研究问题重组，而不是保存孤立摘要
```

这只是浏览器研究的一种实例。对其他网站能否复刻，必须服从站点权限、接口条件、服务条款和数据使用边界。

#### Dice：保存负知识

```text
Confirmed  已确认，可作为后续工作的基线
Rejected   已试过或已有证据排除，避免重复走弯路
Unverified 尚未证实，不得冒充事实
```

游戏业务和代码只提供必要背景，重点是研究状态怎样跨会话传递。

#### Tabloom：调研贯穿开发周期

真实用户反馈、模型输出、运行错误和产品边界都会产生新的信息缺口。调研不是实现前的一次准备，而是需求、实现、验证和维护之间的循环。

#### 长期项目记忆

建议最后把全场产物收束为：

- 当前目标与硬约束；
- 来源、版本与访问日期；
- 已确认事实和适用范围；
- 已排除方案与原因；
- 尚未验证的问题；
- 验收方法和真实运行结果；
- 下一位 Agent 可以直接执行的任务。

#### 无 AI 时仍然成立

这套实践可以追溯到信息觅食、假设驱动调试、源码考古、最小复现、测试反馈、决策记录和工程交接。AI 降低了执行成本、扩大了可调查范围，但没有改变一个事实成立所需的证据。

#### 本幕产生的判断

> 真正产生复利的不是一次回答，而是项目从此记住自己为什么这样做。

| Web Excel | 主案例 | 由需求约束驱动候选筛选和可比较实验 |
| Deck.gl | 主案例 | 失败反馈会改变检索对象，开发与调研形成闭环 |
| ECharts | 短故事 | 版本问题要回到当前安装版本，不能继续猜字段 |
| B747 货舱 | 短案例 | 用罕见术语和数字指纹进入陌生专业资料 |
| 飞机建模 | 短案例 | 业务事实、视觉参考与创作性资产必须分层 |

## 五、可拆卸的扩展章节

全量稿允许包含以下内容，现场版再根据节奏决定是否保留。

### 扩展 A：没有 AI 时如何照做

将整套方法映射到传统工程实践，防止演讲被理解成某个产品教程。

### 扩展 B：AI 应替人注意的细节

可列举版本一致性、来源独立性、仓库维护状态、许可证边界、包格式、截图证明范围、转载污染和引用覆盖等检查。正文不逐项教学，而用它说明自动化检查的价值。

### 扩展 C：AI 调研的成本并未消失

讨论源码读取、浏览器运行、截图、测试、文档维护和 Skill 漂移的成本。优化目标不是最少 token，而是把 token 用在会改变决策、暴露错误或留下复用资产的地方。

### 扩展 D：Commit Message 和 Worktree 到底有什么用

作为 Codex 工作方式中的可选小节：

- Commit Message 是变化原因和意图的历史线索，不是天然正确的规范；
- `git log`、`git blame`、PR 和 Issue 可以共同回答“为什么现在长这样”；
- worktree 让多个任务在独立工作目录中并行，减少未完成修改相互污染；
- 这些工程设施的价值是建立可回退、可比较、可审查的实验空间，而不是展示 Git 命令。

此节需要从本项目或可公开项目中选取真实、可展示的提交记录后，才进入逐页稿。不能凭空模拟 Codex 的提交风格。

## 六、逐页演讲稿的固定字段

后续将创建的 `37-全量逐页演讲稿.md` 中，每页采用以下结构：

```markdown
### 页码｜页面标题

**本页唯一判断**

**屏幕文字**

**完整口播**

**画面占位**
- [项目图片] 这里展示……
- [网站/搜索图片] 这里展示……

**证据与边界**

**转场**

**编排标签**：核心 / 可删 / 附录候选
```

画面占位需要区分：

- **项目图片**：本地项目真实截图、运行报告、渲染或文件裁切；
- **网站图片**：将来需要重新核对访问时间与展示权利的网页截图；
- **搜索图片**：搜索过程或候选池截图，必须避免暴露内部或个人信息；
- **示意图**：重新绘制的流程或抽象画面，明确标为示意；
- **待补证**：当前没有可公开原图，不伪造截图。

## 八、写作与删减原则

1. 每个项目先出现可见问题，再解释搜索和解决路径；
2. 每页只承担一个主要判断；
3. 每个完整案例至少有一个失败、一个检索转折和一个可执行产物；
4. 具体 API 字段默认进入证据库或问答，除非该字段本身就是认知转折；
5. 网上大师观点只用于命名、解释或外部支撑，不抢占一手项目故事的主角位置；
6. 不做模型品牌排行榜，不推测不可观察的内部搜索机制；
7. 不把验证写成独立的大型章节，验证始终回答“为什么这条资料足以用于行动”；
8. 先多写案例细节，再通过彩排删除；不在母稿阶段为 45 分钟强行压缩；
9. 图片承担事实、冲突或变化，不作为无信息装饰；
10. 现场版优先保留故事转折，优先删除重复方法定义和次要技术细节。

## 九、成功标准

完成全量稿后，应能回答：

- 听众能否复述三个主案例各自不同的转折？
- 非开发听众能否找到自己需要提供的项目现场信息？
- 开发听众能否知道何时应查看文档、源码、Issue、提交历史或本地依赖？
- 听众能否理解编译、测试、运行和截图为何回答不同问题？
- 公司只提供较小模型或受限 Agent 时，是否仍有一套可以复刻的工作方式？
- 删除任意一个短案例后，六幕主线是否仍然成立？
- 所有具体主张是否都能回到本地项目记录或可核验来源？

如果答案成立，后续 45 分钟现场版就可以通过删案例和合并回响来压缩，而无需重写整套逻辑。
