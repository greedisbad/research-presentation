# 《AI 辅助技术调研实践》六幕全量演讲稿结构设计

> 状态：待讲者审阅。  
> 用途：指导后续全量逐页演讲稿、案例演讲素材母稿和开场/结尾候选稿的写作。  
> 边界：本设计不覆盖既有 55 页方法论故事板，也不提前压缩到 45 分钟，更不决定最终使用 HTML、PPTX 或 PDF。

## 一、这次重构要解决什么

既有 [`30-完整长版故事板.md`](30-完整长版故事板.md) 以“定义问题—搜索—筛选—验证—归档”为主轴，适合作为研究课程和方法索引，但作为现场经验分享存在三个问题：

1. 方法定义先出现，真实项目较晚才进入，开场缺少可见冲突；
2. WPS、Deck.gl、Web Excel 等完整经历被拆散，讲者的一手经验优势被削弱；
3. 听众容易记住步骤名，却未必记住什么时候应去读源码、Issue、本地依赖或运行画面。

新稿改为**项目驱动的混合叙事**：先讲项目中真实发生的困难和转折，再从故事里抽出方法。不是把所有项目平均介绍一遍，而是让 B747、WPS、Web Excel 和 Deck.gl 四个锚点构成骨架；Deck.gl 放在后半场，其他项目只补充一种新的资料形态、反馈媒介或长期记忆方式。

全量稿追求“丰富、真实、可筛选”。现场版的时长、页数和案例数量留到冷读与彩排后处理。

## 二、演讲的中心问题

全场围绕一个问题展开：

> 当人把只有自己知道的项目现场告诉 AI 后，搜索、阅读、比较、试验和整理中，还有多少工作可以交给 AI？

这里的“项目现场”包括：

- 以前发生过的问题和已经失败的路线；
- 当前需求与常见需求的差异；
- 公司内部的权限、网络、合规和表达限制；
- 当前安装版本、宿主环境和交付形式；
- 未来可能扩展的业务场景；
- 结果最终由谁使用，以及怎样才算成功。

演讲不主张“这些信息给完后，人就无需思考”。更准确的职责边界是：

> 人提供目标、现场、风险权重和最终验收；AI 扩展候选、寻找证据、执行低成本比较，并把过程变成可审查的资产。

## 三、六幕结构

### 第一幕：AI 很聪明，但它不知道你的现场

#### 本幕任务

让非技术听众也能先进入问题：AI 可以迅速给出一个完整答案，却不知道公司历史、当前约束、真实使用者和未来场景。开场不展示方法目录，也不从 Deck.gl 等技术细节起步。

#### 三个 hook 候选及建议用法

1. **主开场候选：AI 打工人**

   > AI 终于过上了打工人梦想中的生活：上级必须把需求说清楚，工作出错领导全权负责，钱到位才上班，少一分、晚一秒都罢工。它还会摸鱼偷懒——而且你骂它也要花钱。

   这段最适合作为正式开场，因为人人能理解，而且能自然转入“指令明确并不等于结果可靠”。口播时应收紧长度，不把“AI 偷懒”说成拟人化事实。

2. **成本章节回响：免费的脑子**

   > 卧槽，惊奇发现：用自己的脑子写代码不烧 token，是免费的。

   适合放在第四或第五幕谈验证成本时，作为节奏缓冲，不建议承担中心论点。

3. **记忆章节回响：memory 双关**

   > AI has made memory more expensive.
   > 爱让记忆变得更加珍贵——AI 让存储变得更加昂贵。

   适合放在第六幕谈上下文、项目记忆和资料积累时。英文 `memory` 同时指记忆与存储，中文翻译作为故意的文字游戏呈现。

三个段子可以分别出现，不必竞争唯一名额；现场版彩排后再判断是否过密。

#### 人人都能理解的短故事

- Web Excel：“找一个像 Excel 的库”没有说明实际要完成什么工作；
- ECharts：AI 连续改配置但画面没有变化，后来才回到当前安装版本；
- B747：面对一张满是行业符号的货舱图，第一步不是猜，而是弄清这些符号叫什么。

#### 本幕产生的判断

> 模型知道大量公共知识，人知道当前项目的过去、现在和未来。

### 第二幕：B747——从一张看不懂的图，找到能行动的资料

#### 本幕任务

利用航空公司听众熟悉的业务对象，展示 AI 如何进入一个资料稀疏、术语陌生、版本和构型复杂的领域。内容可以比原设计多展开一点，但目标仍是讲搜索方法，而不是教授货机装载知识。

#### 故事顺序

1. 3D 配载需求需要货舱位置、轮廓和尺寸，普通图片搜索不能直接给出可建模数据；
2. 从业务图中识别 `A1/A2/B1`、`LR/LL/PL`、`11P`、`PA1/PA2/PMD/H4M/HPL/PEB` 等低频符号；
3. 将罕见代码、机型、货舱、位置和轮廓组合成查询，而不是反复搜索中文需求原句；
4. 当术语仍然模糊时，用尺寸和数字组合作为“指纹”反查资料；
5. 区分航空公司资料、制造商材料、装载手册、二手图表和搜索摘要分别能证明什么；
6. 遇到 SF、ERF、航空公司构型等差异时保留冲突，不强行拼成唯一答案；
7. 将结论转换成几何约束、置信度、来源和未知项，供后续建模与业务确认。

#### 建议画面

- 原始货舱轮廓图或合规裁切；
- 图中低频代码被逐个圈出的动画；
- 查询词从自然语言变成“代码共现”的过程；
- 不同来源的构型冲突并排；
- 最终几何约束示意，而非密集参数表。

#### 本幕产生的判断

> 搜索的第一项技术，不是会写长 Prompt，而是从陌生材料里找出真正能打开资料库的术语和数字指纹。

### 第三幕：WPS——找巨人的肩膀，不等于找到一个巨人

#### 本幕任务

用最完整的一手工程案例回答：AI 怎样从多个来源取得不同局部资产，并把它们翻译进当前工程，而不是寻找一个可以整包复制的项目。

#### 故事顺序

1. 交代 WPS 插件要解决的问题和宿主限制；
2. 展示候选仓库，而不是直接公布“最佳项目”；
3. 解释为什么没有一个项目同时满足宿主、输出、编辑性和迁移成本；
4. 从不同项目分别提取 API 用法、架构模式、设计参数和验证方法；
5. 将外部经验翻译为 Theme、内容协议、工具接口和 adapter；
6. Prompt 反复失效后，把稳定规则下沉到 schema、规范化和 executor；
7. 区分自动测试、浏览器 mock 与 WPS 真机截图能够证明的范围；
8. 展示最终留下的不只是代码，还有文档、失败路线和门禁。

#### 本幕第一次明确来源分工

| 来源 | 更适合回答的问题 |
|---|---|
| 项目源码 | 实际怎样实现，真实接口和边界在哪里 |
| 项目维护文档 | 作者希望使用者怎样接入与理解项目 |
| 官方线上文档 | 对外承诺支持什么能力和用法 |
| GitHub Issue | 哪些真实环境、版本或边界会失败 |
| PR 与 Commit Message | 行为为什么改变，当时在修复什么 |
| Release 与 Changelog | 哪个版本引入或移除了能力 |
| 本地依赖与类型定义 | 当前项目实际安装版本允许什么 |
| 编译、运行和真机画面 | 当前环境实际上发生了什么 |

#### 本幕产生的判断

> 不要问“哪个项目最好”，要问“哪个来源能补上当前哪个信息缺口”。

#### 建议核心图

```text
仓库 A ── API 用法 ───────┐
仓库 B ── 页面协议 ───────┤
仓库 C ── 设计参数 ───────┼─→ 当前 WPS 项目
仓库 D ── 验证方法 ───────┤
官方文档 ─ 能力边界 ──────┘
```

### 第四幕：人给标准，AI 替我们扩大选择

#### 本幕任务

用 Web Excel 展示候选生成、初筛、对比实验和条件性建议。前半仍然是非技术听众可理解的“选择问题”，后半再逐渐进入工程验证。

#### 主案例：Web Excel

```text
“找一个 Vue 3 的复杂表格”
→ 记录表格还是电子表格
→ 免费、交互和部署分别意味着什么
→ 14 个候选
→ 许可、维护和能力初筛
→ 6 个同数据、同任务实验
→ 浏览器状态与截图
→ 绑定当前约束的条件性建议
```

保留两个转折：HTTP 200 不等于拿到了浏览器可用的资源；拖动没有报错不等于最终行顺序符合业务目标。

由此再扩大到人的职责：人提供公司以前踩过的坑、不能使用的方案、当前需求差异和未来场景；AI 可以完成大量候选展开、低风险排除和重复比较。不能把这种分工说成人从此无需思考，最终权重和风险仍由人负责。

#### 一句带过的 B站尝试

> 我也试过让 AI 搜索 B站视频、下载音频、转成文字再总结。它适合快速了解主流观点和发现关键词，但转写得到的是候选材料，不是经过核验的专业结论。

不再把 B站扩成独立章节。只有当现场需要说明“网页之外还有视频和结构化数据”时，才追加一张流程小图。

#### 本幕产生的判断

> 人定义哪些差异会影响决策；AI 可以替人扩大候选、执行初筛，并把选项变成可比较的实验。

### 第五幕：Codex 怎样行动，以及怎样把这种能力搬回公司

#### 本幕任务

这是后半场技术浓度最高的一幕。先从多个 `IMPLEMENTATION-NOTES.md` 和复盘文档归纳 Codex 的可观察优势，再讨论公司使用 Claude CLI、小模型或网络受限 Agent 时如何复制这些能力。Deck.gl 放在本幕作为最完整的闭环案例，因此出现位置明显后移。

#### 第一组：Deck.gl 展示失败驱动的研究闭环

```text
AI 生成 HTML
→ 页面能打开，但目标行为失败
→ 把现象拆成对象、数据、生命周期和版本问题
→ 官方文档
→ 目标版本源码与相邻实现
→ 运行时产生新错误
→ 新错误生成更精确的查询
→ 最小对照实验
→ 浏览器、截图和运行报告裁决
```

正文不讲具体 accessor 名，重点是失败如何改变下一步搜索对象。

#### 第二组：从其他项目抽取 Codex 的能力表现

后续写稿必须回读以下原始复盘，而不是只依据本项目摘要：

- `/Users/wang/Documents/ChatGPT/deckgl-rotation/IMPLEMENTATION-NOTES.md`
- `/Users/wang/Documents/ChatGPT/aircraft-modeling/IMPLEMENTATION-NOTES.md`
- `/Users/wang/Documents/ChatGPT/web-excel/IMPLEMENTATION-NOTES.md`
- Dice 的三份 session retrospective
- Tabloom 的本地研究与决策轨迹材料

计划提取的能力维度包括：

1. 进入项目后先读取规则、文档和已有实现；
2. 建立源码、依赖、测试和资料地图；
3. 不把第一个答案当结论，而是保留候选假设；
4. 根据目标版本查看本地依赖、源码、Issue、PR 和提交历史；
5. 主动调用编译、类型检查、lint、测试和浏览器；
6. 用控制台、实例状态、截图和渲染结果接收不同层次的反馈；
7. 工具通道失败时切换到 CLI、本地文件或最小实验；
8. 下载或生成任务需要的模型、资源和中间资产；
9. 将已确认、已排除和待验证内容写回项目；
10. 使用独立工作目录、提交和可回退历史控制实验风险。

飞机建模、Dice 和 Tabloom 不再分别展开成完整案例：

- 飞机建模用于说明资料可进入参数化模型，构建后仍需视觉检查；
- Dice 用于说明跨会话保存 Confirmed / Rejected / Unverified；
- Tabloom 用于说明用户反馈和真实模型输出会继续生成信息缺口；
- 大话骰截图用于说明缺少视觉反馈时，“功能完成”仍可能很难看。

#### 第三组：编译、测试和视觉反馈为什么值得花 token

```text
写代码
→ 编译 / 类型检查 / lint
→ 测试
→ 浏览器运行与控制台
→ 截图、录屏和视觉观察
→ 新的信息缺口
→ 再搜索、再修改
```

这里插入“用自己的脑子写代码不烧 token”作为笑话，然后认真说明：这些动作确实昂贵，但 token 换来的是现实反馈，而不是更长、更自信的回答。

#### 第四组：搬回公司的方式

```text
能力较强的模型
目标 + 项目现场 + 工具 + 权限边界 + 验收标准
→ 允许自行规划，并让它审查既有 Skill

能力较小的 Agent / CLI
明确来源顺序 + 固定输出字段 + 检查清单
+ 降级路径 + 编译/测试/浏览器反馈 + 停止条件
→ 用外部工作环境补足规划和自检能力
```

不宣称 Codex 的内部网络搜索机制优于其他模型。公司网络受限时，可复刻的是本地源码、本地依赖、内部文档、仓库历史、已下载官方资料、包元数据、允许访问的结构化接口和最小实验。

“不要教 GPT-6 做事”作为段子和条件性判断出现：能力强的模型不需要几十条微观动作，但仍需要项目事实、权限边界和验收标准；既有 Skill 也应让更强模型反向审查是否过时。对较小模型，明确流程仍然有价值。

#### 本幕产生的判断

> 真正可迁移的不是 Codex 这个名字，而是“项目上下文、可操作工具、现实反馈、隔离实验和长期记忆”构成的工作环境。

### 第六幕：今天还要学，因为这种交互方式正在到来

#### 本幕任务

回到人的位置，收束公司实践、长期记忆和未来交互方式。语气可以比传统总结更轻松，不做夸张的产品预测。

#### 从当下到未来

可以使用讲者的诙谐表达：

> 这大概就是未来的软件交互方式。学得慢也不用太焦虑，几个月后工具可能自己就补上来了；但今天需求还在排期里，所以我们还是得先学会怎么做。

“几个月后”只能作为幽默和主观预期，不能写成确定的行业时间表。

#### 长期项目记忆

- 当前目标与硬约束；
- 来源、版本与访问日期；
- 已确认事实和适用范围；
- 已排除方案与原因；
- 尚未验证的问题；
- 验收方法和真实运行结果；
- 下一位 Agent 可以直接执行的任务。

在这里使用 `AI has made memory more expensive` 的双关，转入真正的结论：上下文和存储更贵了，但被维护的项目记忆也更有价值。

#### 无 AI 时仍然成立

信息觅食、假设驱动调试、源码考古、最小复现、测试反馈、决策记录和工程交接都早于生成式 AI。AI 降低了这些动作的执行成本并扩大了范围，没有改变事实需要证据、工程需要验收。

#### 最终责任边界

人无需亲自研究所有候选，但必须提供 AI 不知道的过去、现在和未来，并对最终选择负责。AI 可以替我们找、读、比较、试验和记录，不能替组织承担“为什么这已经足以行动”的责任。

#### 本幕产生的判断

> 真正产生复利的不是一次回答，而是项目从此记住自己为什么这样做。

## 五、可拆卸的扩展章节

全量稿允许包含以下内容，现场版再根据节奏决定是否保留。

### 扩展 A：没有 AI 时如何照做

将整套方法映射到传统工程实践，防止演讲被理解成某个产品教程。

### 扩展 B：AI 应替人注意的细节

可列举版本一致性、来源独立性、仓库维护状态、许可证边界、包格式、截图证明范围、转载污染和引用覆盖等检查。正文不逐项教学，而用它说明自动化检查的价值。

### 扩展 C：AI 调研的成本并未消失

讨论源码读取、浏览器运行、截图、测试、文档维护和 Skill 漂移的成本。优化目标不是最少 token，而是把 token 用在会改变决策、暴露错误或留下复用资产的地方。

### 扩展 D：Commit Message 和 Worktree 到底有什么用

作为 Codex 工作方式中的可选小节：

- Commit Message 是变化原因和意图的历史线索，不是天然正确的规范；
- `git log`、`git blame`、PR 和 Issue 可以共同回答“为什么现在长这样”；
- worktree 让多个任务在独立工作目录中并行，减少未完成修改相互污染；
- 这些工程设施的价值是建立可回退、可比较、可审查的实验空间，而不是展示 Git 命令。

此节需要从本项目或可公开项目中选取真实、可展示的提交记录后，才进入逐页稿。不能凭空模拟 Codex 的提交风格。

## 六、逐页演讲稿的固定字段

后续将创建的 `37-全量逐页演讲稿.md` 中，每页采用以下结构：

```markdown
### 页码｜页面标题

**本页唯一判断**

**屏幕文字**

**完整口播**

**画面占位**
- [项目图片] 这里展示……
- [网站/搜索图片] 这里展示……

**证据与边界**

**转场**

**编排标签**：核心 / 可删 / 附录候选
```

画面占位需要区分：

- **项目图片**：本地项目真实截图、运行报告、渲染或文件裁切；
- **网站图片**：将来需要重新核对访问时间与展示权利的网页截图；
- **搜索图片**：搜索过程或候选池截图，必须避免暴露内部或个人信息；
- **示意图**：重新绘制的流程或抽象画面，明确标为示意；
- **待补证**：当前没有可公开原图，不伪造截图。

## 八、写作与删减原则

1. 每个项目先出现可见问题，再解释搜索和解决路径；
2. 每页只承担一个主要判断；
3. 每个完整案例至少有一个失败、一个检索转折和一个可执行产物；
4. 具体 API 字段默认进入证据库或问答，除非该字段本身就是认知转折；
5. 网上大师观点只用于命名、解释或外部支撑，不抢占一手项目故事的主角位置；
6. 不做模型品牌排行榜，不推测不可观察的内部搜索机制；
7. 不把验证写成独立的大型章节，验证始终回答“为什么这条资料足以用于行动”；
8. 先多写案例细节，再通过彩排删除；不在母稿阶段为 45 分钟强行压缩；
9. 图片承担事实、冲突或变化，不作为无信息装饰；
10. 现场版优先保留故事转折，优先删除重复方法定义和次要技术细节。

## 九、成功标准

完成全量稿后，应能回答：

- 听众能否复述 B747、WPS、Web Excel 和 Deck.gl 四个锚点各自不同的转折？
- 非开发听众能否找到自己需要提供的项目现场信息？
- 开发听众能否知道何时应查看文档、源码、Issue、提交历史或本地依赖？
- 听众能否理解编译、测试、运行和截图为何回答不同问题？
- 公司只提供较小模型或受限 Agent 时，是否仍有一套可以复刻的工作方式？
- 删除任意一个短案例后，六幕主线是否仍然成立？
- 所有具体主张是否都能回到本地项目记录或可核验来源？

如果答案成立，后续 45 分钟现场版就可以通过删案例和合并回响来压缩，而无需重写整套逻辑。
