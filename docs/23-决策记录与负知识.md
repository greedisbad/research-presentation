# 决策记录与负知识：让下一个 Agent 不必重新踩坑

## 核心判断

源码通常能回答“系统现在怎么做”，却很难独立回答“当时为什么这样做、哪些方案试过、什么条件会使决定失效”。如果 AI 每次只读当前代码，它会把历史约束重新当成开放问题，也可能把已失败路线包装成新建议。

技术调研的长期产物因此至少要保存四类内容：

```text
事实：我们确认了什么
决策：在什么上下文中选择了什么
负知识：什么路线在什么条件下失败
未知：还缺什么证据、何时应重新调查
```

## 一、ADR 保存的不是结论，而是结论成立时的上下文

Michael Nygard 在 2011 年提出用短小、模块化的 Architecture Decision Record 保存重要架构决策。其格式包含 Title、Context、Decision、Status 和 Consequences；被后续决策替代的记录不删除，而标记为 superseded 并指向替代项。[原始文章](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)

对 AI 技术调研尤其有用的是三个原则：

1. **一条记录只承担一个重要决策**：便于按需检索，不必把整份项目史塞入上下文。
2. **Context 与 Decision 分开**：外部事实、局部约束和人的选择不会混成“唯一正确答案”。
3. **旧决定不删除**：上下文变化时，人和 Agent 能判断是继续接受，还是有理由重新打开。

Nygard 的文章是经验型方法，不是受控研究；它适合提供记录格式，不用于证明具体效率收益。

## 二、开发者真正需要的是 rationale，而不只是 diff

Safwan 与 Servant 对 code commit rationale 的混合方法研究指出，开发者在多类软件任务中需要寻找变更理由，并把 rationale 分解为多个组成部分；研究也讨论了导致开发者放弃寻找理由的因素。[Journal of Systems and Software 论文](https://doi.org/10.1016/j.jss.2022.111320)

更早的 Microsoft 开发观察同样发现：当源码不能解释设计缘由时，开发者经常转向同事；获得的信息很有价值，却很少再次写入持久记录。[Software Development at Microsoft Observed](https://www.microsoft.com/en-us/research/wp-content/uploads/2016/02/tr-2005-140.pdf)

这两类研究共同支持：Git 历史和源码是证据入口，但 rationale 不会自动从 diff 中出现。Agent 可以帮助检索 commit、Issue、PR 和讨论，却仍需要把“观察到的变更”与“作者明确表达的原因”分开。

## 三、负知识必须绑定失败条件

低质量负知识通常写成：

> 方案 A 不行。

它会制造两个问题：未来环境变化后没人敢重试；或者 Agent 因为看不到原因，换个名字再次提出同一路线。

合格记录应写成：

```yaml
proposal: 使用 Range.InsertAfter("\\r" + text) 新增 Word 段落
environment: WPS Word 目标运行时，2026-05 本地项目
expected: getParagraphs 能看到新增段落
observed: 文本附加到已有段落末尾，段落数量不变
evidence: 运行时调试记录 + 修复后的 adapter 代码
decision: 改用 InsertParagraphAfter 后设置新段落文本
reopen_when: WPS 目标 API 或版本明确改变该行为
```

关键不是记录“失败”，而是让失败可重现、可质疑、可在条件变化后重新评估。

## 四、为什么不能只保留聊天记录

完整聊天对当事人有帮助，但对新 Agent 存在几个问题：

- 事实、建议、猜测和用户决定混在一起；
- 相同结论可能在数十轮后被推翻；
- 上下文大，关键约束难以检索；
- 失败原因未必出现在最终摘要；
- 新 Agent 无法知道哪一条是当前有效状态。

聊天应当保留为可追溯原始记录；同时生成面向行动的压缩层：

| 文件 | 保存什么 | 不保存什么 |
|---|---|---|
| `FACTS.md` | 带来源的已确认事实 | 未裁决猜测 |
| `DECISIONS.md` / ADR | 上下文、选择、状态、后果 | 全部讨论流水账 |
| `LEARNINGS.md` | 失败现象、原因、修复和复用条件 | 无条件的“最佳实践” |
| `OPEN-QUESTIONS.md` | 未知、风险、下一步证据 | 已解决事项 |
| `TASK-BRIEF.md` | 下一执行者所需目标、边界和验收 | 整段聊天转抄 |

这些文件是“索引与当前状态”，原始聊天、源码、日志和外部来源仍是按需回读的证据层。

## 五、让 AI 自动生成记录时的门禁

AI 可以在会话结束时提出记录草案，但不应自动把所有解释升级为事实。

### 事实门

- 是否有文档、源码、日志、实验或用户确认？
- 版本和环境是否写清？
- 这是观察，还是对观察的解释？

### 决策门

- 谁作出决定？
- 当时有哪些备选？
- 选择依据与代价是什么？
- 状态是 proposed、accepted、deprecated 还是 superseded？

### 负知识门

- 预期行为和实际行为分别是什么？
- 是否保存了失败输出或至少可定位记录？
- 是方案本身不可行，还是当前版本/条件不可行？
- 什么变化会触发重新验证？

### 交接门

- 新 Agent 能否不依赖隐含聊天上下文开始工作？
- 明确列出禁止重复路径了吗？
- 下一步的验收命令或可观察结果是什么？

## 六、与本地案例的连接

### WPS：从运行事故到项目级规则

- `09-LEARNINGS.md` 保存 `InsertAfter`、批量调用、Ribbon 和日志工具问题；
- 根 `AGENTS.md` 把跨阶段有效的约束提升为启动即读取的规则；
- Phase 07 不删除失败方案，而将 PPT 图表路径标记为放弃并保留原因。

这是一条完整的沉淀路径：

```text
运行异常 → 定位证据 → 修复 → Learnings → 项目规则 → 后续 Agent 约束
```

### Dice：用 Confirmed / Rejected / Unverified 维持跨会话状态

Dice 复盘最适合做短例子：游戏实现本身不重要，重要的是新会话能读到哪些假设已确认、哪些被拒绝、哪些尚待验证，以及下一任务的风险与验收标准。

## 七、推荐进入演说的内容

推荐度：A，适合接在案例之后作为“如何让一次调研产生复利”。

主 PPT 只保留：

1. **源码记录现在，决策记录为什么。**
2. **失败路线不能只写“不行”，必须绑定版本、条件、观察和重开触发器。**
3. **聊天是原始记录，FACTS / DECISIONS / LEARNINGS / OPEN QUESTIONS 是 Agent 可用的当前状态。**

详细 ADR 格式与 YAML 示例放附录。

## 八、证据边界

- ADR 的模块化格式来自实践者经验，不能单独证明适合所有团队。
- 软件知识管理研究发现大量工作仍是案例和经验报告，不能给出一个普遍最优记录工具。
- 负知识减少重复搜索目前在本项目中尚无对照测量；演讲只把它作为可检查的设计原则。
- 过度记录也会制造维护成本。只记录会改变后续决策、实现或验证的重要事项。
