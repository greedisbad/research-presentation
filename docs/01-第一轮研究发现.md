# 第一轮研究发现

## 1. 最值得讲的不是“AI 搜索”，而是“证据如何流向代码”

普通搜索的终点是链接列表；技术调研的终点应是一个可以被工程验证的决策。建议把整场分享的评价标准从“AI 找了多少资料”改为：

- 是否覆盖了不同方案和反例；
- 是否能追溯到官方文档、源码或论文；
- 是否明确适用版本和边界；
- 是否转化成接口、测试、约束或实现计划；
- 是否记录失败路径，避免团队再次踩坑。

## 2. 推荐的七阶段流水线

| 阶段 | AI 负责 | 人负责 | 主要产物 |
|---|---|---|---|
| 问题建模 | 拆分问题、生成术语与查询矩阵 | 定义真正要做的决策 | Research brief |
| 广度搜索 | 多查询、多来源并行发现候选 | 确认范围和停止条件 | 候选池 |
| 分层筛选 | 去重、聚类、按规则初评 | 调整权重、识别遗漏 | 来源评分表 |
| 深度取证 | 阅读源码、文档、转写视频 | 判断语境和可信度 | 来源卡、代码定位 |
| 交叉验证 | 寻找支持、冲突与版本差异 | 对关键结论做最终裁决 | 证据矩阵 |
| 工程转化 | 生成方案、接口、测试和实验 | 选择取舍并运行验证 | Spike、PLAN、测试 |
| 能力沉淀 | 总结模式、生成 Skill 与模板 | 删除偶然经验、保留通用规则 | Skill、脚本、索引 |

## 3. WPS 案例的最佳叙事

WPS 案例不是“AI 帮我写了插件”，而是一条长期演化的参考复用链：

1. 先从官方 API、类型声明和既有项目定位可用能力；
2. 调研 11 个 PPT 相关项目，并按对 WPS 的实际价值评级；
3. 从不同项目分别借用布局、主题、Agent 流程和质量门禁，而不是照搬整个项目；
4. 把候选方案按环境约束筛成 A/B/C 三条可行路径；
5. 用浏览器适配器、类型检查、单元测试和 WPS 真机实验验证；
6. 记录不可行方案，例如 PPT 图表数据注入不可靠；
7. 把踩坑结果写回 `AGENTS.md` 和阶段 Learnings，成为下一轮开发的输入。

这个案例尤其适合说明三个观点：

- **不要搜索“最终答案”，要搜索“可借用的局部结构”。**
- **文档缺失时可以从相邻生态推断，但推断必须经过运行时实验。**
- **失败结论也是高价值资产，因为它缩小了未来搜索空间。**

## 4. 视频案例的最佳叙事

视频案例展示了另一类问题：信息不在可搜索文本里。现有材料已经包含：

- 7 个维度、约 65 个关键词的查询矩阵；
- 标题、简介、评论、字幕、播放量等分层字段；
- 对“教程、工作流、提示词、项目地址”等高价值信号的筛选规则；
- 字幕不可用时转向音频下载与 ASR 的降级路径；
- 按工具、引擎、工作流和资源重新组织结果；
- 把整个流程沉淀成可复用 Skill。

演示时应避免展示大量视频卡片，更适合选择一个代表视频，展示它如何经历：

> 搜索命中 → 元数据初筛 → 音频转写 → 结构化提取 → 找到项目地址/提示词/工作流 → 与官方资料或源码核验。

## 5. 第一轮外部证据带来的补充

- OpenAI 对 Deep Research 的官方描述明确包含规划、多步搜索、来源控制、结构化报告和引用复核。这能支持“研究是过程，不是一次问答”。
- GitHub 官方文档建议先理解仓库结构，再用仓库限定词和独特字符串定位实现。这能支持“从行为或界面反查源码”的具体技巧。
- Wohlin 的软件工程系统文献研究指出，可通过向后参考文献与向前引用做 snowballing。这可迁移成技术调研中的“从一个高质量种子项目扩展生态图谱”。
- RAG 原始论文指出，纯参数化模型在知识访问、来源追溯和知识更新方面存在问题。这为“关键事实必须接入外部证据”提供理论背景。
- NotebookLM 官方说明展示了视频、音频、网页、PDF 等多模态来源如何变成基于来源的问答，但也明确要求信息必须存在于导入来源中。这适合说明“先构建语料，再提问”的工作方式。

## 6. 后续重点

下一轮不继续无限扩充工具清单，而是补齐四块内容：

1. 技术资料的来源层级与评分模型；
2. 查询矩阵、滚雪球搜索和停止条件；
3. AI 总结的验证清单与反幻觉策略；
4. 两个案例中可以上台展示的真实文件、差异和失败实验。
