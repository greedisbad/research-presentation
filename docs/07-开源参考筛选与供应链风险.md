# 开源参考筛选与供应链风险

技术调研里最危险的一次跳跃，是从“找到了相似仓库”直接跳到“把它装进项目”。AI 可以扩大候选池、比较实现和生成适配代码，但不能替团队拥有许可证判断、依赖风险和最终验收责任。

## 1. 先区分三种使用关系

| 使用关系 | 实际动作 | 至少要检查什么 | 风险级别 |
|---|---|---|:---:|
| 阅读学习 | 阅读结构、API 用法和设计思路，不复制表达 | 来源真实性、版本匹配、方案是否可运行 | 低 |
| 复制或改写 | 复制代码、配置、测试或文档片段 | 许可证、版权声明、归属要求、兼容性 | 中 |
| 引入依赖 | 安装包、镜像、Action、二进制或服务 | 上述全部，加漏洞、维护、发布链、传递依赖和退出成本 | 高 |

“GitHub 上公开可见”不等于“可以任意复制”。GitHub 官方明确说明：没有许可证时，默认版权仍然适用；平台条款允许他人查看和 fork，并不自动授予复制、分发或制作衍生作品的权利。因此，AI 找到的无许可证代码只能作为阅读线索，不能因为生成结果换了变量名就视为风险消失。

## 2. 候选仓库九项评分

Stars 和搜索排名只适合发现候选，不适合决定采用。每个进入短名单的项目至少按以下九项评价：

| 维度 | 核心问题 | 可观察证据 |
|---|---|---|
| 问题相关性 | 是否解决同一个问题，而非只有相似 UI 或关键词？ | README、示例、核心 symbol、测试用例 |
| 运行环境匹配 | 语言、框架、宿主、版本、权限模型是否一致？ | manifest、lockfile、release notes、CI matrix |
| 实现可解释性 | 能否定位“它为什么工作”的具体代码路径？ | 入口、调用链、错误处理、测试 |
| 许可证可用性 | 允许复制、修改、分发和商业使用吗？ | 根目录 LICENSE、文件头、依赖许可证 |
| 维护状态 | 最近是否仍在处理缺陷与发布？ | release、commit、issue/PR 响应，而非单看更新时间 |
| 工程质量 | 是否有测试、CI、代码评审和可复现构建？ | workflows、测试目录、贡献规则 |
| 安全状态 | 已知漏洞、危险 workflow、过宽 token 权限如何？ | OSV、advisory、Scorecard、依赖图 |
| 集成成本 | 需要改多少接口和架构假设？ | spike、最小适配器、变更面估算 |
| 可逆性 | 如果判断错了，能否替换或回滚？ | adapter 边界、feature flag、锁定版本、替代方案 |

一个可用的粗略门槛是：许可证不清、关键版本不匹配、核心路径不可解释三者任一出现时，不进入“复制/依赖”阶段，只保留为发现线索。

## 3. 让 AI 搜“实现证据”，而不是搜“最佳项目”

GitHub Code Search 的官方语法支持布尔运算、精确短语、正则以及 `repo:`、`language:`、`path:`、`symbol:`、`content:`、`license:`、`is:` 等限定符。好的委托不是“找最好的 WPS 插件”，而是给 AI 一组可验证的查找任务：

```text
repo:owner/project "CreateTaskPane"
repo:owner/project path:/src/ "InsertParagraphAfter"
language:typescript symbol:WpsSlideAdapter
language:javascript "GetActiveObject" NOT path:test
license:MIT "ribbon.xml" NOT is:archived
```

使用时要注意：

- `symbol:` 找定义，不等同于找全部引用；语言支持也不完全一致。
- 搜到字符串只证明它存在，不能证明调用路径在目标版本有效。
- AI 应返回文件、symbol、commit/release、许可证和最小证据片段，而不是只给仓库主页。
- 搜索语法和索引能力会变化，演示前重新验证查询。

## 4. 从“源码参考”升级为“依赖”时加一道闸门

GitHub Dependency Graph 会从 manifest 与 lockfile 识别直接和传递依赖，并可连接安全告警与 SBOM；它适合回答“项目实际上带进来了什么”。OpenSSF Scorecard 自动检查维护状态、分支保护、代码评审、固定依赖、危险 workflow、token 权限、签名发布等供应链信号；它是调查入口，不是安全认证。OSV 则能按包版本或 commit 查询来自权威漏洞库的受影响范围，适合对具体锁定版本做机器化核验。

建议把引入闸门写成固定步骤：

1. 从 lockfile 记录精确版本，不只记录包名。
2. 查看直接依赖与关键传递依赖。
3. 用 OSV/生态 advisory 查询该版本，不以“最新版没有新闻”代替核验。
4. 查看 Scorecard 的单项证据，不只抄总分。
5. 核对 release tag、源码 commit 与下载产物是否能对应。
6. 运行最小 spike 和现有测试，验证目标平台行为。
7. 记录采用理由、未解决风险、升级与退出策略。

## 5. AI 与人的责任边界

AI 适合批量做：候选扩展、语法化查询、manifest/lockfile 摘要、许可证文件定位、漏洞 API 查询、不同实现的结构化对比、生成最小 spike。

人必须负责：确认业务使用方式、判断许可证义务、接受剩余安全风险、识别组织合规要求、决定是否让依赖进入生产，以及对运行结果签字验收。涉及真实法律判断时，应由组织的法务或开源治理流程确认。

## 6. 可直接用于 WPS 案例的验收表

- [ ] 参考项目解决的是同一种 WPS 宿主与 API 场景。
- [ ] 关键能力能定位到具体文件、symbol 和调用链。
- [ ] 官方 WPS 文档或目标客户端运行实验至少提供一条独立验证。
- [ ] 复制内容的许可证和归属要求清楚。
- [ ] 不把 star、README 宣称或 AI 摘要当成运行证据。
- [ ] 第三方包已检查精确版本、传递依赖和已知漏洞。
- [ ] 适配层将参考实现与业务逻辑隔离，失败时可替换。
- [ ] 已记录“不采用”的候选及原因，避免团队重复踩坑。
