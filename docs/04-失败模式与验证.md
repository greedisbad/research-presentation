# 失败模式与验证

## 1. AI 搜到了来源，但来源没有支持结论

最常见的问题不是没有引用，而是“引用存在但不蕴含主张”。验证时应：

1. 把回答拆成原子主张；
2. 打开每个关键引用；
3. 找到直接支持该主张的段落、代码或数据；
4. 记录来源的版本、范围和限制；
5. 无法直接支持时，将结论降级为推断或删除。

Google DeepMind 的 SAFE 方法正是通过拆分事实、逐项搜索和判定支持关系来评估长回答事实性。[Long-form factuality](https://deepmind.google/research/publications/85420/)

ALCE 基准进一步把评估拆为流畅性、回答正确性和引用质量；在其 ELI5 数据集上，即使当时最佳系统也有约一半内容缺少完整引用支持。重点不是沿用这个旧数值评价今天的产品，而是认识到“生成了引用”和“全部陈述被引用支持”是两项不同能力。[Gao et al., EMNLP 2023](https://aclanthology.org/2023.emnlp-main.398/)

## 2. 模型记忆被当成当前事实

模型参数中的知识存在版本滞后、来源不可见和长尾错误问题。RAG 原始论文明确把来源追溯和知识更新视为纯参数化模型的开放问题。[Lewis et al., 2020](https://arxiv.org/abs/2005.11401)

应对方式：产品能力、价格、API、版本、Stars、许可证和维护状态必须重新检索；高风险事实优先看一手来源。

## 3. 资料很多，但没有覆盖反例

搜索“为什么 X 很好”只会得到确认偏误。查询矩阵必须包含：

- limitation / unsupported / issue / failure；
- alternative / comparison / migration；
- breaking change / deprecated / security；
- 目标环境和版本号。

对每个候选方案主动回答：“什么条件下不要用它？”

## 4. 复制了参考实现，却复制错了上下文

参考代码可能依赖不同语言、运行时、许可证、数据模型和部署环境。WPS 案例中，Excel Chart 与 PPT MsoChart 看似接近，实际对象模型和数据注入方式不同。

应对方式：建立“参考资产—当前约束—转化方式—验证方法”四列表，而不是直接复制代码。

## 5. 总结压缩掉了关键限定词

视频和长文摘要容易丢失“仅在某版本”“实验性”“需要字幕”“不支持私有内容”等限定条件。建议：

- 所有强结论保留原文定位；
- 技术名词、命令和数字回看原始片段；
- 摘要字段中强制包含版本、环境和限制；
- 对转写文本保留时间戳。

## 6. 把 Prompt 当成可靠控制面

WPS Word 案例中，Prompt 要求批量操作后，模型仍逐段调用工具。最终通过数组参数从接口层提供批量能力。

原则：

> 能用类型、Schema、权限、测试和执行环境强制的规则，不只写在 Prompt 里。

## 7. AI 可能降低效率

METR 对 16 名熟悉自身成熟开源仓库的开发者、246 个真实任务进行随机对照研究，报告早期 2025 AI 工具使完成时间平均增加约 19%。这不是“AI 无用”的普遍结论，而是提醒：任务类型、工具时代、开发者熟悉度和审核成本会决定净收益。[METR 研究论文](https://metr.org/Early_2025_AI_Experienced_OS_Devs_Study-paper.pdf)

DORA 2025 则将 AI 描述为组织能力的放大器：它会放大已有的优势和弱点，收益来自底层系统而不只是工具采购。[DORA 2025](https://dora.dev/research/2025/dora-report/)

适合演讲的结论是：**在陌生信息搜索、批量阅读、重复迁移和可自动验证任务中，AI 更容易产生杠杆；在专家已熟悉的复杂仓库、验证成本高或目标模糊时，AI 可能制造额外工作。**

## 8. 只看最终结果，不检查过程

最终页面看起来正确，不代表 API 使用正确、边界条件安全或未来可维护。SWE-bench 将真实 GitHub Issue、代码仓库和单元测试组合起来评价 Agent 是否真正解决问题，而不是只评价生成文本。[SWE-bench](https://arxiv.org/abs/2310.06770)

可迁移到日常调研的门禁：

| 门禁 | 要求 |
|---|---|
| 来源门禁 | 关键结论至少有一个适用的一手来源 |
| 引用门禁 | 引用内容直接支持主张 |
| 版本门禁 | API 与案例标注目标版本和日期 |
| 反证门禁 | 主动搜索限制、失败和替代方案 |
| 实验门禁 | 关键未知点有最小可运行实验 |
| 工程门禁 | 类型检查、测试、构建或真实环境验证通过 |
| 沉淀门禁 | 结论写入可检索、可版本化的位置 |

## 9. 官方案例也需要识别激励与偏差

OpenAI、Google、GitHub、Anthropic 的工程案例是一手材料，但也是厂商发布内容；效率数字通常来自被选择的成功场景。使用时应同时说明：

- 数据由谁测量；
- 是否有对照组；
- 任务和样本是什么；
- 是否能迁移到听众场景；
- 哪些结果由自动测试验证，哪些来自自报。

因此，官方案例适合证明“这种工作流真实存在”，独立研究更适合证明“它并非在所有场景都提效”。

## 10. 在原网站上读得很认真，仍可能判断错来源

Lateral Reading 研究发现，专业事实核查者不会先在陌生网站内部读到底，而会快速离开原站，打开其他标签核查发布者、资助者和外部评价。这个方法可以直接迁移到技术资料：先确认项目维护者、许可证、Release、Issue 活跃度和外部引用，再投入深读。[Wineburg & McGrew](https://papers.ssrn.com/sol3/papers.cfm?abstract_id=3048994)

适合做成一个四步口诀：

> 停一下（Stop）→ 查来源主体 → 找更好的覆盖 → 追溯到原始上下文。

## 11. 多代理越多，不代表研究越好

Anthropic 的研究系统适合“多个相互独立方向”的广度问题；其内部数据也显示，多代理研究消耗的 token 显著高于普通聊天，而且强依赖、共享上下文多的任务并不适合并行。[Anthropic Engineering](https://www.anthropic.com/engineering/multi-agent-research-system)

因此并行前先问：

- 两个任务是否能在不共享中间结果的情况下独立推进？
- 是否能给每个研究者清晰、互斥的范围？
- 汇总者能否检查重复、冲突和遗漏？
- 任务价值是否值得额外成本？

## 12. 安全与可信不是最后一次人工扫一眼

NIST 的生成式 AI 风险管理框架建议持续验证来源与引用，并检查检索增强系统使用的数据和输出是否 grounded。对开发者演讲可转译为：来源校验、访问权限、敏感数据、供应链风险和输出验证都应进入工作流，而不是留到发布前补做。[NIST AI 600-1](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)

## 13. 连续生成失败后仍只改 Prompt

当结果“看起来完整但不能运行”时，继续要求 AI 重写，往往只是重复采样相近假设。Deck.gl 案例采用了更有效的切换条件：

1. 把失败现象拆成对象边界、数据语义、生命周期、版本兼容和非功能约束；
2. 把模型解释标成假设；
3. 为每个假设指定最合适的来源；
4. 多个解释竞争时，只改变一个变量做对照；
5. 把运行结果写回证据记录。

适合演讲的原则：**两轮生成仍没有收敛时，不要只升级 Prompt；升级问题分解、证据来源和反馈环境。** “两轮”是实践提醒，不是统计学阈值。

## 14. 把 AI 评审当作最终裁决

Dice 复盘中，评审曾因只检查一个测试文件而误报“缺少测试”；主线程依据 diff、实际文件和测试输出驳回了误报。同一轮中另一个定时器所有权问题有真实证据，因此被接受。

评审意见应走与搜索结果相同的裁决链：

```text
Finding → 定位文件/行为 → 检查 diff 与测试 → 必要时复现 → Accept / Reject / Defer
```

多一个 Agent 意味着多一组候选判断，不意味着自动获得真相。

## 15. 验证在演讲中的位置

验证是技术调研可信的必要闭环，但不是本次分享的叙事中心。正文保留三条即可：

- 关键事实尽量回到一手来源；
- 关键未知尽量落到最小可运行实验；
- 验证媒介与失败媒介匹配：源码、运行时、视觉和产品体验分别取证。

像素签名、自动拾取、初始化计数、定时器生命周期和完整测试矩阵属于案例证据层，适合附录、课后资料或现场追问，不应挤占“搜索—筛选—结构化—转化”的主体篇幅。
