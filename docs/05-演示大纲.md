# 演示大纲（材料期版本）

> 这不是最终页序，而是“哪些观点值得进入演讲”的候选结构。研究、证据切片和第一版 PPT/HTML 不受 45 分钟限制：先形成完整长版，冻结后再复制并删减为现场版。

## 主线

> 不要让 AI 直接从问题跳到答案。让它先扩大参考空间，再沿着文档、源码、视频、案例和实验建立证据链，最后把结论转化为可执行、可复用的开发资源。

## 第一幕：为什么要先找巨人的肩膀

- AI 很会生成一个“像答案的东西”，但它不知道你的版本、工程边界和验收标准是否匹配。
- 技术调研不是收集链接，而是为一个具体工程决策降低未知性。
- 人负责定义决策与风险；AI 适合扩展查询、批量阅读、定位源码、整理冲突和制作候选实验。

## 第二幕：一条可复用的调研流水线

1. 定义决策问题和硬约束；
2. 生成查询矩阵，扩大搜索空间；
3. 建立候选池并给来源分层；
4. 从种子来源追到文档、源码、Issue、视频和引用网络；
5. 把结论拆成主张—证据；
6. 将参考翻译到当前项目约束；
7. 用最小实现或对照实验消除关键未知；
8. 把结论、失败和停止条件写回仓库。

## 第三幕：三个完整案例与一个短案例

### 案例一：WPS——从外部参考到工程实现

重点：一个“轮子”不必整体复制；可以分别抽取 API 用法、架构边界、布局规则和测试方式，再适配当前约束。

### 案例二：视频——把不可搜索内容变成知识资产

重点：先用元数据筛选，再下载、转写、分段提取和外部核验；AI 把观看成本转换为可检索、可聚合的文本。

### 案例三：Deck.gl——从失败生成到定向调研

重点：停止盲目重试，将失败拆成问题；让模型提出假设，用官方文档、同版本源码和对照实验筛选候选路线。

### 短案例：Dice——让结论跨会话积累

重点：保存已确认、已排除和待验证内容；用风险优先纵向切片和任务 brief，把一次调研变成后续 Agent 可消费的资产。

## 第四幕：验证是闭环，不是主角

正文只讲三个原则：

1. 关键事实尽量回到一手来源；
2. 关键未知尽量落到最小可运行实验；
3. 验证媒介要匹配失败媒介：源码问题看源码，运行问题必须运行，视觉问题需要真实观察。

像素签名、自动 picking、计时器生命周期和完整测试矩阵保留为附录或课后材料，不在主体展开。

## 第五幕：把一次调研变成长期能力

- Research Brief：问题、约束、预算、完成条件；
- Evidence：来源、版本、事实、推断和冲突；
- Experiments：候选路线、控制变量和结果；
- Acceptance：如何证明足够好；
- Learnings：失败路线、负知识和下次优先验证项。
